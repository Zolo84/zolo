# Специфікація: бінарна карта (`lightmap*.tbl`, `boundbox.tbl`, `colorscales.csv`)

Область: карта світу Darkest Hour (Europa Engine, лінія HoI2) — растрові рівні деталізації, ідентифікатори
провінцій по пікселях, обмежувальні прямокутники провінцій, кольорові шкали та спосіб, у який із цього
будується зображення.

Джерело фактів — "Alternative HoI2 Editor" (C#, `/home/user/pylypenko99/hoi2editor/HoI2Editor`). Код
**не** копіюється; нижче — опис формату власними словами. Посилання `Файл.cs:рядок` дані відносно
`HoI2Editor/`. Усе, що виведено логічно, а не прочитано прямо в коді, позначено **(припущення)**.
Псевдокод у цьому документі — власний, у Rust-подібному стилі.

Прочитані файли: `Models/Map.cs` (повністю), `Models/Maps.cs` (повністю),
`Controllers/MapPanelController.cs` (повністю), а також пов'язані місця в `Models/Game.cs`,
`Models/Misc.cs`, `Models/Province.cs`, `Parsers/MiscParser.cs`, `Forms/ScenarioEditorForm.cs`,
`HoI2EditorController.cs`, `HoI2EditorSettings.cs`.

## 1. Огляд

* Карта зберігається у **чотирьох рівнях деталізації** (масштабах), кожен в окремому файлі
  `lightmap1.tbl` … `lightmap4.tbl` (`Models/Game.cs:423-438`, `Models/Map.cs:189-213`).
* Кожен рівень — це сітка **блоків 32×32 пікселі** (`Models/Map.cs:1508`, `Models/Map.cs:1513`).
  Розмір сітки не зберігається у файлі: редактор жорстко задає 936×360 блоків для рівня 1 і ділить на 2
  для кожного наступного рівня (`Models/Map.cs:103`, `Models/Map.cs:108`, `Models/Map.cs:131-132`).
* Файл починається з таблиці 32-бітних зміщень (по одному на блок + 1), далі йдуть стиснуті блоки.
* Кожен блок — **квадродерево** (quadtree) глибиною до 5 рівнів (32→16→8→4→2→1 піксель). Кожен лист
  дерева несе:
  1. індекс у локальному (на блок) списку ID провінцій;
  2. 6-бітне значення «освітлення/відтінку» (shade, 0..63) — значення у **лівому верхньому куті** листа.
* Зображення пікселів відновлюється **інтерполяцією** між кутовими значеннями листів (лист бере значення
  своїх сусідів праворуч і знизу), тому декодування йде від правого нижнього кута карти до лівого
  верхнього. ID провінцій інтерполяції не мають — кожен піксель листа отримує ID листа.
* Карта **замикається по горизонталі** (схід–захід): правим сусідом останнього стовпця блоків є стовпець 0
  (`Models/Map.cs:515-519`, `Models/Map.cs:539-543`). По вертикалі замикання немає.
* `boundbox.tbl` — масив 16-байтних записів, індексований ID провінції: прямокутник провінції в
  координатах рівня 1 (`Models/Maps.cs:285-312`).
* `colorscales.csv` — іменовані 64-ступеневі кольорові градієнти; 6-бітний shade пікселя вибирає
  ступінь (`Models/Maps.cs:317-450`).
* У самому декодері (`Map.cs`, `Maps.cs`) **немає розгалужень за типом гри**: формат однаковий для HoI2,
  AoD і DH. Від типу гри залежить лише **тека**, з якої беруться файли (див. §2 і §10).
* Редактор використовує карту лише на вкладці провінцій редактора сценаріїв, і лише **рівень 2**
  (`Forms/ScenarioEditorForm.cs:323`, `Controllers/MapPanelController.cs:147`): показ, клік → ID провінції,
  підсвічування провінцій.

Редактор **не читає** `id.tbl`, файли суміжності (adjacency) та інші `*.tbl` теки `map` — пошук за
`.tbl`, `id.tbl`, `adjacen`, `boundbox`, `lightmap`, `colorscales` по всьому репозиторію знаходить тільки
перелічені тут файли (див. §11, відкриті питання).

### 2.2 Тека карти

Функція вибору теки (`Models/Game.cs:808-820`):

* якщо гра — **не** DH, **або** `Misc.MapNumber == 0` → тека `map`;
* інакше (DH і `MapNumber != 0`) → тека `map\Map_<MapNumber>` (наприклад, `map\Map_1`).

`MapNumber` — це перше поле секції `map` у `db\misc.txt` (лише DH, див. §10). За відсутності значення
вважається 0 (`Models/Misc.cs:328`).

Усі шість файлів з §2.1 читаються з цієї ж теки (`Models/Map.cs:214`, `Models/Maps.cs:288`,
`Models/Maps.cs:319`) — у тому числі `colorscales.csv`.

### 2.3 Порядок пошуку (мод / тека експорту / оригінал)

`Game.GetReadFileName(folder, name)` (`Models/Game.cs:585-616`) будує відносний шлях `folder\name` і
перевіряє по черзі:

1. теку експорту (якщо активна) — `<export>\<шлях>` (`Models/Game.cs:587-594`, `Models/Game.cs:563-566`);
2. теку мода (якщо активна) — `<mod>\<шлях>` (`Models/Game.cs:595-602`, `Models/Game.cs:541-544`);
3. оригінальну теку гри — `<game>\<шлях>` (`Models/Game.cs:603`, `Models/Game.cs:519-522`).

Кандидат приймається, якщо існує файл **або тека** з таким ім'ям (`Models/Game.cs:590`, `Models/Game.cs:598`).
Якщо нічого не знайдено, повертається шлях в оригінальній теці навіть коли файлу там немає — відкриття
тоді завершується винятком (обробки помилок у `Maps.LoadFiles` немає, `Models/Maps.cs:253-280`).

Тека мода для DH — `<game>\Mods\<mod>` (`Models/Game.cs:303`, `Models/Game.cs:839-844`), для AoD/HoI2 —
`<game>\<mod>` (`Models/Game.cs:846-848`). Тека експорту — аналогічно (`Models/Game.cs:871-877`).

Важливо: при `MapNumber != 0` на кожному з трьох коренів шукається лише шлях `map\Map_N\<file>`;
**відкату на `map\<file>` немає**. Чи робить такий відкат сама гра — невідомо (§11).

### 2.4 Коли файли читаються

* Рівень завантажується ліниво у фоновому потоці: `Maps.LoadAsync(MapLevel.Level2, …)` при відкритті

* `boundbox.tbl` і `colorscales.csv` читаються один раз — разом із першим завантаженим рівнем
  (`Models/Maps.cs:264-274`).
* Повторне читання вимагається після зміни теки гри/мода (`Models/Maps.cs:117-126`,
  `HoI2EditorController.cs:115`).
* Користувач може заборонити читання карти взагалі (`Models/Maps.cs:47`, `Models/Maps.cs:135-138`,
  `HoI2EditorSettings.cs:321-325`).
* Бінарні файли читаються цілком у пам'ять одним викликом (`Models/Map.cs:216-220`, `Models/Maps.cs:291-297`).

## 3. Рівні деталізації та розміри

Перелік рівнів — `MapLevel` (`Models/Maps.cs:530-536`): `Level1 = 0`, `Level2 = 1`, `Level3 = 2`,
`Level4 = 3`. Числове значення рівня `L` використовується як величина зсуву.

* ширина сітки блоків `BW = 936 >> L` (`Models/Map.cs:103`, `Models/Map.cs:131`);
* висота сітки блоків `BH = 360 >> L` (`Models/Map.cs:108`, `Models/Map.cs:132`);
* розмір у пікселях: `BW·32 × BH·32` (`Models/Map.cs:481`, `Models/Map.cs:1010`, `Models/Map.cs:1028`).

| Рівень (`L`) | Файл | Блоків (BW×BH) | Кількість блоків N | Пікселів (Ш×В) | Розмір таблиці зміщень `(N+1)·4`, байт |
|---|---|---|---|---|---|
| `Level1` (0) | `lightmap1.tbl` | 936 × 360 | 336 960 | 29 952 × 11 520 | 1 347 844 |
| `Level2` (1) | `lightmap2.tbl` | 468 × 180 | 84 240 | 14 976 × 5 760 | 336 964 |
| `Level3` (2) | `lightmap3.tbl` | 234 × 90 | 21 060 | 7 488 × 2 880 | 84 244 |
| `Level4` (3) | `lightmap4.tbl` | 117 × 45 | 5 265 | 3 744 × 1 440 | 21 064 |

Примітки:

* Коментарі в коді (`Models/Game.cs:421`, `Models/Maps.cs:532-535`) підписують рівні як «936x360»,
  «468x180» тощо — це розміри **в блоках**, не в пікселях (936 не ділиться на 32, тож це не може бути
  піксельна ширина).
* Кожен наступний рівень — рівно вдвічі менший по кожній осі. Координати рівня 1 переводяться в рівень
  `L` зсувом `>> L` (`Models/Map.cs:1348-1351`).
* Файл не має ні сигнатури, ні заголовка з розмірами. Розміри треба знати заздалегідь (або перевіряти:
  `offsets[0]` зазвичай 0, а таблиця має рівно `N+1` записів) **(припущення)**.
* Обсяг пам'яті: масив ID (`u16`) для рівня 1 — ≈ 690 МБ, для рівня 2 — ≈ 172 МБ; масив shade (`u8`) —
  удвічі менше. Редактор тому працює тільки з рівнем 2. Для Rust-реалізації рекомендується
  декодувати блоки ліниво/з кешем **(рекомендація)**.

## 4. `lightmapN.tbl` — бінарний формат

Усі багатобайтні числа — **little-endian**.

### 4.1 Загальна структура файлу

```
зміщення 0                : u32le offsets[N + 1]      // N = BW * BH
зміщення 4·(N+1)          : область даних блоків
блок i починається з      : 4·(N+1) + offsets[i]
```

* Читання таблиці: `Models/Map.cs:227-239`; база області даних `(count + 1) * 4`: `Models/Map.cs:169`;
  перехід до блоку: `Models/Map.cs:174-178`.
* Порядок блоків — **рядками** (row-major): `i = by·BW + bx`, де `bx` — стовпець блоку зліва направо,
  `by` — рядок блоку згори вниз (`Models/Map.cs:1542-1546`, `Models/Map.cs:1530-1534`).
* Останній запис `offsets[N]` читається, але не використовується. Найімовірніше, це кінець області даних
  (= її довжина) **(припущення)**.
* Блок не має поля довжини: він самообмежений (див. §4.2). Редактор кожен блок читає з його власного
  зміщення, тож не залежить від того, чи блоки лежать підряд. Реалізація не повинна вважати зміщення
  монотонними чи унікальними (однакові блоки, напр. відкрите море, теоретично можуть спільно
  використовувати дані) **(припущення)**.

### 4.2 Структура блоку

Блок складається з чотирьох секцій, що йдуть одна за одною; кожна починається з **межі байта**
(`Models/Map.cs:244-254`):

| # | Секція | Розмір |
|---|---|---|
| A | Список ID провінцій блоку | `2·K` байт, `K` = 1..256 |
| B | Біти квадродерева | `ceil(bits/8)` байт, мінімум 1 |
| C | Індекси провінцій для листів | 0 / `ceil(M/8)` / `ceil(M/4)` / `ceil(M/2)` / `M` байт (залежить від `K`) |
| D | Shade листів | `3·ceil(M/4)` байт |

де `K` — довжина списку A, `M` — кількість листів дерева (1..1024).

#### 4.2.A Список ID провінцій (`Models/Map.cs:260-275`)

Послідовність слів `u16le`. Кожне слово `w` дає один елемент списку:

| Біти `w` | Маска | Значення |
|---|---|---|
| 15 | `0x8000` | 1 = це **останній** елемент списку |
| 14 | `0x4000` | 0 = пряме значення ID; 1 = посилання на вже прочитаний елемент |
| 0..13 | `0x3FFF` | ID провінції (при біті 14 = 0). Редактор маскує `0x7FFF`, але біт 14 тут нульовий, тож фактично 0..16383 (`Models/Map.cs:270`) |
| 8..13 | `0x3F00` | при біті 14 = 1: `j = ((w >> 8) & 0x3F) − 4` — індекс у **цьому ж** списку; елемент дорівнює `list[j]` (`Models/Map.cs:270`). Біти 0..7 ігноруються |

* Ознака кінця перевіряється **після** запису елемента (`Models/Map.cs:271`), тож список завжди має ≥ 1
  елемент.
* Максимум 256 елементів (`Models/Map.cs:113`, `Models/Map.cs:262`); більше — виняток у редакторі.
* Буфер списку — 256 нулів, тож індекс із секції C, що виходить за `K`, дає ID 0 замість помилки
  (`Models/Map.cs:262`, `Models/Map.cs:1055`).
* Посилання з `j < 0` (поле 0..3) у редакторі спричинило б виняток — валідні файли таких, очевидно, не
  містять **(припущення)**. Сенс зміщення «−4» і того, чому посилання взагалі потрібні (дубль ID у межах
  одного блоку), з коду не випливає (§11).

Приклади слів: `0x0123` → ID 291, не останній; `0x8456` → ID 1110, останній;
`0xC500` → останній, посилання, `j = 5 − 4 = 1` → копія `list[1]`.

#### 4.2.B Квадродерево (`Models/Map.cs:281-361`)

**Вузол** має рівень `l` і покриває квадрат `2^l × 2^l` пікселів з лівим верхнім кутом `(x, y)` у
координатах блоку. Корінь: `l = 5` (`MapTreeNode.MaxLevel`, `Models/Map.cs:1637`), `(0, 0)`
(`Models/Map.cs:286`).

**Читання бітів** (`Models/Map.cs:290-299`): біти беруться з байтів по черзі, **починаючи з молодшого**
(біт 0, потім біт 1, …, біт 7), потім наступний байт. Перший байт секції читається одразу при першому
біті. Невикористані старші біти останнього байта відкидаються; секція C починається з наступного байта.

**Алгоритм** (власний опис):

```text
поточний = корінь (l=5, x=0, y=0); стек = []
цикл:
    b = наступний біт
    якщо b == 0:                       // поточний вузол — лист
        додати лист (l, x, y) з номером = кількість_листів
        якщо стек порожній → кінець; інакше поточний = стек.pop()
    інакше якщо l >= 2:                // розбиття з подальшим читанням бітів
        h = 2^(l-1)
        стек.push((l-1, x,   y  ))     // TL
        стек.push((l-1, x+h, y  ))     // TR
        стек.push((l-1, x,   y+h))     // BL
        поточний = (l-1, x+h, y+h)     // BR — обробляється першим
    інакше (l == 1):                   // розбиття 2×2 на 4 пікселі — біти НЕ читаються
        додати листи рівня 0 у порядку: (x+1,y+1) BR, (x,y+1) BL, (x+1,y) TR, (x,y) TL
        якщо стек порожній → кінець; інакше поточний = стек.pop()
```

Наслідки:

* **Порядок обходу та нумерації листів**: прямий (pre-order) обхід з порядком дочірніх
  **BR → BL → TR → TL** (тобто «знизу-справа вгору-вліво»). Нумерація листів 0, 1, 2, … іде саме в цьому
  порядку (`Models/Map.cs:303`, `Models/Map.cs:346-349`). Той самий порядок має обхід під час
  відмальовування (`Models/Map.cs:1198-1220`).
* Вузли рівня 0 (1 піксель) ніколи не споживають бітів: піксельні листи з'являються лише через
  розбиття вузла рівня 1.
* Лист рівня `l ≥ 1` споживає 1 біт (0); розбиття вузла рівня `l ≥ 1` споживає 1 біт (1).
* `M` (кількість листів) = `NodeCount` (`Models/Map.cs:360`), 1 ≤ M ≤ 1024.
* Глибина стека ≤ 12 (по 3 на кожному з рівнів 5..2); редактор виділяє 2048 (`Models/Map.cs:171`).

#### 4.2.C Індекси провінцій листів (`Models/Map.cs:367-448`)

Для кожного листа (у порядку нумерації) — індекс у списку A. Ширина поля залежить від `K`:

| `K` (довжина списку A) | Біт на лист | Листів на байт | Байт у секції |
|---|---|---|---|
| 1 | 0 | — | 0 (секція відсутня, усі індекси 0) |
| 2 | 1 | 8 | `ceil(M/8)` |
| 3..4 | 2 | 4 | `ceil(M/4)` |
| 5..16 | 4 | 2 | `ceil(M/2)` |
| 17..256 | 8 | 1 | `M` |

Пакування: перший лист байта — у **молодших** бітах (біти 0.. для 1-бітних полів; біти 0-1, 2-3, 4-5, 6-7
для 2-бітних; молодший, потім старший напівбайт для 4-бітних). Залишкові поля останнього байта — доповнення,
ігноруються. Значення індексу ≥ K редактор не перевіряє.

#### 4.2.D Shade листів (`Models/Map.cs:454-470`)

Для кожного листа — 6-бітне значення 0..63. Групи по 4 листи в 3 байтах:

```text
g = b0 | (b1 << 8) | (b2 << 16)        // 24 біти little-endian
shade[4k+0] =  g        & 0x3F
shade[4k+1] = (g >>  6) & 0x3F
shade[4k+2] = (g >> 12) & 0x3F
shade[4k+3] = (g >> 18) & 0x3F
```

Байт: `3·ceil(M/4)`. Поля, що виходять за `M`, ігноруються. Після секції D блок закінчується.

**Повний розмір блоку**: `2K + ceil(bits_B/8) + bytes_C(K, M) + 3·ceil(M/4)`.

### 4.3 Робочий приклад 1 — повний блок (13 байт)

## 6. `colorscales.csv` — текстовий формат (`Models/Maps.cs:317-450`)

### 6.1 Кодування і рядки

* Читається `StreamReader` без явного кодування (`Models/Maps.cs:320`) — тобто UTF-8 з розпізнаванням
  BOM; для ASCII-вмісту це те саме, що CP1252. Справжнє кодування файлу гри — ймовірно ASCII/CP1252
  **(припущення)**.
* Кінці рядків — будь-які (`CRLF`, `LF`, `CR`) — так поводиться `ReadLine`.
* Роздільник полів — `;` (`Models/Maps.cs:330`, `Models/Maps.cs:379`).

### 6.2 Структура запису

Запис займає **6 рядків**:

1. **рядок назви**: порожні рядки перед ним пропускаються (`Models/Maps.cs:326-329`); назва = перше поле,
   з обрізаними подвійними лапками з обох кінців, у нижньому регістрі (`Models/Maps.cs:335`);
2. **рядок, що безумовно пропускається** (`Models/Maps.cs:336`) — імовірно заголовок/коментар
   **(припущення)**;
3. – 6. **чотири опорні точки** кольору (`Models/Maps.cs:338-361`), кожна: `R;G;B;Pos[;…]`
   * потрібно щонайменше 4 поля (`Models/Maps.cs:380`), зайві ігноруються;
   * кожне з перших чотирьох — ціле число (`int.TryParse`, допускає пробіли й знак)
     (`Models/Maps.cs:387`);
   * значення > 255 обрізаються до 255 (`Models/Maps.cs:391-394`); від'ємні не обробляються
     (колір → виняток у редакторі);
   * `Pos` — номер відтінку 0..64 у 64-елементній шкалі.

Якщо будь-яку опорну точку не вдалося розібрати, запис відкидається, і розбір продовжується **з
наступного рядка** (вже прочитані рядки назад не повертаються). Повторна назва перезаписує попередню
(`Models/Maps.cs:363`).

### 6.3 Побудова 64-ступеневої шкали (`Models/Maps.cs:404-450`)

Три відрізки `[P0, P1)`, `[P1, P2)`, `[P2, P3)` між опорними точками `C0..C3` (кольори) / `P0..P3`
(позиції). Для кожного каналу окремо, з фіксованою комою 10 біт:

```text
для k у 0..3:
    w = P[k+1] - P[k]
    d = if w > 0 { ((C[k+1] - C[k]) << 10) / w } else { 0 }   // ділення з відкиданням дробу до нуля
    v = C[k] << 10
    для i у P[k] .. P[k+1]:  шкала[i] = v >> 10;  v += d       // >> арифметичний
```

* Записи поза `[P0, P3)` лишаються «порожніми» (прозорий чорний, ARGB 0,0,0,0); сам `P3` не
  заповнюється. Тож очікувано `P0 = 0`, `P3 = 64` **(припущення; узгоджується з `docs/formats.md`)**.
* `Pos > 64` → вихід за межі масиву (виняток у редакторі).
* У редакторі є дрібна невідповідність регістру: перевірка наявності назви — у нижньому регістрі, а
  вибірка — за назвою як є (`Models/Maps.cs:497` проти `Models/Maps.cs:502`); з викликами редактора
  (усі назви малими) це не проявляється.

### 6.4 Ілюстративний приклад (вигаданий, не з файлу гри)

```
"orange";;;
R;G;B;Pos
255;220;150;0
230;160;80;20
180;100;40;45
90;40;10;64
```

Дає (R,G,B): `[0] = 255,220,150`, `[1] = 253,217,146`, `[19] = 231,163,83`, `[20] = 230,160,80`,
`[45] = 180,100,40`, `[63] = 94,43,11` (перевірено обчисленням з тими самими правилами округлення).

## 7. Відновлення пікселів (shade-зображення)

Результат декодування — масив `u8` розміром `Ш×В` пікселів (рядками), значення 0..63
(`Models/Map.cs:479-507`, `Models/Map.cs:1008-1021`).

### 7.1 Модель

* Shade листа — значення пікселя в **лівому верхньому куті** листа.
* Решта пікселів листа обчислюється з: (а) shade листа; (б) пікселя безпосередньо **під** лівим нижнім
  кутом листа `P[x, y+s]`; (в) стовпця пікселів безпосередньо **праворуч** від листа `P[x+s, y..y+s-1]`.
  Ці пікселі належать сусідам, які вже декодовано — тому порядок «знизу-справа вгору-вліво» і всередині
  блоку (BR → BL → TR → TL), і між блоками.
* Арифметика з фіксованою комою 8.8: значення множиться на 256 (`<< 8`), крок — різниця, зсунута
  **арифметично** вправо на `l` (тобто поділена на `s = 2^l` з округленням до −∞), піксель = `значення >> 8`.

### 7.2 Заповнення одного листа (точна поведінка редактора)

`Models/Map.cs:664-691` (буферний варіант) і `Models/Map.cs:697-985` (прямо в зображення) — однакова
семантика:

```text
fn fill_leaf(P, x, y, l, shade, cond):
    s = 1 << l
    якщо l == 0: P[x, y] = shade; return
    T  = shade << 8
    Bv = P[x, y + s] << 8
    dy = if cond(Bv - T) { (Bv - T) >> l } else { 0 }
    L = T
    для r у 0..s:
        R  = P[x + s, y + r] << 8
        dx = if cond(R - L) { (R - L) >> l } else { 0 }
        c = L
        для k у 0..s: P[x + k, y + r] = c >> 8; c += dx
        L += dy
```

Тобто лівий стовпець листа інтерполюється вертикально від shade до пікселя знизу, а кожен рядок —
горизонтально від лівого значення до пікселя праворуч у тому ж рядку.

**Умова `cond` у редакторі**: `d < SmoothingThrethold`, де поріг = `0 << 8 = 0`
(`Models/Map.cs:118`, `Models/Map.cs:676`, `Models/Map.cs:681`, `Models/Map.cs:710`, `Models/Map.cs:718`).
Отже інтерполяція відбувається **лише коли цільове значення менше** за поточне (спадний градієнт); при
рівності або зростанні рядок/стовпець заливається плоско. Коментар у коді називає це «без
згладжування», але фактично це «половинне» згладжування. Імовірно, гра виконує повну інтерполяцію
(`cond` завжди істинна) — сама будова формату (лише кут листа + сусіди справа/знизу) розрахована на неї
**(припущення)**. Рекомендація: зробити `cond` параметром — `EditorCompat` (`d < 0`), `Full` (завжди),
`Flat` (ніколи).

**Приклад** (лист рівня 2, 4×4, shade 40, піксель знизу 20, праворуч по рядках 48, 24, 30, 10):

`T = 10240`, `Bv = 5120`, `dy = −5120 >> 2 = −1280`.

| Рядок | L | R | Редактор (`d < 0`) | Повна інтерполяція |
|---|---|---|---|---|
| 0 | 10240 | 12288 | 40 40 40 40 | 40 42 44 46 |
| 1 | 8960 | 6144 | 35 32 29 26 | 35 32 29 26 |
| 2 | 7680 | 7680 | 30 30 30 30 | 30 30 30 30 |
| 3 | 6400 | 2560 | 25 21 17 13 | 25 21 17 13 |

(Перевірено еталонним Python-кодом.)

### 7.3 Порядок блоків і краї карти (`Models/Map.cs:479-507`)

1. блок (BW−1, BH−1) — правий нижній;
2. нижній рядок: `bx = BW−2 … 0`;
3. для `by = BH−2 … 0`: спочатку правий блок (BW−1, by), потім `bx = BW−2 … 0`.

**Внутрішні блоки** (не правий стовпець і не нижній рядок) малюються прямо в зображення: пікселі праворуч
і знизу вже є (`Models/Map.cs:594-600`).

**Крайові блоки** малюються в робочий буфер 33×33 (`Models/Map.cs:482`): `[0..32)×[0..32)` — сам блок,
стовпець 32 — «правий сусід», рядок 32 — «нижній сусід», `(32,32)` — кут. Після заповнення 32×32
копіюється в зображення (`Models/Map.cs:992-1003`). Стовпець/рядок/кут заповнюються так:

| Випадок | Стовпець 32 (рядки 0..31) | Рядок 32 (стовпці 0..31) | Кут (32, 32) |
|---|---|---|---|
| Правий нижній (BW−1, BH−1), `Models/Map.cs:512-530` | синтез із листів лівого краю блоку **(0, BH−1)** — замикання схід–захід | синтез із листів нижнього краю **цього ж** блоку | shade листа, що містить лівий нижній піксель блоку (0, BH−1), **`<< 2`** |
| Правий стовпець (BW−1, by), `Models/Map.cs:536-556` | синтез із листів лівого краю блоку **(0, by)** | копія 32 пікселів уже декодованого зображення — див. «Вада» нижче | shade лівого нижнього листа блоку (0, by), **`<< 2`** |
| Нижній рядок (bx, BH−1), `Models/Map.cs:562-587` | копія вже декодованого лівого стовпця блоку (bx+1, BH−1) | синтез із листів нижнього краю **цього ж** блоку | shade лівого нижнього листа блоку (bx+1, BH−1), **`<< 2`** |

**Синтез стовпця 32** (`Models/Map.cs:615-634`, обхід `Models/Map.cs:1254-1274`): перебираються листи
джерельного блоку з `x == 0`, **знизу вгору**. Для листа рівня `l` у рядку `Y`: значення в рядках
`Y..Y+2^l−1` стовпця 32 будуються від shade листа до вже записаного значення стовпця 32 у рядку `Y+2^l`
(для найнижчого листа — до кута) за тим самим правилом `cond`/8.8. Лист рівня 0 — просто shade.

**Синтез рядка 32** (`Models/Map.cs:640-658`, обхід `Models/Map.cs:1227-1247`): листи блоку з
`y + 2^l == 32`, **справа наліво**; для листа в стовпці `X` значення в `X..X+2^l−1` будуються від
shade листа до значення рядка 32 у стовпці `X+2^l` (для крайнього правого — до кута).

**Кут** (`Models/Map.cs:606-609`, обхід `Models/Map.cs:1281-1288`): спуск лише по BL-дітях до листа,
що містить піксель (0, 31) джерельного блоку.

Особливості й вади (для сумісності/свідомого відхилення):

* **Кут `<< 2`**: кутове значення множиться на 4 (до 252) — поза діапазоном 0..63. У редакторі це
  нешкідливо, бо при `d < 0` інтерполяція до більшого значення не виконується, а сам кут у зображення не
  копіюється. При повній інтерполяції це зіпсувало б крайові пікселі (і старші біти індексу кольору,
  §9), тому в реалізації кут слід брати без зсуву **(рекомендація)**.
* **Вада зміщення** (`Models/Map.cs:546-548`): для правого стовпця блоків рядок 32 мав би бути **першим**
  рядком блоку (BW−1, by+1) (рядок зображення `(by+1)·32`, стовпці від `(BW−1)·32`). Через використання
  піксельної ширини замість ширини в блоках редактор копіює **останній** рядок того блоку (рядок
  зображення `(by+2)·32 − 1`). Реалізація має брати перший рядок **(рекомендація)**.
* Нижній край карти не має реального сусіда: рядок 32 синтезується з кутових значень **нижніх листів
  самого блоку**, тож у листах, що торкаються низу карти, вертикального градієнта фактично немає.
* Синтез стовпця 32 використовує кутові значення листів, а не вже декодовані пікселі блоку (0, by), бо
  блок (0, by) у своєму рядку декодується останнім. Результат збігається з тим, що дало б декодування
  лівого стовпця блоку (0, by) за тим самим правилом, **крім найнижчого листа**: для нього ціллю є кут
  (`<< 2`), а не справжній піксель (0, 0) блоку (0, by+1).
* Буфер 33×33 не очищується між блоками, але кожен крайовий блок перезаписує всі використовувані комірки.

### 7.4 Діапазон значень

При `cond = d < 0` усі пікселі зображення лежать у 0..63 (значення лише зменшуються від кутового
значення до сусіднього, кут у зображення не потрапляє). Отже два старші біти байта вільні — їх
використовує палітра (§9).

## 8. ID провінції для пікселя

### 8.1 Повна розгортка (`Models/Map.cs:1026-1187`)

* Масив `u16` `Ш×В` (рядками), індекс `y·Ш + x` (`Models/Map.cs:1666-1670`).
* Для кожного блоку `(bx, by)` (порядок не важливий): для листа `n` — `id[n] = list[index[n]]`
  (`Models/Map.cs:1053-1056`); усі пікселі квадрата листа отримують `id[n]` **без інтерполяції**
  (`Models/Map.cs:1067-1187`). Початок блоку в масиві: `by·32·Ш + bx·32` (`Models/Map.cs:1059`).
* Клік мишею: `ID = ids[y·Ш + x]` для координат пікселя рівня 2 (`Controllers/MapPanelController.cs:396-401`).

### 8.2 Довільний доступ (рекомендація, не з редактора)

```text
fn province_at(level, x, y):
    bx = x >> 5; by = y >> 5; i = by*BW + bx
    блок = parse_block(дані[4*(N+1) + offsets[i] ..])
    знайти лист, що містить (x & 31, y & 31)   // листи покривають блок без перетинів
    return блок.list[блок.index[лист.номер]]
```

Секцію B не можна «перестрибнути» без розбору: дерево самообмежене, довжини секцій C/D залежать від `M`.
Тому має сенс кешувати розібрані блоки.

## 9. Палітра, кольори та межі (як редактор малює карту)

### 9.1 Байт пікселя і палітра

* Зображення — 8 біт на піксель з палітрою 256 кольорів (`Models/Map.cs:1010-1017`).
* Палітра = **4 групи × 64 відтінки** (`Models/Maps.cs:80`, `Models/Maps.cs:85`, `Models/Maps.cs:514`):
  індекс палітри = `(група << 6) | shade`.
* Група провінції зберігається як байт-маска `група << 6` у масиві на 10 000 провінцій
  (`Models/Maps.cs:71`, `Models/Maps.cs:99`, `Models/Maps.cs:461-487`).
* Оновлення провінції (`Models/Map.cs:1345-1394`): у межах її прямокутника з `boundbox.tbl`, зменшеного
  до рівня (`>> L`), кожен піксель, чий ID дорівнює ID провінції, отримує `(байт & 0x3F) | маска` —
  shade зберігається, змінюються лише старші 2 біти. Якщо `x + ширина` виходить за ширину зображення,
  прямокутник розбивається на дві частини: `[x, Ш)` і `[0, x + ширина − Ш)` (горизонтальне замикання,
  `Models/Map.cs:1353-1361`).
* Початкова палітра (до застосування шкал) — сірий градієнт: для відтінку `j` колір
  `RGB(255 − 4j, 255 − 4j, 255 − 4j)` у кожній групі (`Models/Maps.cs:512-522`). Тобто shade 0 —
  найсвітліший, 63 — найтемніший (значення 3).
* Після декодування всі пікселі мають групу 0.

### 9.2 Групи кольорів редактора

`Controllers/MapPanelController.cs:116-122`, імена шкал — `Controllers/MapPanelController.cs:212-218`:

| Група | Значення | Шкала з `colorscales.csv` |
|---|---|---|
| 0 | `Land` (суша, звичайна) | `orange` |
| 1 | `Sea` (море) | `water` |
| 2 | `Highlighted` (підсвічена) | `green` |
| 3 | `Invalid` (недійсна) | `black` |

Шкала копіюється в групу цілком (64 записи) (`Models/Maps.cs:494-507`). Якщо назви немає, група
лишається сірою.

Класифікація провінцій за `Terrain` з `province.csv` (`Models/Province.cs:295-354`;
`Controllers/MapPanelController.cs:163-195`):

* суша: `Plains, Forest, Mountain, Desert, Marsh, Hills, Jungle, Urban, Clear` → група 0;
* море: `Ocean, River` → група 1;
* недійсні: `TerraIncognito, Unknown` → група 3.

Пропускаються провінції з `Id <= 0` або `Id >= кількість записів boundbox.tbl`
(`Controllers/MapPanelController.cs:165-171`).

Підсвічування (група 2) залежить від режиму фільтра (`Controllers/MapPanelController.cs:100-107`,
`Controllers/MapPanelController.cs:334-371`): `None`, `Core` (національні), `Owned` (власні),
`Controlled` (контрольовані), `Claimed` (претензії) — за відповідними списками країни в сценарії.
Оновлюються лише провінції, що змінили стан (`Controllers/MapPanelController.cs:305-326`).

### 9.3 Межі провінцій

Редактор **не малює** межі явно — ні окремим проходом, ні з порівняння сусідніх ID. Видимі межі —
лише ті, що «запечені» у shade-дані, та контраст між групами кольорів **(припущення)**. Гра, імовірно,
малює межі сама, порівнюючи ID сусідніх пікселів (`id(x,y) != id(x+1,y)` або `id(x,y) != id(x,y+1)`)
**(припущення / рекомендація для нашого рендера)**.

### 9.4 Прокрутка

Центрування на провінції бере прямокутник з `boundbox.tbl` і ділить на 2 (`>> 1`) — жорстко під рівень 2
(`Controllers/MapPanelController.cs:224-274`). Це підтверджує, що `boundbox.tbl` — у координатах рівня 1.

## 10. Відмінності DH від AoD / HoI2

1. **Тека карти** (`Models/Game.cs:808-820`): лише в DH при `MapNumber != 0` усі файли карти
   (`lightmap1..4.tbl`, `boundbox.tbl`, `colorscales.csv`) читаються з `map\Map_<N>\`; в AoD/HoI2 (і в DH
   з `MapNumber = 0`) — з `map\`.
2. **Супутні переміщення файлів у DH-карті** (ті самі умови):
   * `province.csv`: `db\` → `map\Map_<N>\` (`Models/Game.cs:753-763`, `Models/Provinces.cs:3587`);
   * `province_names.csv`: `config\` → `map\Map_<N>\` (`Models/Game.cs:769-779`, `Models/Config.cs:322-326`);
   * зображення провінцій: `gfx\interface\ill_prov_<id>.bmp` → `map\Map_<N>\gfx\ill_prov_<id>.bmp`
     (`Models/Game.cs:786-802`, константа `gfx` — `Models/Game.cs:298`).
3. **Тека мода**: DH — `<game>\Mods\<mod>`, інші — `<game>\<mod>` (`Models/Game.cs:839-848`); так само
   тека експорту (`Models/Game.cs:871-877`).
4. **Секція `map` у `db\misc.txt`** існує лише в DH (усі версії DH 1.02/1.03/1.04)
   (`Models/Misc.cs:385`, `Models/Misc.cs:403`, `Models/Misc.cs:2169-2173`, `Parsers/MiscParser.cs:164-170`).
   Поля в порядку (`Models/Misc.cs:1298-1305`, `Models/Misc.cs:4322-4326`):

   | # | Назва | Тип | Діапазон | Посилання |
   |---|---|---|---|---|
   | 1 | `MapNumber` | невід'ємне ціле | ≥ 0; 0 = стандартна карта | `Models/Misc.cs:3037` |
   | 2 | `TotalProvinces` | ціле в діапазоні | 1..10000 | `Models/Misc.cs:3038`, `Models/Misc.cs:3179`, `Models/Misc.cs:3319` |
   | 3 | `DistanceCalculationModel` | перелік | 0 = Old, 1 = New | `Models/Misc.cs:3039`, `Models/Misc.cs:3180`, `Models/Misc.cs:3320` |
   | 4 | `MapWidth` | додатне ціле | > 0 | `Models/Misc.cs:3040` |
   | 5 | `MapHeight` | додатне ціле | > 0 | `Models/Misc.cs:3041` |

   Редактор використовує для карти лише `MapNumber`. `MapWidth`/`MapHeight` **ігноруються** декодером —
   розмір сітки блоків жорстко 936×360 (`Models/Map.cs:103`, `Models/Map.cs:108`). Одиниці
   `MapWidth`/`MapHeight` з коду не видно (§11).
5. **«DH Full»** = DH і `MapNumber > 0` (`Models/Game.cs:890-893`). Тип гри визначається за наявністю
   `Darkest Hour.exe` у теці гри (`Models/Game.cs:907`).
6. Ліміт провінцій редактора — 10 000 (`Models/Maps.cs:71`), що збігається з максимумом
   `TotalProvinces` у DH. ID у lightmap може бути до 16 383 (14 біт), тож ID ≥ 10 000 у редакторі
   спричинили б вихід за межі масиву масок.
7. Сам бінарний формат `lightmap*.tbl` / `boundbox.tbl` / `colorscales.csv` у редакторі **однаковий**
   для всіх ігор (розгалужень за `Game.Type` у `Map.cs`/`Maps.cs` немає).

Не плутати: секція `map = { … }` у файлах сценаріїв (`Parsers/ScenarioParser.cs:187-193`,
`Parsers/ScenarioParser.cs:1716`, ключі `yes`, `no`, `top`, `bottom`, …) — це налаштування області
сценарію, не бінарна карта; вона описується в специфікації сценаріїв.

## 11. Відкриті питання

1. **Біт 14 у списку ID** (§4.2.A): чому посилання на попередній елемент кодується як `(біти 8..13) − 4`,
   і чи мають сенс біти 0..7 такого слова? Можливо, у грі індекси 0..3 зарезервовані під щось інше
   (наприклад, ID сусідніх блоків) **(припущення)**. Потрібна перевірка на реальних файлах.
2. **Інтерполяція в грі**: повна (обидва знаки різниці) чи як у редакторі (лише спадна)? Що гра бере як
   «правого/нижнього сусіда» на краях карти, і чи множить кут на 4?
3. **Сенс shade**: рельєф/освітлення, чи в ньому «запечені» межі провінцій і берегові лінії? Як гра
   малює межі провінцій/країн?
4. **`offsets[N]`**: чи це завжди довжина області даних? Чи бувають спільні (дубльовані) зміщення?
5. **`boundbox.tbl`**: що в байтах 2-3, 6-7, 10-11, 14-15 (старші половини `i32`?); як кодуються
   провінції, що перетинають шов карти; чи є запис для ID 0.
6. **`colorscales.csv`**: справжній вигляд файлу (що в другому рядку запису, діапазон `Pos` — 0..63 чи
   0..64, які ще назви шкал існують — напр. для кольорів країн) і кодування.
7. **DH `MapWidth`/`MapHeight`**: у яких одиницях і чи можуть карти `Map_N` мати сітку, відмінну від
   936×360 блоків? Редактор цього не враховує.
8. **Відкат шляхів**: чи шукає гра файл у `map\`, якщо його немає в `map\Map_N\`?
9. **Файли, яких редактор не читає**: `id.tbl`, файли суміжності провінцій (adjacency) та інші `*.tbl`
   у `map\` — потрібні інші джерела (реверс-інжиніринг гри).
10. **Координати в `province.csv`** (`CityXPos`, `ArmyXPos`, `FillCoordX1` тощо,
    `Models/Province.cs:1299-1334`): у якій системі координат (рівень 1?) — редактор їх з картою не
    пов'язує.
11. **ID 0**: чи означає «немає провінції»/terra incognito у пікселях lightmap? Редактор лише
    пропускає `Id <= 0` при розфарбовуванні.
12. **Співвідношення** `TotalProvinces` (misc), кількості записів `boundbox.tbl` і кількості рядків
    `province.csv` — що з них гра вважає авторитетним.
