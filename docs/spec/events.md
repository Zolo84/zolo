# Специфікація: події, тригери, вибір дії й команди (DH 1.05.1)

Позначки: ✅ простежено в коді; 🔎 частково/непрямо; ❓ відкрите. Адреси — VA (база 0x400000). Країна, для якої
перевіряється подія, — `C`; подія — `E`; дія — `A`; `misc ai[n]`, `mod[n]` — позиції в секціях `db/misc.txt`.

**Статус перевірки.** Усі шість груп тверджень незалежно перевірено вдруге за дизасемблером і власним розбором
файлів гри (§9): завантаження, планування, тригери, правила доступності й вибору, типи й обробники команд і приклад
Рейнської області підтверджено; спростовано три твердження — `under_attack` (справжній тригер), «85.01 %» (зміщення
15-бітного `rand()`) і «усі команди синхронні». Реалізація — `dh-data::events`, `dh-sim::events`.

## 1. Завантаження й модель ✅

### 1.1 Файли
* Рядок сценарію `event = "файл"` передає файл завантажувачу менеджера подій (`0x6FFA60`); `include` у сценарії
  підключає `db/events.txt`, який сам складається з таких рядків. Порядок (для 1936: спершу `AI_*.txt` із `.eug`,
  потім `db/events.txt`, потім файли країн) — це порядок додавання подій і постановки їхніх перевірок.
* Спершу шукається копія в активному моді, потім ванільний файл; відсутній файл лише записується в лог.
* Усередині файлу: `event = {…}` — подія, `include` — рекурсивно; **будь-який інший ключ верхнього рівня
  обриває завантаження решти файлу** (`0x6FFCB2`).
* Ванільний 1936: **114 файлів, 2255 подій, без повторів ID**.

### 1.2 Подія
| ключ | зміст | за замовч. |
|---|---|---|
| `id` | номер | — |
| `name`, `desc`, `picture`, `style` | тексти (ключі локалізації), картинка, стиль вікна; `name = "AI_EVENT"` — без новин | `events_empty`, 0 |
| `country` | країна-адресат | будь-яка |
| `tag = {…}` | список адресатів | — |
| `province` | провінція (власник стає адресатом, якщо країни немає) | −1 |
| `date`, `offset`, `deathdate` | перша дата, крок повторних перевірок у днях, остання дата | 0 |
| `random`, `persistent`, `invention` | рандомна, постійна, винахід | ні |
| `save_date` | писати дату спрацювання (для тригера `event = {id days}`) | ні |
| `one_action`, `all`, `decision*` | (`all` — для команди `trigger`; рішення в ванілі вимкнені) | — |
| `trigger = {…}` | умова; порожня — істина | — |
| `action_a`..`action_d`, `action` | **однаково**: кожна додається в кінець у порядку файлу, індекс дії = позиція | — |

Дія: `name`, `ai_chance` (за замовч. **−1**), необов'язковий `trigger`, команди `command = { type which value when
where … }` (невідомий `type` — «незаконна» команда). Дати: `{ year month day hour }`, місяці словами або числом,
день обрізається до 0..29; календар 360 днів (12 × 30). Ключі нечутливі до регістру. Перевірки якості (дублікати
ключів, відсутні картинки, дати без offset тощо) — лише повідомлення в журналі налагодження.

### 1.3 Після розбору
* Нерандомна подія з `offset > 0`: **`date += rand() % offset` днів** (`0x70D180`) — перша перевірка розкидана в
  межах `[date, date + offset − 1]`.
* Винаходи й рандомні події лише потрапляють у свої пули. Решта (`0x700D50`): якщо остання дата
  (`deathdate`, а без неї `date + offset`) уже минула, подія вже в історії або приспана — не планується; інакше
  перевірка ставиться на `date` (якщо вона не в майбутньому — на `сьогодні + rand() % offset`, або завтра за
  `offset = 0`) **окремо для кожного адресата**: країни `country`, кожного тегу `tag`, а без обох — кожного з 343
  слотів країн. Повідомлення несе власне насіння `rand()`.
* «Сьогодні» на завантаженні — дата старту сценарію (1936-01-00), встановлена до читання подій.

## 2. Планування й спрацювання ✅

### 2.1 Перевірка (`0x700210`)
```
лише на авторитетному вузлі
подія приспана або вже виконана → нічого
C := країна слота; немає → власник провінції події; немає й того → якщо подія не в історії й сьогодні < deathdate:
     повторити через offset + 1 днів (так подія може спрацювати для країни, що з'явиться пізніше)
нерандомна й уже в історії → нічого
якщо тригер(C) і є хоч одна доступна дія (§3): спрацювати (§2.2); рандомна — ще й запланувати наступну рандомну
інакше: якщо сьогодні < deathdate → повторити через offset днів; інакше перевірок для цієї країни більше немає
```
Тобто перевірка **періодична, а не щоденна**: на дату, далі кожні `offset` днів до `deathdate`; **без `deathdate` —
одна перевірка**. Подія без адресата перевіряється для всіх країн; перша, для якої тригер істинний, виконує її, і
неперсистентна подія блокується для решти (історія глобальна).

### 2.2 Спрацювання (`0x712010`)
`srand(насіння повідомлення)`; якщо жодна дія не доступна — нічого. Людині (своя країна) — вікно з кнопками
(таймера в обробниках немає); ШІ, опція «автовідповідь» (`mod[14]`) або спостерігач — вибір ШІ (§3.2). Вибір
надходить окремим повідомленням і виконується (§2.3).

### 2.3 Виконання вибору (`0x711960`)
* Подія вже в історії → нічого (захист від повтору).
* `invention` → у список винаходів **країни**; інакше неперсистентна нерандомна → у **глобальну історію**.
* Обрана дія (за позицією) виконує свої команди (§4) з `C` як суб'єктом; новини й журнал.
* `persistent` після виконання перепланується на `сьогодні + offset`, поки є остання дата; у історію не пишеться.

### 2.4 Рандомні події
Лише для країн, якими керує **людина** (для ШІ — ніколи). На старті гри й після кожної виконаної рандомної події
(`0x6FFF20`): до 101 спроби вибрати з пулу подію, що не очікує вибору, підходить країні (`country` / `tag`) і має
істинний тригер (прийнятися можуть лише перші 100); дата — `сьогодні + rand() % r + r/2`, `r = 133` для урядів
SC/ML/SL/SD (66..198 днів), інакше 400 (200..599). Якщо на дату тригер хибний — ланцюжок країни **обривається**.

### 2.5 Винаходи
Щодня з добового обробника країни: `rand() % 360 ≤ research[5]` → серед винаходів країни з істинним тригером
обирається той, що отримав найбільше `rand() & 0x3FF` (research.md §8).

## 3. Тригери й вибір дії ✅

### 3.1 Будова
* `and` і верхній рівень — усі діти істинні (**порожній — істина**); `or` — хоч одна (**порожній — хиба**); `not` —
  **жодна** дитина не істинна (кілька дітей — NOR).
* Невідомий ключ, що є назвою типу дивізії, — «кількість дивізій типу ≥ N»; інший невідомий ключ пропускається
  (вузол не створюється).
* Суб'єкт — `C`; для пар країн `{ country = A country = B }` пропущений чи хибний тег означає `C`, неіснуюча країна
  — хиба.

### 3.2 Найуживаніші тригери (кількість у ванілі 1936: not 3378, alliance 1700, control 1629, ai 1416, war 1120, …)
| тригер | істина, якщо |
|---|---|
| `year` / `month` / `day = N` | поточне значення ≥ N (місяць 0..11, день 0..29) |
| `dissent = N` | dissent C ≥ N |
| `manpower = N` | людські ресурси C **> N** (строго) |
| `random = N` | `rand() % 100 ≤ N` **після перезасівання від таймера реального часу** — у грі недетерміновано |
| `ai = yes/no` / `ai = TAG` | C (або TAG) під ШІ / ні |
| `atwar = yes/no` | C воює з будь-ким |
| `atwar = TAG` | **TAG воює з будь-ким** (не «C з TAG») |
| `under_attack = TAG` | TAG (або C) існує, воює і є стороною, що обороняється, хоч у одній війні |
| `exists = TAG`, `country = TAG` | слот TAG зайнятий; C — це TAG |
| `ispuppet = yes / TAG` | C / TAG має сюзерена; **`ispuppet = no` завжди хиба** |
| `event = N` | N в історії і не приспана — тож для persistent і рандомних подій завжди хиба |
| `event = { id days }` | лише для подій із `save_date = yes`: минуло ≥ days днів |
| `flag`, `local_flag` | значення прапорця (глобального / країни; відсутній = 0) порівняне з `value` (за замовч. 1) за `when` (−2 <, −1 ≤, 0 =, 1 ≥ (типово), 2 >) |
| `minister = ID`, `leader = ID` | існує й активний — **країна не перевіряється** |
| `headofstate`, `headofgovernment`, `incabinet` | міністр у відповідному слоті / будь-якому слоті C |
| `government`, `ideology` | тип уряду C (або `country`) з ідеології міністрів |
| `alliance`, `war`, `access`, `non_aggression`, `guarantee`, `trade` | між A і B (для доступу й пакту — у записі B про A) |
| `puppet = { A B }` | **A — маріонетка B** |
| `control` / `owned = { province data }` | контролер / власник провінції — тег, C (0/−1), ворог C (−2), друг C (−3) |
| `garrison = {…}` | дивізій країни/фільтра в провінції (області, регіоні) ≥ size |
| `technology`, `is_tech_active` | технологію відомо / не деактивовано |
| `relation = { which value }` | відносини C → which ≥ value |
| `difficulty`, `domestic`, `can_change_policy`, `belligerence`, `attack`, `lost_national`, `land_percentage` | див. нотатки реалізації |

### 3.3 Доступність дії
Дія доступна, якщо її власний `trigger` істинний і **хоча б одна команда валідна** (власний `trigger` команди,
існування цілі тощо); у рандомних подіях вирішує **перша** команда. Дія без валідних команд недоступна (ванільний
`mod[15] = 0`); подія без доступних дій не спрацьовує.

### 3.4 Вибір ШІ (`0x711DB0`)
```
доступні дії з шансами (ai_chance ≥ 0, інакше −1); одна доступна → вона
G := misc ai[24] (ваніль 85)
сума додатних шансів > 0:
    G = −3 → перша з найбільшим шансом;  інакше r := rand() % сума — пропорційно; шанс 0 чи −1 не обирається ніколи
жодного додатного шансу:
    G = −1 → rand() % n рівноймовірно;  G = −2/−3 → перша
    інакше p := round((100 − G)/(n − 1)·100);  перша отримує 10000 − (n − 1)·p,  кожна інша p;
           r := rand() % 10000, вибір за накопиченими межами
```
`rand()` гри **15-бітний** (0..32767), тож `rand() % 10000` зміщений до 0..2767: за G = 85 перша з двох дій
обирається з імовірністю **28271/32768 = 86.28 %** (з трьох — 86.28 / 6.87 / 6.86 %), а не 85.01 %. Сума шансів не
нормується до 100 (98/2 → 98 % / 2 %).

## 4. Команди ✅

### 4.1 Виконання (`0x713490`)
Команди дії йдуть у порядку файлу; перед кожною — перевірка валідності. Суб'єкт — `C`; `which` — друга сторона, ID
або параметр. Ефекти технологій виконуються тим самим кодом із тимчасовою подією. Дві групи:
* **Відкладені** (у чергу планувальника; набувають чинності **після всієї дії**): dissent, money, supplies, пули
  ресурсів, manpowerpool, relation, set_relation, peace, belligerence, access, gain_tech, peacetime_ic_mod,
  make_puppet, free_*.
* **Негайні**: secedeprovince, trigger, war, addcore/removecore, control, domestic/set_domestic, прапорці,
  activate/deactivate, delete_unit, sleepleader/sleepminister, ai, alliance, inherit, add_division.

Наслідок для Рейнської області: події 51 і 52, викликані `trigger`, виконуються раніше, ніж до Німеччини дійдуть
зміни відносин, dissent і грошей.

## 5. Приклад: ремілітаризація Рейнської області ✅
* **2060** (для ШІ): `country = GER`, `date` 1936-03-06, без offset і deathdate → **одна перевірка** 6 березня;
  тригер `ai = yes`, Німеччина не воює й не в альянсі з Францією. Одна дія без `ai_chance` (P = 1). Команди:
  відносини з FRA −15, ENG −5, BEL −10, HOL −5; belligerence Німеччини +5; dissent −2; гроші +500; мирний модифікатор
  IC +10; людські ресурси +50; `trigger 51` (Англія: мирний модифікатор IC +10, defense_lobby +1, людські ресурси
  +15) і `trigger 52` (Франція: мирний модифікатор IC +10, людські ресурси +15) — обидві виконуються одразу й до
  відкладених змін Німеччини; інший AI-файл; `sleepevent 2000`; defense_lobby +1.
* **2000** (для людини): з 1936-01-01, `offset = 1`, deathdate 1963 → перевірка **щодня**, поки гравець не введе
  дивізію в провінцію 75 (Вестфалія); ШІ-Німеччина приспить її подією 2060.
* **2061** (людина, `persistent`, offset 45, до 1963): перевіряється кожні 45 днів до 1963 і спрацьовує, лише поки
  тригер істинний (dissent < 13, 2000 ще не сталася, немає війни/альянсу з Францією): dissent +3.

## 6. Реалізація в `dh-sim`
`dh-data::events` завантажує файли подій сценарію (з `include`, копією з моду, обривом файлу на невідомому ключі) у
типізовані події, тригери й команди; ваніль 1936 — 114 файлів, 2255 подій без попереджень. `dh-sim::events`
(система `Events`) планує перевірки з розкидом дат, повтором до `deathdate`, глобальною історією, persistent,
`sleepevent` і негайним `trigger`; оцінює тригери; обирає дію ШІ точно за §3.4 (15-бітний `rand()`, 86.28 %);
виконує відкладені й негайні команди §4.1 у правильному порядку. Тест на реальних даних відтворює ланцюжок §5:
2060 перевіряється один раз і спрацьовує 6 березня (день 6 у нумерації гри з 0 — 7 березня за звичайним
календарем), 51 і 52 — того ж тіку, усі зміни відносин, belligerence, dissent, грошей, людських ресурсів і повзунків
лягають як у грі, 2000 приспано, 2061 не спрацьовує. Прогін року всіх ванільних подій — без збоїв.
Спрощення: `random = N` і перезасівання гри — детермінований `Rng`; перевірки одного дня — у порядку постановки;
`offset = 0` з повтором чекає добу; рандомні події не запускаються (усі країни — ШІ); не змодельовані тригери
(міністри, уряд/ідеологія, гарантії, `can_change_policy`, `land_percentage`, гарнізон за областю, кількість
дивізій) дають хибу, а не змодельовані команди (міністри, `ai`, `peacetime_ic_mod`, `free_*`, юніти) лише
рахуються; `war` не залучає союзників, `alliance`/`peace` — за спрощеними правилами.

## 7. Відкриті питання
1. Порядок повідомлень з однаковою міткою часу й година доби, коли перевіряються події, відносно добового обробника
   країн.
2. `offset = 0` разом із `deathdate` (у ванілі немає).
3. Рішення (`decision`, вимкнені в ванілі), повні словники значень команд, складні обробники (війна, альянси,
   анексія, маріонетки, незалежність, юніти, передача провінцій), рідкісні тригери.
4. Чи має вікно події таймер; яка з двох подій з однаковим ID перемагає; чи перезапускаються рандомні ланцюжки після
   завантаження збереження.

## 9. Незалежна перевірка: поправки ✅
1. **`under_attack` — справжній тригер** (перший прохід вважав його невідомим ключем): істина, якщо TAG (або C)
   існує, воює і обороняється хоч у одній війні.
2. **Вибір ШІ без шансів зміщений**: `rand()` 15-бітний, тож перша з двох дій за G = 85 — 86.28 %, а не 85.01 %
   (з реальним засіванням і без інших викликів `rand()` між ними — 87.17 %).
3. **Не всі команди синхронні**: частина йде в чергу планувальника й діє після всієї дії (§4.1).
4. Невідомий ключ верхнього рівня у файлі подій обриває завантаження решти файлу.
5. Рандомний планувальник тягне до 101 кандидата, але прийняти може лише перших 100.
6. Нові деталі: `gain_tech` дає креслення; `access` — односторонній доступ без згоди (перевірка прочитала напрям як «C отримує доступ до `which`»; за семантикою запису відносин у русі військ і за документацією гри доступ отримує `which` на території C); `set_relation` бере цілу
   дельту, обчислену до відкладених змін; власник провінції поточної події переважає `country` події-цілі в
   `trigger`; 2061 перевіряється до 1963, лише не спрацьовує при хибному тригері.
7. Підтверджено: завантаження й поля, порядок дій, `ai_chance = −1`, розкид дати, постановка для кожного адресата
   (343 слоти), правила повторних перевірок, історія, persistent, винаходи, рандомні події лише для людини,
   семантика `and`/`or`/`not` і всіх названих тригерів (кількості використань збігаються), правила доступності й
   `rand() % сума`, типи й обробники команд, обмеження грошей, ресурсів, відносин, dissent і прапорців, числа
   прикладу; 114 файлів, 2255 подій, без повторів ID.
