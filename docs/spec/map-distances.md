# Специфікація: таблиці відстаней (`airdist.tbl`, `navaldist.tbl`, `navaldist2.tbl`, `distances.csv`)

Область: як Darkest Hour 1.05.1 (GOG) зберігає та обчислює відстані між провінціями — «повітряні»
(по великому колу) і «морські» (уздовж морського маршруту), і як на це впливає параметр
`DistanceCalculationModel` у `db\misc.txt`.

Джерело фактів — `Darkest Hour.exe` (32-бітний PE, база образу `0x400000`), розібраний за адресами
(VA). Код гри **не** копіюється: нижче — опис поведінки власними словами; адреси, розміри та
константи наведено точно, щоб кожен міг перевірити. Перевірка на реальних файлах — еталонним
декодером (Python, лежить поза репозиторієм).

Позначки:

* ✅ — підтверджено на справжніх файлах гри (декодування, порівняння, повторне обчислення);
* 🔎 — прочитано з коду `Darkest Hour.exe` (адреса VA вказана поруч);
* ❓ — гіпотеза / не перевірено до кінця.

Пов'язані документи: [map.md](map.md) (тека карти `map` / `map\Map_N`), [leaders-ministers-misc.md](leaders-ministers-misc.md)
(секція `map` у `misc.txt`: `MapNumber`, `TotalProvinces`, `DistanceCalculationModel`).

## 2. Параметр `DistanceCalculationModel` (`db\misc.txt`)

Секція `map = { … }` у `db\misc.txt` — позиційні числа без імен (імена — з HoI2Editor):

| № | Назва | Куди потрапляє (🔎 `0x78C4B5..0x78C505`) |
|---|---|---|
| 1 | `MapNumber` | номер карти; при `≠ 0` тека карти = `map\map_%d` (🔎 рядок `0x87B7F0`, код `0x792A2F..0x792A45`) |
| 2 | `TotalProvinces` | глобальне ціле `0x877650`, обрізається до `10000` (`0x2710`) |
| 3 | `DistanceCalculationModel` | глобальне ціле `0xDC192C` (дробове число усікається до цілого) |
| 4 | `MapWidth` | `0x877654` (у грі «NOT USED YET») |
| 5 | `MapHeight` | `0x877658` |

Рядок тексту з шляхом поточної теки карти — глобальний буфер `0xDC1930` (`map` або `map\map_N`),
тека активного мода — `0xDC39C0` (порожній рядок, якщо мод не обрано) (🔎 використання в
`0x77FEE0..0x77FF2D`).

Поведінка (🔎):

* Модель вважається «новою» **лише при значенні рівно `1`** — усі перевірки мають вигляд «`== 1`»
  (`0x77FED7`, `0x44A986`, `0x4ED521`, `0x66EBA7`). Будь-яке інше значення працює як стара модель.
  Окремо «режим сумісності» `navaldist.tbl` вмикається лише при значенні рівно `0` (`0x4ED60E`, §6.3).
* `= 1`:
  * під час запуску гри читається (або перераховується з `distances.csv`) `airdist.tbl` (§4–5);
  * функція «відстань між провінціями» бере значення з цієї таблиці (§4.4);
  * морські відстані читаються з `navaldist2.tbl` (§6).
* `≠ 1`:
  * `airdist.tbl` і `distances.csv` **не читаються взагалі** (перехід `0x77FEDA` одразу в кінець);
  * відстань між провінціями — евклідова відстань у пікселях карти між точками `Army XPos/YPos`
    (§4.5);
  * морські відстані — з `navaldist.tbl`.
* Якщо з `airdist.tbl` щось не так (немає файлу і не вдалося перерахувати, не той розмір, не та
  кількість провінцій, помилка читання), гра пише повідомлення «… Switching to old distance
  calculation!» і **сама скидає** `0xDC192C` у `0` (`0x780625`, `0x780663`, `0x78067E`, `0x7806B3`).
  Оскільки морська таблиця читається пізніше, після такого скидання буде використано `navaldist.tbl`.

Значення в постачаних файлах (✅):

| Файл | `MapNumber` | `TotalProvinces` | `DistanceCalculationModel` |
|---|---|---|---|
| `db/misc.txt` (ванільний DH) | 0 | 2608 | **0** |
| `Mods/Darkest Hour Light/db/misc.txt` | 0 | 2608 | 1 |
| `Mods/Darkest Hour Full/db/misc.txt` | 1 | 2770 | 1 |

Отже, ванільна гра без мода використовує стару модель і `map/navaldist.tbl`; `map/airdist.tbl` і
`map/navaldist2.tbl` потрібні для «DH Light»; `map/Map_1/airdist.tbl` і `map/Map_1/navaldist2.tbl` — для
«DH Full». Офіційний підручник (`Modding documentation/DH - Mapediting - Tutorial.rtf`) описує те саме:
при `1` потрібен `distances.csv`, `airdist.tbl` будується при старті, `navaldist2.tbl` — при
завантаженні сценарію (✅ текст підручника).

## 3. `distances.csv`

### 3.1 Структура (✅ обидва файли)

Кодування — однобайтове (Latin-1/CP1252), кінець рядка CRLF, роздільник `;`.

Схема (власна, з місцезаповнювачами замість даних):

```
<total>;Total Provinces;…         ← рядок 1: перше поле = кількість провінцій разом з 0 (2608 / 2770)
<другий заголовок>                ← рядок 2: ігнорується
<lat>;<lon>;PROV0;…               ← рядок 3: провінція 0, ігнорується
<lat>;<lon>;PROV1;<назва>;<регіон> ← провінція 1
…                                 ← провінції 2 … total−1, по одній на рядок, за зростанням ID
EOF;…                             ← останній рядок, без кінцевого LF
```

* Поле 1 — широта в градусах (північ «+»), поле 2 — довгота (схід «+»). Решта полів (`PROVn`,
  назва, регіон) гра не читає.
* ID провінції **не читається** — номер провінції визначається номером рядка: рядок `k + 3`
  (1-базний) = провінція `k` (✅ відтворення таблиці, §5.3).
* Невикористані провінції мають `0;0` — 40 штук у `map/` (ID 223, 224, 291, 1057, 1168, 1169, 1173,
  1400–1403, 1449, 1595, 1623, 1779, 1810, 1811, 1875, 1876, 1884–1897, 1899, 2602–2607) і 10 у
  `map/Map_1/` (✅). Для них у таблиці стоять відстані до точки 0° N 0° E — фактично сміття.
* Мітка `PROVn` у полі 3 **не завжди** відповідає номеру рядка (✅, `map/`): рядок 2446 файлу
  `map/distances.csv` повторно містить `PROV2442` (Gulf of Sidra, 31.036° N 16.152° E), а рядка з
  `PROV2444` немає — далі мітка `PROV2443` (Gulf of Taranto) стоїть у рядку 2447. Кількість рядків від
  цього не змінюється, тож гра (яка дивиться лише на номер рядка) дає провінції 2443 (Gulf of Taranto)
  координати затоки Сидра, а провінції 2444 (North Adriatic Sea) — координати затоки Таранто. Наслідок у
  постачаному `map/airdist.tbl`: 2443 → Таранто (523) = 1055 км, 2444 → Венеція (378) = 909 км, хоча це
  сусідні провінції. Сумісна реалізація має відтворювати цю поведінку (номер рядка, а не `PROVn`).
  У `map/Map_1/distances.csv` усі мітки `PROVn` збігаються з номером рядка (✅).

### 3.2 Як гра читає файл (🔎 `0x77FF7A..0x78009E`)

1. Файл відкривається через загальний CSV-читач (`0x426120`), який спершу пробує
   `<мод>\<тека карти>\distances.csv`, потім `<тека карти>\distances.csv` (🔎 `0x426135..0x426175`).
2. «Кількість рядків» = **кількість байтів LF у файлі** (🔎 `0x426720`). Останній рядок `EOF` без LF
   не враховується.
3. Перше ціле поле файлу (`atoi`) і `кількість LF − 2` мають **обидва** дорівнювати `TotalProvinces`
   (🔎 `0x77FFDE..0x77FFEE`), інакше — помилка `ERROR : Incorrect number of provinces/lines!` і перехід на
   стару модель. (Звідси правило з підручника: файл для 2608 провінцій має 2611 рядків.)
   ✅ `map/`: 2608 і 2610 − 2 = 2608; `map/Map_1/`: 2770 і 2772 − 2 = 2770.
4. Пропускаються 3 рядки (два заголовки й провінція 0) (🔎 `0x77FFF9..0x77FFFE`).
5. Для кожної з `n = total − 1` провінцій (ID 1…n): прочитати поле → `double` (широта), поле →
   `double` (довгота), перейти на наступний рядок (🔎 цикл `0x78006D..0x78009E`).
   Поле читається до `;`, LF або кінця файлу і перетворюється **CRT-функцією `atof`**
   (🔎 `0x426470` → `0x7A7F65`): береться найдовший числовий префікс.

Наслідки для сумісної реалізації (✅ перевірено на ванільному файлі):

* рядки, де між довготою і `PROVn` загублено `;` (довгота «злита» з `PROVn` — рядки 599, 1177, 2024
  файлу `map/distances.csv`, тобто провінції 596, 1174, 2021), читаються правильно, бо `atof` зупиняється
  на першому нечисловому символі (вигаданий приклад: `atof("-12.5PROV7") = -12.5`);
* рядки без поля `PROVn` (11 штук у `map/`: рядки 7, 747, 1983, 2090, 2308, 2368, 2370, 2419, 2512,
  2519, 2579) не заважають — читаються лише перші два поля;
* у `map/Map_1/distances.csv` таких аномалій формату немає.

## 4. `airdist.tbl`

### 4.1 Бінарний формат (✅ + 🔎)

Усе little-endian, без вирівнювання:

| Зміщення | Розмір | Тип | Зміст |
|---|---|---|---|
| 0 | 2 | `u16` | `n` = `TotalProvinces − 1` = найбільший ID провінції |
| 2 | `2·n(n−1)/2` | `u16[n(n−1)/2]` | відстані в **цілих кілометрах**, строго верхній трикутник |

Порядок елементів — рядками: `(1,2), (1,3), …, (1,n), (2,3), …, (2,n), …, (n−1,n)`. Діагоналі та
провінції 0 у файлі немає. ✅ Порядок підтверджено повним повторним обчисленням (§5.3): 0 розбіжностей
на 3 396 921 + 3 832 296 значеннях.

Індекс пари `a < b` (обидва в `1..n`):

```
idx(a, b) = (a − 1)·n − (a − 1)·a / 2 + (b − a − 1)
```

Гра рахує те саме через допоміжний масив «початків рядків» `base[0..n)` (🔎 `0x780535..0x780579`):
`base[0] = 0`, `base[1] = −1`, `base[k] = base[k−1] + (n − k + 1)` для `k ≥ 2`; тоді
`idx(a, b) = base[a] − a + b` для `a < b` (🔎 `0x44A9A7..0x44A9C7`). ✅ Еквівалентність формул
перевірена на 20 000 випадкових парах для обох карт.

Значення (✅):

* мінімум — 0 (співпадні координати: 791 пара в `map/`, 46 у `map/Map_1/`; майже всі — пари
  «невикористаних» провінцій з `0;0`);
* максимум — 20 022 / 20 028 км (теоретична межа `π·R = 20 039,6 км`, `R` — §5.2);
* жодних «сторожових» значень (на кшталт `0xFFFF`) немає; `u16` не переповнюється, бо
  максимум < 65 535;
* нерівність трикутника: на 500 000 випадкових трійках ~100 порушень, усі рівно на 1 км (наслідок
  округлення до цілих км).

Приклади (✅, `map/` → `map/Map_1/` дають ті самі км, хоча ID різні):

| Пара | `map/` (ID) | км | `map/Map_1/` (ID) | км |

| Лондон — Париж | 19 — 56 | 343 | 29 — 55 | 343 |

| Лондон — Токіо | 19 — 1184 | 9571 | 29 — 1552 | 9571 |

### 4.2 Де гра шукає файл (🔎 `0x77FEE0..0x77FF50`)

Лише при `DistanceCalculationModel == 1`:

1. якщо обрано мод — `<мод>\<тека карти>\airdist.tbl` (шаблон `%s\%s\airdist.tbl`, рядок `0x878878`);
2. інакше / якщо не знайдено — `<тека карти>\airdist.tbl` (шаблон `%s\airdist.tbl`, рядок `0x878868`);
3. якщо не знайдено ні там, ні там — перерахунок із `distances.csv` (§5), запис файлу і повторний
   пошук за тими ж правилами (🔎 `0x78030E..0x780376`).

### 4.3 Читання (🔎 `0x7803E8..0x78061E`)

1. Файл відкривається в режимі `"rb"` загальним відкривачем (`0x426D70`; він теж спершу пробує
   `<мод>\<шлях>`).
2. Читаються 2 байти `n`. Вимога: `n + 1 == TotalProvinces`, інакше
   `ERROR in provinces (expected: %d, found: %d)!` → стара модель (`0x780469..0x780476`).
3. Вимога до розміру файлу: `розмір == 2 + 2·n(n−1)/2`, інакше `ERROR in file size!` → стара модель
   (`0x78047C..0x780490`).
4. Читаються `n(n−1)/2` значень `u16`; невдача читання → `ERROR reading file!` → стара модель.
5. Кожне значення перетворюється на `f32` як `км × 0.01f` (константа `0x3C23D70A` за `0x7E543C`) і
   кладеться в глобальний масив `f32` (вказівник на дані — `0xD77ADE`), поряд — масив `base`
   (вказівник `0xD77AEE`) (🔎 `0x7804EB..0x780579`).
6. У журнал пишеться `Done! (%d provinces read in %d ms)`.

### 4.4 Функція «відстань між провінціями», нова модель (🔎 `0x44A980`)

Сигнатура: два ID провінцій → `f32` (через `st(0)`), одиниця 100 км. Прямих викликів — 96
(🔎 пошук інструкцій `call 0x44A980`).

* якщо `a == b`, `a == 0` або `b == 0` → `0.0`;
* інакше → `table[base[min] − min + max]`.
* Перевірки меж (`a, b ≤ n`) **немає** — ID поза таблицею дадуть читання чужої пам'яті (🔎).

### 4.5 Стара модель (`DistanceCalculationModel ≠ 1`) (🔎 `0x44A9CB..0x44AA54`)

* якщо `a == b` → `0.0` (на відміну від нової моделі, провінція 0 тут не виняток);
* інакше беруться цілі координати `Army XPos`/`Army YPos` обох провінцій (колонки 23/24
  `Province.csv`; поля структури провінції `+0x3FA`/`+0x3FE`, заповнення — 🔎 `0x4EB34A..0x4EB38A`) у
  пікселях рівня 1 (карта 29 952 × 11 520);
* `dx = xa − xb`, `dy = ya − yb`; якщо `|dx| > 15000` (`0x3A80`), то `dx = 29952 − |dx|`
  (`0x7500`) — горизонтальне замикання карти;
* результат = `sqrt(dx² + dy²) · 0.01f · 0.66f` (константи `0x7E543C`, `0x7E5438` = `0x3F28F5C3`),
  тобто **1 піксель = 0.66 км**. Добуток рахується в x87 з подвійною точністю і обрізається до `f32`
  лише при збереженні.

## 5. Перерахунок `airdist.tbl` з `distances.csv`

### 5.1 Послідовність (🔎 `0x77FF56..0x7802A4`)

1. Повідомлення `airdist.tbl not found! Recalculating from %s\distances.csv...` (рядок `0x878828`).
2. Читання `distances.csv` за §3.2 (масиви `lat[0..n)`, `lon[0..n)` типу `double`; індекс `i` ↔
   провінція `i + 1`).
3. Виділяється масив `u16` на `n(n−1)/2` елементів.
4. Подвійний цикл: зовнішній `i = 0 … n−1`, внутрішній `j = i+1 … n−1`, лінійний лічильник
   результату зростає на 1 — це й дає порядок «рядками верхнього трикутника».
5. Для кожної пари (усе в `double`, x87):
   * `φ1 = lat[i]·K`, `φ2 = lat[j]·K`, `Δλ = lon[j]·K − lon[i]·K`, де `K` — §5.2;
   * `c = cos(Δλ)·cos(φ1)·cos(φ2) + sin(φ1)·sin(φ2)` (сферичний закон косинусів);
   * `d = acos(c) · R` (`acos` — CRT, `0x7A5B20`);
   * `d` зберігається як `f32` (обрізання до одинарної точності), знову завантажується і
     перетворюється на ціле інструкцією `fistp` — **округлення до найближчого, половини — до
     парного** (режим FPU за замовчуванням);
   * у масив записуються молодші 16 біт цього цілого.
6. Запис (🔎 `0x780197..0x780200`): шлях `<тека карти>\airdist.tbl`, режим `"wb"` (рядок `0x82EF98`)
   через відкривач `0x426D70`, який спершу пробує `<мод>\<тека карти>\airdist.tbl` — тобто якщо в моді
   існує тека карти, файл ляже туди ❓ (висновок з коду відкривача, не перевірявся запуском).
   Пишуться 2 байти `n` (молодша половина 32-бітного лічильника), потім `2·n(n−1)/2` байтів масиву.
7. Журнал: `Done! (%d calculations for %d provinces in %d ms)`; за прапорцем розширеного журналу
   (`0xDC4B1E`) також перша й остання пара координат (`Lat 0 = …`, `Lat %d = …`).
8. Потім файл шукається й читається звичайним шляхом (§4.2–4.3).

## 6. `navaldist.tbl` і `navaldist2.tbl`

### 6.1 Бінарний формат (✅ + 🔎)

| Зміщення | Розмір | Тип | Зміст |
|---|---|---|---|
| 0 | 4 | `u32` | `N` — кількість «морських вузлів» |
| 4 | `4·N·N` | `f32[N][N]` | повна матриця, рядками; `M[i][j]` за зміщенням `4 + 4·(i·N + j)` |

* Одиниця — **100 км** (наприклад, `5.28` = 528 км).
* Діагональ — `0.0` (✅ у всіх трьох файлах).
* Матриця **симетрична** побітово (✅ 0 несиметричних пар у всіх трьох файлах) — гра записує обидві
  половини однаковими (§7.1).
* `0.0` поза діагоналлю означає «шлях не знайдено» **або** «шлях нульової довжини». У постачаних
  файлах недосяжних пар немає; у `map/navaldist2.tbl` є 8 нулів (4 пари) — це сусідні провінції з
  однаковими координатами в `distances.csv` (`airdist = 0`): 1740–2257, 1742–2258, 1753–1980,
  1926–2209 (✅). У `map/navaldist.tbl` і `map/Map_1/navaldist2.tbl` нулів поза діагоналлю немає.
* Інших сторожових значень немає; від'ємних значень немає (✅).
* Розмір файлу = `4 + 4·N²` (✅: 1461² = 2 134 521, 1380² = 1 904 400).

### 6.2 Морський індекс (номер рядка/стовпця)

Рядок/стовпець матриці — не ID провінції, а «морський індекс», який гра присвоює під час читання
`Province.csv` (🔎 `0x4EB574..0x4EB6C5`, лічильник — глобальне `0xABF100`, поле провінції `+0x16A`):

1. для кожного рядка `Province.csv` у порядку файлу (ID зростають; рядки з `ID ≥ TotalProvinces`
   пропускаються, 🔎 `0x4EA654..0x4EA66A`) індекс спершу `−1`;
2. якщо `Port Seazone` (колонка 14) `> 0` — провінція отримує наступний індекс;
3. окремо: якщо номер області (колонка 3 `Area`) `> 0x1C5` (453) — провінція отримує наступний індекс
   (🔎 `0x4EB6A4..0x4EB6C5`).

Номери областей — з вбудованої таблиці 606 назв (`0x25E` вказівників за `0x83F7EC`; пошук без
урахування регістру, `_stricmp` за `0x7A8430`, невідома назва → 0; 🔎 `0x4C797A`). Індекс `0x1C5` —
`Lake`, усі наступні (`Adriatic Sea`, `Aegean Sea`, `Black Sea`, …, `Caspian Sea`) — моря; `0` — `-`.

Пункти 2 і 3 у даних не перетинаються, тож кожна провінція має щонайбільше один індекс (✅).
Перевірка (✅): `map/` — 786 + 675 = 1461 = `N`; `map/Map_1/` (свій `Province.csv` з
`map\map_1\province.csv`, рядок `0x87B7FC`) — 812 + 568 = 1380 = `N`. Відповідність індекс ↔ ID
додатково підтверджена §8 (значення «прибережна провінція → її морська зона» збігаються точно).

Перші індекси `map/`: 0 ↔ ID 1, 1 ↔ 2, 2 ↔ 3, …; останній (1460) ↔ ID 2601.

### 6.3 Завантаження (🔎 `0x4ED4E0`, викликається з `0x4E0626` після завантаження провінцій)

1. Ім'я: `<тека карти>\navaldist2.tbl` (рядок `0x848E98`), якщо модель `== 1`, інакше
   `<тека карти>\navaldist.tbl` (`0x848EAC`) (🔎 `0x4ED505..0x4ED53A`).
2. Відкриття `"rb"` відкривачем `0x426D70` (спершу `<мод>\…`, потім основна тека). Не відкрилося →
   одразу перерахунок (§7).
3. Якщо в моді існує копія, ім'я в буфері замінюється на мод-шлях (🔎 `0x4ED570..0x4ED5DD`) — воно
   далі йде в журнал і як шлях запису після перерахунку.
4. Статичний прапорець `0xABF104`: якщо таблиця вже була прочитана в цьому процесі — нічого не
   робиться (🔎 `0x4ED5F8..0x4ED5FF`).
5. Читається `u32 N`.
6. **Режим сумісності** (лише при моделі `== 0`): `N' = (int) sqrt((розмір − 4) / 4)`; якщо `N' ≠ N`,
   пишеться `%s is read in compatibility mode! (Read %d, Valid: %d)` і для читання береться `N'`
   (🔎 `0x4ED605..0x4ED64B`). Тобто старі файли без коректного заголовка все одно читаються.
7. Виділяються `N·N` значень `f32` (вектор `0xABC4D8`, дані — `0xABC4DC`) і таблиця початків рядків
   `i·N` (вектор `0xABC8F0`, дані — `0xABC8F4`); читаються `N·N` значень `f32` (результат читання не
   перевіряється) (🔎 `0x4ED65D..0x4ED7E3`).
8. Прапорець «прочитано» = 1; журнал `Done! (%d naval provinces, Read distances = %d)`.
9. Якщо `N` із **заголовка** не дорівнює поточній кількості морських вузлів (`0xABF100`) — перерахунок
   (🔎 `0x4ED83A..0x4ED845`). Інших перевірок свіжості немає (зміна координат чи суміжності без зміни
   кількості вузлів таблицю **не** оновить). Підручник прямо попереджає, що зміна морських зон у
   `province.csv` спричиняє перебудову.

### 6.4 Доступ (🔎 `0x4ED480`)

Метод провінції «морська відстань до провінції з ID `q`»: якщо в цієї провінції або в `q` морський
індекс `< 0` → `0.0`; інакше `M[idx(this)·N + idx(q)]`. Викликається з ~37 місць (🔎).

## 7. Перерахунок морських таблиць

### 7.1 Схема (🔎 `0x4ED84B..0x4EDCBC`)

1. Журнал: `Recalculating %s (%d Naval connections of %d Provinces)` (рядок `0x848D8C`).
2. Створюється матриця `N×N` (N = поточна кількість вузлів), заповнена нулями.
3. Створюється об'єкт пошуку шляху з таблицею віртуальних методів `0x7E8140` («морський» варіант).
4. Подвійний цикл по **всіх ID провінцій** `0 … TotalProvinces−1` (зовнішній `p`, внутрішній `q`),
   пропускаючи провінції без морського індексу. Нехай `a = idx(p)`, `b = idx(q)`:
   * якщо `M[a][b] ≠ 0.0` — пара вже заповнена, пропустити;
   * інакше шукається шлях `p → q` (загальний A*, `0x431220`, без юніта);
   * сума `acc` (`f32`, від 0) іде по вузлах шляху від першого після `p` до `q`: на кожному кроці
     `acc += Відстань(попередній, поточний)` (функція §4.4/§4.5 — залежить від моделі!) і **одразу**
     записується `M[a][idx(вузол)] = M[idx(вузол)][a] = acc`;
   * після циклу `M[a][b] = M[b][a] = acc` (якщо шляху немає — лишається 0).
   Діагональ лишається 0, бо пошук `p → p` відхиляється перевіркою старту (`0x4325F0`).
5. Запис: той самий шлях (§6.3 п. 1/3), режим `"wb"`: `u32 N`, потім `N·N` значень `f32`
   (🔎 `0x4EDC59..0x4EDCB7`).
6. За прапорцем `0xDC4B1F` — докладний журнал по кожній парі (`%d(%d) dist. to:` / ` %.0fkm |`).

Наслідки:

* Записане значення — **геометрична** довжина маршруту (сума відстаней кроків), а не «вартість», за
  якою маршрут обирався (§7.2).
* Записи для проміжних вузлів (`M[a][x]`) перезаписуються без перевірки, тож значення пари може бути
  «префіксом» маршруту до іншої, дальшої цілі ❓ (так пояснюються 2 аномалії в §8).

### 7.2 Пошук шляху (🔎, морські віртуальні методи таблиці `0x7E8140`)

Загальний A* (`0x431220`): двійкова купа `0x893720`; у структурі провінції — батько `+0x474`, `g`
`+0x478`, `f` `+0x47C`, ознака «у відкритому списку» `+0x480`; сусіди — масив 12-байтних записів
суміжності (`+0x290` кількість, `+0x298` вказівник; запис: ID сусіда `+0`, тип `+4`, «через»
провінцію `+8` — той самий 12-байтний запис, що в `adjacent.tbl`). Вузол, знайдений дешевшим шляхом,
знову додається до купи.

Морська специфіка (для `юніт = NULL`, як при перерахунку):

| Слот | Адреса | Що робить |
|---|---|---|
| `+0x34` старт | `0x4325F0` | ціль не заблокована (`+0x180`), ID різні й ненульові; ціль — вода (тип рельєфу 8 «sea/ocean» або 9 «lake/river», поле `+0x254`, 🔎 `0x4EAA45..0x4EAB9C`) або має `Port Seazone ≠ 0` |
| `+0x38` ціль | `0x431880` | ID поточного вузла == ID цілі |
| `+0x30` хід | `0x432640` | загальна перевірка `0x4318D0` (не назад до батька, сусід не 0 і не заблокований `+0x180`; усі інші її перевірки — тип суміжності 4, провінція «через», власники баз — виконуються лише коли є юніт, 🔎 `0x431912..0x431B9E`); **хоча б один** із двох вузлів — вода; сусід — вода **або** має `Port Seazone ≠ 0`; область сусіда ≠ `Lake` (`0x1C5`) |

| `+0x40` евристика | `0x4316E0` | `Відстань(вузол, ціль)`; якщо вузол не вода — × `0.012f` (`0x83B874`) |

`terrain types.csv` шукається як `<тека карти>\terrain types.csv` загальним CSV-читачем, тобто з

Hills 1.2, Jungle 2.0, Urban 1.1, Ocean 1.0, River 1.0, Terra incognito 0, Unknown 0.

## 8. Чим `navaldist.tbl` відрізняється від `navaldist2.tbl`

Формат, набір вузлів і їх порядок — **однакові** (✅ `N = 1461` в обох файлах `map/`). Відрізняється
лише функція відстані одного кроку маршруту (і, отже, вибір маршруту):

| | `navaldist.tbl` | `navaldist2.tbl` |

## 10. Рекомендації для реалізації (Rust)

* `AirDist { n: u16, km: Vec<u16> }`; доступ `km(a, b)` за формулою §4.1, `0` для `a == b`/`a == 0`/`b == 0`;
  для ігрової логіки повертати `f32` = `km as f32 * 0.01` (одиниця 100 км), як гра.
* `NavalDist { n: u32, m: Vec<f32> }` + `naval_index: Vec<i32>` (на провінцію, `-1` якщо немає),
  побудований за §6.2 при читанні `Province.csv`. Доступ: `0.0`, якщо хоч один індекс `< 0`.
* Обирати файл за `DistanceCalculationModel == 1` (не `!= 0`). Реалізувати відкат на стару модель при
  будь-якій помилці `airdist.tbl` (§2).
* Генератор `airdist.tbl`: `f64`, сферичний закон косинусів, константи §5.2 точно (бітово), `as f32`,
  округлення half-to-even (`f32::round_ties_even`), далі `as i32 as u16` (молодші 16 біт; прямий
  `f32 as u16` у Rust насичує, а не обрізає). Порядок записів — §4.1.
  `distances.csv` розбирати як гра: поля до `;`/LF, `atof`-префікс, рядок `k+3` ↔ провінція `k`,
  перевірка «LF − 2 == total == TotalProvinces».
* Генератор `navaldist*.tbl`: для сумісності з постачаними даними достатньо мінімальної за вартістю
  моделі §7.2 (99–100 % пар); для точного відтворення потрібен розбір A* і суміжності (§11).

## 11. Відкриті питання

1. ❓ Чому ~1.3 % пар ванільного `navaldist2.tbl` (0.5 % у `navaldist.tbl`) не збігаються з
   мінімальною за вартістю моделлю: особливості A* (`0x431220`, порівняння в купі `0x893720`), перезапис
   префіксів (§7.1) чи застарілі дані.
2. ❓ Чи впливають на постачані таблиці ребра `adj-defs.csv` типу `impassable` (з `юніт = NULL` гра їх не
   блокує, 🔎 `0x431912..0x43192E`) — на збіг моделі їх наявність не вплинула.
3. ❓ Що повертає `0x4D7620` (точка за замовчуванням для координат `0;0` у `Province.csv`) — потрібно для
   старої метрики провінцій без `Army XPos/YPos`.
4. ❓ Запис перерахованого `airdist.tbl` при активному моді (відкривач `0x426D70` спершу пробує
   `<мод>\…` і з режимом `"wb"`) — перевірити запуском.
5. ❓ Чи дає Rust/libm на Windows/macOS ті самі цілі км, що glibc (на glibc — 0 розбіжностей).
