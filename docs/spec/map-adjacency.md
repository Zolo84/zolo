# Специфікація: суміжність провінцій (`adjacent.tbl`, `adj-defs.csv`)

> **Джерело.** Дизасемблювання `Darkest Hour.exe` (DH 1.05.1, GOG; 32-біт PE, image base `0x400000`)
> і звірка з файлами цієї ж інсталяції. Код гри **не копіювався**: поведінку описано власними словами,
> псевдокод — власний. Дослівно наведено лише ідентифікатори: імена файлів, рядки формату, константи,
> зміщення, розміри.
>
> **Адреси.** Усі адреси — віртуальні (VA) у `Darkest Hour.exe`. Адреса функції — її перша інструкція;
> адреса факту — інструкція, де це видно. Рядки лежать у секції `.data` (не `.rdata`).
>
> **Позначки.** ✅ — перевірено на реальних даних інсталяції; 🔎 — прочитано з коду exe;
> ❓ — гіпотеза/інтерпретація. Комбінація «🔎✅» — прочитано в коді й підтверджено даними.
>
> **Термінологія.** N — кількість провінцій («Total provinces» з `db/misc.txt`), ID провінцій `0..N-1`.
> «Запис суміжності» — 12-байтна структура `{to, type, through}`.

## 0. Коротко

* `adjacent.tbl` — **CSR-подібний масив списків сусідів**: таблиця з `N+1` зміщень `u32`, далі суцільний
  масив 12-байтних записів. Заголовка, сигнатури, версії немає. N у файлі не зберігається — гра бере його з
  `db/misc.txt` (секція `map`, «Total provinces»). 🔎✅
* Запис: `i32 to` (ID сусіда), `i32 type` (тип з'єднання 0..4), `i32 through` (ID провінції «через яку»).
  У постачених файлах `type` = 0 у **всіх** записах, `through` = `0xCDCDCDCD` (сміття неініціалізованої
  пам'яті) у **всіх** записах. Фактичні типи з'єднань (річка, протока, канал, непрохідність) задає лише
  `adj-defs.csv`, який гра накладає поверх таблиці під час завантаження. 🔎✅
* Таблиця симетрична у `map/` (усі 7430 зв'язків у обидва боки); у `map/Map_1/` є **один** односторонній
  зв'язок `2200 → 1050`. Списки відсортовані за зростанням ID, без дублікатів і петель. ✅
* Якщо файлу немає, гра будує його сама з растрової карти ID `map\id.tbl` (якої в GOG-інсталяції немає). 🔎✅
* `adjacentenemy` / `adjacency` — це **не** формат файлу, а ключові слова AI-файлів `ai/*.ai`. 🔎✅

## 2. Формат `adjacent.tbl`

Порядок байтів — little-endian. Вирівнювання — 4 байти, без заповнювачів.

```
зміщення 0            : u32 offs[N + 1]          // індекси записів, НЕ байтові зміщення
зміщення (N+1)*4      : Rec recs[offs[N]]        // 12 байт кожен
кінець файлу          = (N+1)*4 + offs[N]*12

Rec (12 байт):
  +0  i32 to        // ID сусідньої провінції
  +4  i32 type      // тип з'єднання (див. §2.2)
  +8  i32 through   // ID провінції-«посередника» для type 2/3 (і 1, див. §6.2)
```

* Список сусідів провінції `p` — це `recs[offs[p] .. offs[p+1])` (півінтервал). 🔎 (`0x4E09EC..0x4E0A58`) ✅
* Таблиця читається двома викликами: `N+1` елементів по 4 байти, потім `offs[N]` елементів по 12 байт
  (`0x4E096E`, `0x4E09B4`; читач `0x427220` робить один `fread` з розміром елемента 1 і кількістю
  `розмір × кількість`, `0x427243`). Довжина файлу ніде не перевіряється. При короткому читанні рядок
  « Error reading file %s!» (`0x83A3F0`) лише форматується в буфер об'єкта файлу (`0x42725C`) і передається
  в `0x405AD0`, яка в цій збірці порожня (`ret`, див. §7.4), — тобто **нікуди не виводиться**; ставляться
  прапорець об'єкта `+0x13C` і глобальний прапорець помилки `0x88F1DA` (`0x42726D`, `0x427274`). 🔎
  (уточнено під час перевірки: раніше тут стверджувалося, що повідомлення виводиться)

### 2.3 Поле `through` і значення `0xCDCDCDCD`

* Будівник це поле **ніколи не записує** — воно лишається з неініціалізованого буфера (§7). 🔎
* `0xCDCDCDCD` — шаблон, яким налагоджувальна (debug) CRT MSVC заповнює щойно виділену купу. Отже, постачені
  файли записала debug-збірка гри або зовнішнього інструмента карти. ❓
* Для гри це безпечно: усі місця, що використовують `through`, спершу перевіряють `0 < through < N` як знакове
  ціле (`0x43193D..0x43194E`, `0x431A0C..0x431A1D`), а `0xCDCDCDCD` як `i32` = −842 150 451. 🔎
  Рекомендація для реалізації: трактувати `through ≤ 0 || through ≥ N` як «немає».

## 3. Алгоритм декодування (довідковий)

```text
fn decode(bytes, n_opt) -> Vec<Vec<Rec>>:
    // 1. N: з misc.txt; якщо невідоме — знайти N, для якого
    //    (N+1)*4 + u32_at(4*N)*12 == len(bytes), offs[0]==0, offs неспадні.
    //    На обох постачених файлах розв'язок єдиний (2608 і 2770).
    n    = n_opt.unwrap_or(infer(bytes))
    offs = [u32_le(bytes, 4*i) for i in 0..=n]
    base = 4*(n+1)
    assert base + 12*offs[n] == len(bytes)
    rec(k) = (i32_le(base+12k), i32_le(base+12k+4), i32_le(base+12k+8))

    adj[0] = []                                   // гра ігнорує список провінції 0
    for p in 1..n:
        adj[p] = [rec(k) for k in offs[p]..offs[p+1]]
    // through: якщо !(0 < through < n) — вважати відсутнім
    return adj
```

Потім, щоб отримати граф, яким користується гра, треба накласти `adj-defs.csv` (§5).

## 4. Як гра завантажує таблицю

### 4.1 Порядок викликів

1. **Ініціалізація карти** (функція `0x4D71B0`): перевірка існування `adjacent.tbl` (функція `0x427770`,
   виклик `0x4D7334`). Якщо файлу немає — у `savedebug.txt` пишеться «`\n%s not found! Rebuilding... `»
   (`0x8477FC`), викликається будівник `0x4EB950(provinces, N)` (§7), потім «Done!». Далі — завантаження
   `0x4E0910(path)` (`0x4D7377`). 🔎
2. **Завантаження провінцій** (функція `0x4E03B0`, викликається з `0x42EEE5` і `0x42F3F2`): після розбору
   `province.csv` таблиця завантажується **ще раз** (`0x4E0619`), одразу після цього накладається
   `adj-defs.csv` (`0x4E3B70`, виклик `0x4E0621`), далі `0x4ED4E0` (читає `navaldist.tbl`/`navaldist2.tbl`,
   поза цією специфікацією), перевірка «зв'язків із провінцією 0» і, за потреби, звіт (§8). 🔎

Наслідок: правки з `adj-defs.csv` діють від повного перезавантаження таблиці, тобто не накопичуються. 🔎

### 4.2 Що робить завантажувач `0x4E0910`

* Виділяє `(N+1)*4` байт під `offs`, читає їх, потім виділяє і читає `offs[N]` записів. 🔎
* Провінції 0 ставить обидва лічильники в 0 (`0x4E09C3`, `0x4E09CF`). 🔎
* Для `p = 1..N-1` (`0x4E09EC..0x4E0AEB`): 🔎
  * `regular_count` (поле провінції `+0x290`) = кількість **початкових** записів списку, чий сусід не має рельєфу
    River (код рельєфу 9); підрахунок зупиняється на першому сусіді з рельєфом 9;
  * `total_count` (`+0x294`) = `offs[p+1] - offs[p]`;
  * старий масив (`+0x298`) звільняється, виділяється новий на `total_count` записів, кожен запис
    копіюється методом `0x4EB6F0` (див. нижче).
* Симетрію гра не відновлює: кожен список копіюється незалежно. 🔎 Тому односторонній запис у `Map_1`
  (`2200 → 1050`) у грі так і лишається одностороннім. ✅🔎

Рельєф 9 («River» у `map/Terrain types.csv`: `0 Plains … 8 Ocean, 9 River, 10 Terra incognito, 11 Unknown`)
у DH 1.05 не використовується жодною провінцією ні в `db/Province.csv`, ні в `map/Map_1/Province.csv`,
тому для постачених даних `regular_count == total_count` для всіх провінцій. ✅
Майже весь код гри (перевірка суміжності `0x4E76F0`, лічильник `0x513D50`, звіт) бачить лише «регулярну»
частину `[0, regular_count)`. 🔎

### 4.3 Пов'язані поля структури провінції

Масив провінцій — за вказівником `0xAB2774`, розмір структури `0x4B2` (1202) байти. Використані тут поля:

| Зміщення | Зміст | Де видно |
|---|---|---|
| `+0x254` | код рельєфу (0..11, 8 = Ocean, 9 = River) | `0x4E0A14`, `0x4EB71B`, `0x4E8CE0` (IsLand: рельєф ∉ {8, 9}) 🔎 |
| `+0x288` | індекс області (Area) у таблиці назв областей | запис `0x4EA712`; таблиця вказівників `0x83F7EC`, 606 (`0x25E`) назв, пошук `0x4C797A` 🔎 |
| `+0x290` | `regular_count` | `0x4E0A41` 🔎 |
| `+0x294` | `total_count` | `0x4E0A58` 🔎 |
| `+0x298` | вказівник на масив 12-байтних записів | `0x4E0AA2` 🔎 |
| `+0x3DC` | Port Seazone з `Province.csv` | `0x5266E0` 🔎 |
| `+0x46F` | прапорець: є з'єднання з `type` 1 або 2 | `0x4EB79B`, `0x4EB7AD` 🔎; зміст ❓ |
| `+0x470` | прапорець: суходіл, що межує з Ocean, область якого ≠ `Lake` | `0x4EB75E` 🔎; «прибережна» ❓ |
| `+0x471` | прапорець: морська провінція межує з суходолом (рельєф < 8) | `0x4EB78E` 🔎 |

Таблиця областей: індекс 0 = `-`, `0x1C5` (453) = `Lake`, останній (605) = `Caspian Sea`; індекси, більші
за `0x1C5`, — морські області (`0x513D10` повертає «область > 0x1C5»). Невідома назва області також дає 0. 🔎✅

Метод `0x4EB6F0` (запис одного елемента) копіює 12 байт і ставить прапорці `+0x46F/+0x470/+0x471`.
Зверніть увагу: прапорець `+0x46F` ставиться лише тут, тобто для записів, які мали `type` 1/2 вже у файлі,
або для **нових** з'єднань, доданих з `adj-defs.csv`; зміна типу існуючого з'єднання (§5.3) цей метод не
викликає. 🔎 Наслідки для гри ❓.

## 5. `adj-defs.csv`

### 5.1 Колонки

Заголовок (в обох файлах): `From;To;Type;Through;Comment`. Перший рядок пропускається (`0x4E3BAC`). 🔎✅

| # | Назва | Як читається | Значення |
|---|---|---|---|
| 1 | `From` | ціле (`atoi`) | ID першої провінції; `< 0` — кінець файлу; `0` — див. нижче |
| 2 | `To` | ціле | ID другої провінції |
| 3 | `Type` | рядок, без обрізання пробілів, порівняння без урахування регістру (`_stricmp`, `0x7A8430`) | `river`, `sea`, `canal`, `impassable`, `normal`, `remove` |
| 4 | `Through` | ціле | ID провінції-посередника (морська зона для `sea`, провінція каналу для `canal`), інакше 0 |
| 5 | `Comment` | **не читається** | після `Through` решта рядка пропускається (`0x4E4024`) |

Читач поля (`0x426380` для чисел, `0x4265C0` для рядків) збирає символи до `;` або `\n`; число — через
`atoi` (`0x7A783C`), тож нечислове поле дає 0. 🔎

### 5.2 Алгоритм розбору (власний опис функції `0x4E3B70`)

```text
skip_line()                                         // заголовок
loop:
    from = read_int()
    if from < 0: break                              // термінатор "-1;-1;;;"
    if from == 0 or area(from) == 0: continue       // !!! без skip_line: наступне ПОЛЕ стане "From"
    to = read_int()
    if area(to) == 0: continue                      // так само без skip_line
    t  = read_str()
    match lower(t):
        "river"=>1, "sea"=>2, "canal"=>3, "impassable"=>4, "normal"=>0,
        "remove"=> remove = true,
        _ => 0  (+ повідомлення про помилку, лише в режимі налагодження)
    through = read_int()
    if remove:      видалити to зі списку from і from зі списку to (якщо to є в регулярній частині from)
    elif to вже є в регулярній частині from:
                    у всіх входженнях to у регулярній частині from і from у регулярній частині to
                    переписати type і through
    else:           додати {to, type, through} у from і {from, type, through} у to
    skip_line()
```

* Термінатор: рядок з від'ємним `From`. Обидва файли закінчуються `-1;-1;;;` (у `map/` перед ним ще
  порожній рядок, який дає `From = 0` і пропускається). ✅ Без термінатора цикл не завершиться: на кінці
  файлу читач не оновлює значення, а `From` перед кожним читанням скидається в 0 (`0x4E3BC7`), що веде до
  гілки «0 → продовжити». 🔎 (висновок про нескінченний цикл ❓, не перевірявся запуском)
* Рядки-коментарі (`####...;;;;`, `# China Border;;;;`) обробляються не як коментарі, а тим, що кожне їхнє поле
  дає `atoi = 0` і тихо пропускається по одному. 🔎✅ Коментар, що починається з цифри, зламав би розбір. ❓
* Перевірка `area(...) == 0` — це індекс області з `Province.csv` (поле `+0x288`): провінція з `Area = -` або з
  назвою, якої немає в таблиці exe, не може брати участь у `adj-defs.csv`; гірше — пропуск відбувається без
  переходу на новий рядок, тож решта полів рядка читається як нові `From`/`To`. 🔎 Жоден справжній рядок
  даних у постачених файлах під це правило не потрапляє (усі назви областей з обох `Province.csv` є в таблиці
  exe). Але в `map/adj-defs.csv` є два **закоментовані** рядки даних — рядок 535 `#1305;1304;River;0;Mekong`
  і рядок 634 `#1306;1327;River;0;Red`. Вони пропускаються саме через цю гілку: `#1305` → `From = 0`
  (пропуск), далі `1304` стає `From`, `River` стає `To` = 0, `area(0) == 0` → пропуск, `0` і `Mekong` дають
  `From = 0`. Результат такий самий, як від справжнього коментаря, але лише тому, що область провінції 0 — `-`. ✅🔎
  (виправлено під час перевірки: раніше стверджувалося, що жоден рядок не потрапляє під правило)
* Значення `To` і `Through` перед кожним рядком **не** скидаються в 0 (обнуляються лише раз перед циклом,
  `0x4E3BB1`, `0x4E3BB5`; на кожній ітерації скидаються тільки `From` `0x4E3BC7` і прапорець `remove`
  `0x4E3BC2`). Це важить лише на кінці файлу, де читач значення не оновлює. 🔎
* Читач поля вважає `\n` роздільником. Рядок лише з 4 полями (без `Comment` і без завершального `;`)
  змусив би `Through` «з'їсти» кінець рядка, а наступний `skip_line` — пропустити **наступний** рядок даних
  (`0x426380`, `0x426330`). 🔎 У постачених файлах усі рядки мають рівно 5 полів (крім порожнього рядка перед
  термінатором у `map/`). ✅
* Діапазон `From`/`To` не перевіряється (лише `From < 0`); ID ≥ N — вихід за межі масиву. 🔎
* Повідомлення про невідомий тип (`0x848118`: «ERROR : Invalid province connection type (%s) defined in '%s'
  for provinces '%s' [%d] and '%s' [%d]! 'Normal' will be used instead.») пишеться у `savedebug.txt` лише при
  увімкненому налагодженні (`0xDC4B1E`); тоді ж збільшується лічильник помилок `0xDC4B20`
  (`0x4E3D48..0x4E3D51`). Тип за замовчуванням — 0 у будь-якому разі. 🔎
* Нове з'єднання вставляється методом `0x4EB7C0` у позицію `regular_count` (кінець регулярної частини, перед
  River-сусідами), `regular_count` і `total_count` збільшуються на 1; далі — `0x4EB6F0` (прапорці) і лічильник
  `+0x136` провінції (зміст ❓). 🔎 Тобто нові сусіди йдуть **після** сусідів із `.tbl`, а не за порядком ID. 🔎✅
* `remove` шукає `to` тільки в регулярній частині `from`; якщо знайдено — фізично прибирає обидва напрямки,
  зменшуючи лічильники. 🔎 Нові масиви збираються копіюванням лише **регулярної** частини старого
  (`0x4E3E47..0x4E3E8D`, `0x4E3F41..0x4E3F87`), тож «хвіст» River-сусідів при `remove` втратився б; на
  постачених даних хвоста немає (§4.2). 🔎 У постачених файлах `remove` і `normal` не використовуються. ✅
* Повторне визначення тієї ж пари просто ще раз переписує `type/through` (останнє виграє). 🔎 У `map/`
  повторюються **17** пар: 15 — з тим самим типом і `Through` (напр. 1296–1297, 1299–1302 «Irrawaddy»,
  1276–1440 — 5 разів), а **2 — з різними значеннями**: 293 Odense – 294 Copenhagen (рядок 1117 `River`, потім
  рядок 1160 `Sea` через 2476 → у грі `sea`/2476) і 660 Kauai – 661 Niihau (рядок 1142 `Sea` через 1931, потім
  рядок 1144 `Sea` через 1944 → у грі `through` = 1944 French Frigate Shoals). У `Map_1` повторів немає. ✅
  (уточнено під час перевірки: раніше було лише «повтори з однаковим типом»)

## 6. Як типи використовуються в грі (🔎, інтерпретація ❓ де вказано)

### 6.1 Непрохідність (type 4)

* `0x4E7720` — «чи можна пройти в провінцію X»: X є в регулярній частині і `type != 4`. 🔎
* Перевірка ребра шляху `0x4318D0` (викликається з 13 місць: 12 у `0x431C2C..0x432A7D` і ще `0x51DF28`): якщо рухомий об'єкт
  проходить віртуальну перевірку `+0x28` (найімовірніше, «сухопутний підрозділ» ❓) і `type == 4` — ребро
  заборонене. 🔎
* Численні цикли по сусідах пропускають записи з `type == 4` (напр. `0x4E89BD`, `0x4E8A0C`, `0x4EA30C`,
  `0x4EA390`, `0x681A59`, `0x68B409`). 🔎 У переглянутих `0x4E89BD`, `0x4EA30C`, `0x4EA390` це перевірки
  власника/контролера сусідньої провінції. ❓ Офіційний опис
  Invasion AI теж каже, що враховуються лише «enemy neighboring provinces that are not impassable». ✅ (документація)

### 6.2 Протока, річка з посередником, канал (type 1/2/3 і `through`)

У `0x4318D0`, якщо `0 < through < N`: 🔎
* `type` 1 або 2 → перебираються підрозділи в провінції `through`; певні ворожі підрозділи там
  (умова через `0x44B240`, найімовірніше «у війні з» ❓, і прапорець підрозділу `+0x17B`) забороняють
  ребро. Збігається з текстом `ADJ_SEA` («Hostile fleets in %s will block movement»). Тобто й `River` з
  ненульовим `through` (Суец, `map/`) блокується флотом у зоні 2453. 🔎✅
* `type` 3 → якщо контролер провінції `through` (поле `+0x3D8` ❓) ворожий — ребро заборонене; також
  перевіряються ворожі підрозділи в `through`. Збігається з `ADJ_CANAL`. 🔎

### 6.3 Бій

* `0x4C2DCB..0x4C2EE4`: якщо атака йде по з'єднанню з `type == 1`, застосовується модифікатор переправи
  через річку (значення з поля підрозділу `+0x1A4`); якщо `type == 2` (або атака з моря) — гілка з
  модифікатором поля `+0x1A8`, найімовірніше «десантний» штраф. 🔎 / зміст модифікаторів ❓
* `0x4E7760` — допоміжна перевірка «з'єднання з X має тип 1 або 2». 🔎

### 6.4 AI-ключові слова `adjacentenemy` і `adjacency`

* Реєструються в таблиці ключових слів AI: `adjacentenemy` (рядок `0x84BE38`) з кодом `0x71` (`0x52C66C`),
  `adjacency` (`0x84BEC4`) з кодом `0x5E` (`0x52C705`), поруч із `pocket`, `island`, `target`,
  `areadistance` тощо. 🔎
* Використання в даних: `adjacentenemy = 2.0  #higher = much more vary of troops nearby` у блоках
  `invasion = { ... }` файлів `ai/*.ai` (259 файлів; найчастіше 2.0, трапляються також 0.0, 0.005, 0.1, 1.0);
  `adjacency` трапляється лише закоментованим (`#adjacency = 10.0`, `#adjacency = 0.1`). ✅
  Із форматом `adjacent.tbl` не пов'язані.

## 7. Побудова `adjacent.tbl` грою (`0x4EB950`)

Викликається лише тоді, коли файл відсутній (§4.1). Вхід — растрова карта ID **`map\id.tbl`** (рядок
`0x847898`, шлях **жорстко** заданий, навіть для `map_%d`!), вихід — у поточний шлях `adjacent.tbl`
(`0xDC3AC4`). 🔎 У GOG-інсталяції `id.tbl` немає ні в `map/`, ні в `map/Map_1/`. ✅
Отже, видалення `adjacent.tbl` не дасть відновлення в цій інсталяції, а для `Map_1` будівник узагалі взяв би
стандартний `map\id.tbl`. ❓ (наслідок, не перевірявся запуском)

### 7.1 Формат `id.tbl` (як його читає `0x4EEBE0`, запит пікселя `0x4EECA0`) 🔎

```text
u32 run_count
u32 row_start[11520]          // 0x2D00 рядків
u32 runs[run_count]           // молодші 16 біт: x початку відрізка; старші 16 біт: ID провінції (i16)

id(x, y): x >= 29952 -> x -= 29952; x < 0 -> x += 29952 (карта замкнена схід-захід);
          y поза [0, 11520) -> 0;
          від runs[row_start[y]] іти, доки x_start <= x; результат — ID останнього такого відрізка.
```
Кінець рядка, очевидно, позначено відрізком з `x_start > 29951`. ❓
Розміри 29952×11520 (`0x7500`×`0x2D00`) = 936×360 блоків 32×32 рівня 1 `lightmap` (див. `map.md`). 🔎✅

### 7.2 Підрахунок контактів 🔎

* Дві матриці лічильників `(N+1)²` × `i32`, обнулені: **A** — усі контакти, **B** — контакти «через річку»
  (адресація `a*N + b`).
* Обхід **усіх** пікселів `x = 0..29951`, `y = 0..11519` (`0x4EBDBF`, `0x4EBDD6`); розглядаються лише
  пікселі з ID **0** (лінії кордонів у `id.tbl`).
* Для такого пікселя беруться 4 пари проб на відстані 2 px по різні боки:
  `(x−2,y)|(x+2,y)`, `(x,y−2)|(x,y+2)`, `(x+2,y+2)|(x−2,y−2)`, `(x+2,y−2)|(x−2,y+2)` — позначимо `a|b`.
* Якщо `b` має рельєф River (9): `A[a][b] += 1`, і береться третя проба `c` на 16 px від центру за `b`
  у тому ж напрямку — `(x+16,y)`, `(x,y+16)`, `(x−16,y−16)`, `(x−16,y+16)`; якщо `c` — суходіл (рельєф ∉ {8,9}),
  то `A[a][c]`, `A[c][a]`, `B[a][c]`, `B[c][a]` += 1 (сусідство «через річкову провінцію»).
* Інакше: `A[a][b] += 1` і `A[b][a] += 1`. Для не-річкових контактів A симетрична.
* Пари з однаковим ID або з ID 0 потрапляють у матрицю, але далі ігноруються.

### 7.3 Формування списків 🔎

Для `p = 1..N−1`, `offs[p]` = поточна кількість записів:
1. `q = 0..N−1`, `q ∉ {0, p}`, рельєф `q` ≠ River, `A[q][p] > 8` (поріг: щонайменше 9 проб) →
   запис `{q, type = (B[q][p] == A[q][p]) ? 1 : 0, through не записується}`. Тобто `type = 1` лише тоді,
   коли **всі** контакти пари йшли через річкову провінцію.
2. `q = 0..N−1` з рельєфом River і `A[p][q] > 8` → запис `{q, 0, —}` (у кінець списку; саме цю «хвостову»
   частину завантажувач не враховує в `regular_count`).

Потім `offs[N]` = загальна кількість, файл відкривається з `"wb"` (`0x82EF98`) і записуються `N+1` значень
`offs`, а за ними записи по 12 байт (`0x4EC0AC`, `0x4EC0BD`). Третє поле запису не ініціалізується.

### 7.4 Статистика й переповнення 🔎

* Буфер записів — `0x124F80` байт = 100 000 записів. Коли лічильник досягає `0x186A0` (100 000), викликається
  `0x405AD0` з рядком «Build error: Adjacency overflow!» — але в цій збірці `0x405AD0` — порожня функція

## 11. Рекомендації для Rust-реалізації

1. Читати `N` з `misc.txt`; якщо таблиця не узгоджується з розміром файлу — помилка (гра цього не перевіряє).
2. Зберігати записи як `{to: u16/u32, kind: AdjKind, through: Option<ProvinceId>}`, де `through = None`
   для значень поза `1..N-1` (зокрема `0xCDCDCDCD`).
3. Накладати `adj-defs.csv` з точною семантикою §5.2 (включно з «останній рядок виграє», вставкою нових
   сусідів у кінець регулярної частини, видаленням в обидва боки, нечутливим до регістру типом); `\r`
   прибирати перед розбором (гра читає в текстовому режимі). Невідомий тип → `Normal`.
4. Асиметрію **не** виправляти мовчки, щоб поведінка збігалася з оригіналом; але валідатор має про неї
   попереджати (2200 → 1050 у `Map_1`).
5. Провінцію 0 трактувати як таку, що не має сусідів, незалежно від файлу.
6. Якщо колись знадобиться перебудова — алгоритм §7 вимагає `id.tbl`; натомість можна сканувати ID з
   `lightmap1.tbl`, але результат для `Map_1` відрізнятиметься від постаченого (див. §7.5).
