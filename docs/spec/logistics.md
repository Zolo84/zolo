# Специфікація: постачання й логістика — споживання, запаси, TC, IC, поповнення (DH 1.05.1)

Позначки: ✅ простежено в коді, 🔎 імовірно, ❓ невідомо. Адреси — VA (image base 0x400000). Позиції `economy[n]`,
`combat[n]`, `country[n]`, `mod[n]` — 1-based номери чисел у секції ванільного `db/misc.txt`.

**Статус перевірки.** Обидві частини незалежно перевірено вдруге за дизасемблером (§C): частина A — підтверджено з
двома поправками (округлення годинної частки, порядок перевірок у списанні пального); частина B — механіка
підтверджена, але стартові значення Німеччини 1936 уточнено (міністр і технологія, яких не врахував перший прохід).

Реалізація: `dh-sim::consumption` (A), `dh-sim::logistics` (TC, навантаження, IC, ESE країни) і `dh-sim::reinforce`
(поповнення) — частина B.

### A3. Списання

Позначення: `C` = країна (`this`), `L` = провінція списання (об'єкт), `D` = добова потреба (аргумент),
`h := f32(D · (1/24))` (`0x7E5DCC`), `deduct` = останній байт-аргумент, `stat` := (година == 23 (`[0x8934F0]+0x14`
байт години == 0x17)) || (`[0x893710]+0x11D` ≠ 0 ❓). Статистика пишеться лише при `deduct && stat`.
Порівняння «вистачає» — `запас ≥ h` (рівність = успіх), усе f32.

## B. Транспортна ємність (TC), навантаження, IC, поповнення

IC повзунка поповнення, запас MP, ESE (TC/навантаження), відстань D до дружньої провінції.
Далі в тій самій функції — модернізація (повзунок `C+0x3916`, `economy[38..39,41]`, політика UPGRADE_COST/TIME) — не
розбиралась.

#### B5.3 Звідки береться частка IC (повзунок) 🔎
Повзунки — 5 f32 `C+0x3906..0x3916` (CG, production, supplies, reinforcement, upgrade), задаються ключами сценарію
(`consumer`, `production`, `reinforcement`, `upgrading`) або командою `0x479B10` (копіює 5 чисел). У сценарії 1936 їх
немає → reinforcement = 0 на старті. Авто-повзунок (`0x477EF0` «Auto Slider for %s…» → `0x46DF80`) ставить частку
поповнення = `min(вільна частка, C+0x39F4 / IC)` (аналогічно модернізація з `C+0x3A00`), результат — команда `0x45DC70`.
Повна логіка розподілу (порядок, блокування повзунків, CG/supplies) — це економіка, не розбиралась (❓).

#### B5.4 Запас людських ресурсів ✅
`C+0x39CC` (f32, тисячі): конструктор = 10.0 (`0x445D00`); ключ `manpower` у блоці `country` сценарію перезаписує
(`0x54ACD0`: `atof` → +0x39CC і копія +0x39EC; напр. GER 1936 = 850). `relative_manpower` → C+0x3806. Зміна —
лише через `vt+0x28` (`0x49B090`, ≥ 0). Добовий приріст (economy[26..33]) — ❓ не розбирався.

### B6. Арифметика ✅
* `fistp` (TC, load, IC) — поточний режим FPU; гра змінює керівне слово лише в `_ftol` `0x7A5BEC` (усічення, тимчасово
  RC=11b) → у TC/load/IC округлення до найближчого (банківське, half-to-even) 🔎 (DirectDraw, не D3D — точність не
  змінюється). `0x7A5BEC` = `_ftol` (усічення до нуля) — у ліміті ресурсів IC і `economy[6]`.
* Складові load `+0x3974…+0x3988` зберігаються як f32 після **кожного** додавання → накопичувати у f32.

### B7. Відкриті питання
1. ❓ Семантика `state` (`item+0x38`) елемента черги будівництва (множник у TC «province dev/bases»).
2. ❓ Порядок у межах доби: TIMER_HOUR(год 0, поповнення) vs TIMER_DAY (IC/TC) — тікер не знайдено.
3. 🔎 `C+0x4670[t]` / `C+0x48A0[тип]` — технологічні дельти cost/buildtime/manpower (за аналогією; не перевіряв записувачів).
4. ❓ Повна логіка авто-повзунків (`0x46DF80`) і добовий приріст MP (economy[26..33]).
5. ❓ `[[0xD12B00]+0x402]` (вимикає штраф non-national IC), `0x4550F0` (умова «флот лише в порту»), `+0x3ADC/+0x3AE0/+0x3AE4`
   (зарезервовані ресурси в ліміті IC).
6. ❓ Повідомлення `_CEUEVT_REINFORCE_DIVISION_` (0x6F) — обробника не знайшов (не країна: `0x4A8B40` → default).
7. ❓ Ризик повстання `P+0x226` (`0x4E82F0`) детально — потрібен для партизанського навантаження та IC окупованих земель.

## C. Незалежна перевірка: поправки ✅

### C.1 Частина A
1. **Годинна частка:** `h = f32(D · f32(1/24))` (множення на константу `0x7E5DCC` = 0.0416666679), а не `f32(D/24)` —
   різниця до одного ulp. «Досить» — `!(запас < h)`, тобто рівність — успіх.
2. **Пальне (`0x44D190`):** першою перевіряється лише `L.ID == 0` → успіх; `D < 0` обрізається до 0, але **ранньої
   удачі при D ≤ 0 немає**: пошук джерела виконується, і за його відсутності (S < 1 чи без контролера) — невдача
   навіть при нульовій потребі. Припаси (`0x44CCB0`) натомість спершу повертають успіх при `D ≤ 0`.
3. Списання пального з провінційного пулу — пряме віднімання без обмеження; національна нестача — нічого не списує,
   `+0x39B0` не оновлюється.
4. Сухопутні дивізії в повітряному транспорті (`+0x2B2`) пальне споживають (звільняє лише морський `+0x2AE`).
5. Пустельний множник у ванільному `Province.csv` майже не діє: пустелі — 159 Arid і 1 Tropical.
6. Щогодинний обробник країни після пулу ще списує припаси за елементи списку виробництва `+0x3B7E` (`+0x3C == 0`,
   `vt+0x14()`, `+0x46 > 0`): `D = f32(модель.+0x1C + дельта.+0x1C)`, без множника сили, ×0.5 для частини типів (🔎).
7. Точність: CRT ставить 53-бітну точність x87 (`_controlfp(0x10000, 0x30000)` на `0x7ABD5A`), D3D не імпортується;
   константа «0.01» — f32 0.009999999776. Обчислювати в f64, округлювати до f32 там, де гра зберігає 4 байти.

### C.2 Частина B
1. **Множник TC `C+0xE848`** лише **починається** з `country[6]`: подія `_CEUEVT_TC_MOD_` (0x193, `0x490503`)
   змінює його — підтип 1 ставить `v·0.01`, 2 скидає, інакше додає `v·0.01`, мінімум 0.01. Команда технології
   `tc_mod` (тип 0x102) без `which` додає; `techapps` сценарію виконують ефекти технологій при завантаженні
   (`0x549DA0` → `0x7261E0`). Технологія 1310: `tc_mod +10` → 1.1, `tc_occupied_mod +20` → `C+0xE84C` = 1.2.
2. **Міністри:** риса «Silent Workhorse» (`production which=production`, тип 2) дає `C+0x11A88` = 1.05; збіг імені
   риси — без урахування регістру (`_stricmp`).
3. **Німеччина 1936:** B = 142; S = 142 + 7.1 − 14.2 = 134.9 → **IC 135**; TC = fistp(f32(135·1.5·1.10000002)) =
   fistp(222.75) = **223**; навантаження 62 (f32-сума 61.51: суша 46.04 — 36 піхотних, 3 легкотанкові, 1 штаб;
   авіація 14.385 — 11 дивізій на базах; флот 1.085 — 17 кораблів у портах); ESE = 1. Якщо стартовий розрахунок
   іде раніше за перерахунок міністрів (порядок двох обробників GAME_STARTED не доведено), то знімок
   1936-01-01 — IC 128 / TC 211, а з першої доби — 135 / 223.
4. **Навантаження:** кожна дивізія — два окремі f32-додавання (`+0x3974 += пальне·k`, потім `+= припаси·k`);
   частка окупованих (`·1/+0xE84C`) іде в суму неокругленою (`fst`); порядок суми — 3980 + 3974 + 3978 + 3988 +
   3984 + 397C. Функція ESE `0x44AAB0` має ще цілий аргумент, що додається до навантаження (поповнення передає 0).
   «У порту» для пального флоту — об'єкт порту провінції `P+0x46A`.
5. **IC:** поріг (`economy[5]`) рахується від усієї суми S до округлення; `C+0x3AF8/3AF4/3AFC` пишуться після порогу,
   але до обмеження ресурсами; обмеження `_ftol(max(0, min(metal, f32(energy·0.5), f32(rare·2))))` після
   віднімання зарезервованого.
6. **Порядок доби:** тікер `0x5AEA70` → `0x42CF30` зсуває годину й синхронно шле TIMER_DAY, лише потім TIMER_HOUR.
   Тож о 00:00 спершу перераховуються IC/TC/навантаження, а поповнення бачить свіжі значення.
7. **Повзунки:** для гравця денний обробник запускає авто-повзунок (`0x46DF80` на `0x485661`, після TC), якщо ввімкнено
   опцію; ШІ ставить повзунки сам — нульовий повзунок поповнення гарантовано лише на старті.
8. **Округлення:** fistp у режимі «до найближчого парного» важливе: без технології 1310 TC Німеччини було б 202.5 →
   **202** (а не 203).
