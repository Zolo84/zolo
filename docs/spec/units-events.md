# Специфікація: юніти з подій — створення, видалення, розгортання; сон і пробудження генералів (DH 1.05.1)

Позначки: ✅ простежено в коді; 🔎 частково/непрямо; ❓ відкрите. Адреси — VA (база 0x400000). Країна події
(суб'єкт команди) — `C`; дивізія або бригада — `D`; стек (армія, корпус, флот, авіагрупа) — `S`; генерал — `L`;
провінція — `P`. Поля об'єктів — зміщення `+0x…`; номери типів дивізій — `#ID` з units.md.

**Статус перевірки.** Усі десять груп тверджень незалежно перевірено вдруге за дизасемблером і власним розбором
файлів гри (§7): розв'язання випадкових аргументів, `add_corps`, `add_division`, `build_division`, `delete_unit`,
розгортання пулу, сон і пробудження генералів, класи об'єктів дивізій і приклади підтверджено в основному;
спростовано п'ять деталей — `remove_division` порівнює імена **без урахування регістру**, глобальний список
«знищених» дивізій отримує **лише кораблі**, список `C+0x11806` — не `dormant_leaders`, список сплячих `{3007 3050}`
належить SPR, а тригер 3004 вимагає ще й відсутності події 3108. Перевірка додала шість уточнень і лишила два
питання (флот для Graf Spee, країна генералів SPA на момент 3001). Відкликання в пул (§2.1) другим проходом не
перевірялося. Реалізація — `dh-sim::deploy`, `dh-sim::events`.

## 0. Спільна механіка ✅

### 0.1 Типи й обробники
Тип (виконання / валідність): `delete_unit` 0x68 (`0x714110` / `0x710E84`), `build_division` 0xD9 (`0x716153` /
завжди), `add_division` 0xDB (`0x71548E` / завжди), `add_corps` 0xDC (`0x715290` / завжди), `remove_division` 0xDE
(`0x715A77` / `0x7106C8`, спільна з `damage_division` 0xDD і `disorg_division` 0xE0), `wakeleader` 0x09 (`0x714EB1`
/ `0x711184`), `sleepleader` 0x20 (`0x714F55` / `0x7111DF`). Усі сім — **негайні** (events.md §4.1): повідомлення
обробляються синхронно, у порядку файлу. У черзі (після всієї дії) — лише знищення стека, що спорожнів після
`remove_division` (§1.5), і фізичне видалення дивізій знищеного стека (§1.4).

### 0.2 Випадкові аргументи розв'язуються при спрацюванні
Під час спрацювання події (`0x712010`, events.md §2.2) після `srand(насіння повідомлення)` для **кожної** дії
викликається `0x70D1E0`, і лише потім перевіряється доступність дій і пропонується вибір. Виконання обраної дії
(`0x711960`) аргументів не перерозв'язує — виконуються ті, що випали при спрацюванні. Для кожної команди:
```
value, which, where := значення з файлу (збережені копії)       // кожне спрацювання починає з файлових значень
which = −2 → which := провінція-столиця C (0x44E170: столиця, якщо C її контролює, інакше запасна +0x117F0)
which = −3 → which := останній випадковий ID (0x870244) 🔎
далі — гілки за типом (випадковий стек для delete_unit §1.4, пошук за ім'ям для remove_division §1.5, …)
```
Валідність (`0x7102E0`) перевіряється перед кожною командою: спершу власний `trigger` команди, далі **`which < 0` —
команда недійсна** для всіх типів, крім 0x1B..0x1D. Нерозв'язаний −1/−2/−3 означає пропуск команди; дія, де жодна
команда не валідна, недоступна (events.md §3.3).

### 0.3 Форми параметрів (ваніль 1936)
| команда (к-сть) | `which` | `value` | `when` | `where` |
|---|---|---|---|---|
| `delete_unit` (1071) | −1 (701), −2 (272), −3 (98) | — | — | — |
| `add_division` (208) | ім'я (177) | тип дивізії (infantry 55, militia 34, transport 18, …) | модель 0..6 (170) | тип бригади (19) |
| `add_corps` (57) | ім'я | land 37 / air 11 / naval 9 | ID генерала (26) | провінція (57) |
| `build_division` (174) | тип дивізії | тип бригади (36: cag, artillery, naval_improved_hull_l, naval_torpedoes_l) | — | — |
| `remove_division` (32) | ім'я | тег (SPR 17, SPA 15) | — | — |
| `sleepleader` (446), `wakeleader` (48) | ID генерала | — | — | — |

Рядок у `which` (типи 0xDB, 0xDC, 0xDE) парсер зберігає окремо, а `which := 0`; пропущений числовий параметр — 0
(парсер обнуляє всі поля команди). `land` / `naval` / `air` дають `value` 0 / 1 / 2; бригада `#ID` 0 — `none`.

### 0.4 Документація гри
Документація для моддерів (`Modding documentation/event commands.txt`) описує команди так само, як їх виконує код:
`delete_unit` −1/−2/−3 — випадковий сухопутний / морський / повітряний юніт; `add_division` іде в корпус
попереднього `add_corps`, інакше в пул, бригада — найновішої моделі, від'ємний `where` дає пошкоджену дивізію;
`remove_division` — за ID або за ім'ям і тегом; `build_division` — серія, ціна, ім'я, дні до першої одиниці.
Уточнення коду: ім'я порівнюється без регістру; без `when` `add_division` бере модель 0; `build_division` перевіряє
людські ресурси лише на одну одиницю (документація — на кожну); «юніт» у `delete_unit` — цілий стек.

## 1. Команди юнітів ✅

### 1.1 `add_corps`
```
key := новий ID;  «поточний корпус дії» := key      // локальна змінна виконавця; скидається на початку кожної дії
генерал := when > 0 ? (6, when) : немає
value = 0 (land) → сухопутний стек (повідомлення 0x66 → 0x4469B0)
value = 1 (naval) → флот (0x69 → 0x446D30);   інше (air) → авіагрупа (0x67 → 0x446FC0)          // синхронно
новий ПОРОЖНІЙ стек C: ключ := key;  у кінець списку стеків C (C+0x4504);  розмістити в where (0x508670);
    ім'я := which або автоматичне;  +0x180 := 0.5, якщо 0x4A0630(C), інакше 1.0 🔎
генерал є → призначення (повідомлення 0x10B → 0x47BD80, синхронно)
```
* **Перевірок провінції немає** — ні власника, ні контролера. Обмежує лише розміщення: сухопутний стек у провінції з
  рельєфом 8 (море) чи 9 (річка) без перевізника не ставиться й лишається в списку C без провінції.
* Призначення `0x47BD80`: генерал годиться, лише якщо не спить (`+0x2C`), не у відставці (`+0x2D`) і має країну
  (`+0x62`) або стек (`+0x5E`) — умови тригера `leader` (§3.4); інакше стек без генерала (вбудований командир,
  land-combat.md §2.3.2). Генерал знімається зі старого стека, попередній генерал S повертається до списку своєї
  країни (`+0x117F4`), і **генерал переходить до C** (`+0x62 := C`) без перевірки, чий він: `when = <чужий
  генерал>` забирає його в C. Якщо C — людина, дивізії, що вже стоять у S, втрачають 20 % org (новий корпус
  порожній — без наслідків). Start Year не перевіряється (§3.1).
* «Поточний корпус» пише лише `add_corps`: наступні `add_division` дії йдуть у нього до кінця дії або до
  наступного `add_corps`.

### 1.2 `add_division`
```
corps := поточний корпус дії (якщо є)
type := int(value);  btype := where > 0 ? where : 0
model := найновіша доступна модель типу (0x44C410);  when ≥ 0 → model := when      // без when — модель 0!
model ≥ кількості моделей типу → остання
створити D (повідомлення 0x6A → 0x479E20, синхронно):
    об'єкт за класом моделі: суходіл 0x300 (vt 0x7E6A58, +0x15F), авіа 0x2FC (vt 0x7E6A00, +0x160),
        флот 0x300 (vt 0x7E69A8, +0x161);  тип 0x8C («лише бригада», команда add_brigade) — бригада
    власник := C;  характеристики з моделі й бригади btype найновішої моделі
    org := максимальна (модель + модифікатор країни);  ім'я := which або автоматичне;  досвід — як у виробництві
    макс. міцність := стеля типу C (C+0x40A2);  міцність := min(стеля, 100)
    бригада: ім'я — назва типу, org 0, міцність 100 зі 100
    у кінець пулу нерозгорнутих C (§2.1)
where < 0 → D втрачає (−where) % максимальної міцності (повідомлення 0x13E; org не змінюється)
corps є і клас збігається (суходіл ↔ сухопутний стек, флот ↔ флот, авіа ↔ авіагрупа)
    → D переходить у corps (повідомлення 0x6B, org × 0.5, §2.2);  інакше D лишається в пулі
```
**Безкоштовно** (ні людських ресурсів, ні IC, ні ресурсів, ні грошей); доступність моделі не перевіряється. Від
виробленої дивізії (production.md §3.3) відрізняється org: там 0, тут повна. Власник — завжди C. Пастка:
`add_division value = militia` без `when` дає модель 0 навіть країні з новішими.

### 1.3 `build_division`
Не юніт, а **елемент черги виробництва**:
```
type := which;  model := найновіша доступна
value ≥ 0 → бригада value з найновішою моделлю (0 — none);  інакше без бригади
n := when > 0 ? when : 1
cost := cost команди, якщо ≠ 0;  інакше IC на добу дивізії (production.md §2.3)
дні := where > 0 ? −max(1, min(where, дні однієї одиниці))   // від'ємні — «частково виконано» (production §4.1)
                 :  max(1, дні серії з n одиниць)            // production §2.2
людські ресурси C < людських ресурсів ОДНІЄЇ одиниці (production §2.4) → нічого (мовчки)
ім'я := n > 1 ? "" : (name або автоматичне)
замовлення (повідомлення 0x13B → 0x477EF0) у столиці (або запасній провінції)
```
Далі — звичайне виробництво (production.md §4.1: людські ресурси першої одиниці знімаються одразу, від'ємний `cost`
ставить елемент ШІ на початок черги); готова одиниця йде в пул з org 0, звідки її розгортає ШІ (§2).

### 1.4 `delete_unit`
«Юніт» тут — **стек** (об'єкт зі списку `C+0x4504`), а не дивізія.
* Розв'язання при спрацюванні (`0x70D1E0`, гілка спільна зі `switch_allegiance`): `which` −1 / −2 / −3 → кандидати
  — усі **сухопутні / морські / повітряні** стеки C; `rand() % n` → `which`, `value` := ID вибраного стека.
  Кандидатів немає → `which` лишається −1 (для −2/−3 — номер із §0.2, ключ `{which, 0}` не існує) → недійсна.
* Валідність: `which ≥ 1`, стек `{which, int(value)}` існує в реєстрі **і C має хоч один стек**. Явна форма (тип і
  номер ID) зачіпає стек будь-якої країни — повідомлення йде власнику.
* Виконання: UNITDELETE (0x35) власнику, синхронно → `0x483450`: стек існує й ще не знищується (`+0x17D = 0`) →
  загальне знищення `0x449860` (як у бою, але без переможця): рекурсивно знищується все, що стек перевозить; стек
  прибирається зі списку C, з провінції чи порту й з боїв; новина; **генерал повертається в список генералів
  власника** (`+0x117F4`) і звільняється; `+0x17D := 1`; дивізії фізично видаляються, коли обробляється
  повідомлення 0xAD, поставлене в чергу. Людські ресурси **не повертаються** (це робить лише гілка з переможцем).
* Кілька `which = -1` в одній дії вибирають **незалежно** з повного списку й можуть влучити в той самий стек;
  повтор на виконанні недійсний (стека вже немає) і пропускається.

### 1.5 `remove_division`
* Розв'язання за ім'ям (лише 0xDE і 0xDD): `which` — рядок → X := країна з тегу `value`; дивізії всіх стеків X
  порівнюються з рядком **без урахування регістру** (`_stricmp`, `0x7A8430`; у локалі «C» згортаються лише A–Z 🔎);
  перший збіг зупиняє пошук у стеках; потім так само переглядається пул X, і **збіг у пулі переважає**. `which`,
  `value` := ID дивізії; не знайдено → `which = 0` → недійсна. `which = −1` (випадкова) — загальна гілка 🔎.
* Валідність: D існує, її немає в глобальному списку потоплених кораблів `0xD77B36`, власник ≠ 0.
* Виконання: S := стек D; KILL_DIVISION (0x6C) власнику, синхронно → `0x47AA40`: D прибирається зі стека S (S
  перераховується) і з пулів; людські ресурси не повертаються; **корабель** іде в список потоплених (власник := 0,
  лічильники потоплених за типом 🔎) і лишається об'єктом, **сухопутна чи авіадивізія** видаляється одразу. Якщо S
  спорожнів — UNITDELETE для S **у черзі** (після всієї дії), знищення як у `delete_unit`.
* Команда не прив'язана до C: тег `value` може бути будь-яким.

## 2. Пул нерозгорнутих і розгортання

### 2.1 Пул ✅
Список `C+0x4518` (голова `+0x451C`, хвіст `+0x4520`, кількість `+0x4524`) тримає **дивізії й бригади**, не стеки.
Поля D: `+0x6C` стек (0 — у пулі), `+0x14C` провінція призначення (0 — нова одиниця, чекає розгортання), `+0x60`
дата прибуття, `+0x148` провінція походження, `+0x2C0`/`+0x2C6` ключі генерала й стека призначення, `+0x154`
dormant (ключ `dormant = yes`). Джерела: виробництво (org 0), `add_division` (повна org) і відкликання (повідомлення
0x6D → `0x47A780`): D покидає стек, походження := провінція стека (з винятками 🔎), з призначенням — ключі й дата
прибуття; корабель ремонтується до максимуму за `int((макс − міцність) / (рівень морської бази · 0.3 + 1) + 1)`
днів, інший юніт — за дні з повідомлення або 7.

### 2.2 Із пулу в стек: org × 0.5 ✅
Повідомлення 0x6B → `0x47A1F0` (у класах ШІ `0x6A91D0` — те саме плюс облік ШІ):
```
S і D мають існувати;  власник D := C
O := старий стек D;  O стоїть деінде, ніж S → відмова (запис у журнал);  інакше D покидає O
D була в пулі і C ≠ повстанці (343) → org D := max(0, 0.5 · org D)
S сухопутний → окопування S (+0x29E, land-combat.md §4.4) += (окопування O або 0 − окопування S) / (n(S) + 1)
D у S;  походження, призначення, дата := 0
```
**Будь-яке розгортання з пулу половинить org** (і дивізія з пулу «розбавляє» окопування стека). Перевірок класу
й провінції обробник не робить — їх робить той, хто шле повідомлення.

### 2.3 Перевірка місця ✅
«Дружня провінція» `0x4A2ED0(C, P)`: море чи провінція без контролера → `!0x4ECF70(P, C)` 🔎; контролер — C або
власника немає → так; C має військовий доступ до контролера (байт `+0x37` запису C про нього, diplomacy.md §0.3) 🔎
→ так; сюзерен контролера — C → так; спільний альянс → так; інакше ні.

«Можна розгорнути D у P (у стек S)» — `0x49FC40(C, D, P, S)` (вживають ШІ й інтерфейс):
```
D dormant → ні;  контролер P воює з C → ні;  рельєф P — 8 або 9 → ні;  P не дружня → ні;  бригада без S → ні
O := походження D;  O не дружня → O := 0
[для бригад за прапорця 0xDC18DD цей блок пропускається 🔎]
O = 0 (нова): регіон P — на «континенті» регіону столиці (0x4CC9C0) і ВЛАСНИК P = C, інакше ні
O ≠ 0: регіон P — на континенті регіону O, інакше ні (власник не перевіряється)
флот: O ≠ 0, O ≠ P і в O є порт → ні (відкликаний корабель повертається лише до свого порту)
      у P немає порту → ні;  O = 0 і в P немає морської бази → ні
авіа: у P немає авіабази → ні;  S — авіагрупа з ≥ [0xDC15D4] дивізіями, а D не бригада → ні
бригада: у S має бути дивізія, що її приймає (0x4A4000)
→ так
```
Нова дивізія — лише у **власну**, дружню, не захоплену ворогом сухопутну провінцію на континенті столиці; кораблі —
у власну провінцію з портом і морською базою; авіація — з авіабазою. Постачання не перевіряється.

### 2.4 Людина й ШІ ✅
Людина розгортає нові одиниці лише вручну через інтерфейс (`0x61F030` та ін.: `0x49FC40`, новий стек, 0x6B з
org × 0.5 🔎). **Автоматично для людини нічого не розгортається**: агентів розгортання має лише країна ШІ, і виклик
після виробництва (§2.5) робиться лише для ШІ. У ШІ — флот, авіація й бригади (§2.5) і суходіл (§2.6); країна ШІ,
військами якої керує людина, — §2.7. Юніти з призначенням (`+0x14C > 0`) обробляє добовий прохід §2.8.

### 2.5 ШІ: флот, авіація, бригади (`0x6791D0`) ✅
**Коли**: (а) одразу після завершення серії виробництва країни ШІ — у тому ж обробнику (`0x478A95` → `0x67A010` →
`0x679600`, перший крок якого — `0x6791D0`), якщо гра приймає команди (`0x42E980`); (б) агент економіки ШІ
(`0x679FD0`) перепланує себе через `rand() % 2 + 1` днів (1–2) і щоразу запускає той самий планувальник.
```
для кожної D пулу:
    пропуск: D.дата прибуття ≥ сьогодні (у нових — 0), сухопутна (зокрема сухопутні бригади), dormant
    роль := тип 30 (transport) → 1;  25 (destroyer) / 22 (light_cruiser) → rand() непарне;  інакше 0
    S := ПЕРШИЙ стек у списку C: власник C, стоїть у провінції, 0x49FC40(C, D, провінція S, S), провінція в
         регіоні столиці (або запасної провінції, якщо C не контролює столицю), і
         флот: S — флот, має агента ШІ (+0x1F4) і роль агента == роль 🔎
         авіа: S — авіагрупа, сумісність за типом (12..16 — окремі перевірки; типи ≥ 17 — НІКОЛИ)
    S немає → флот: «лише бригада» — пропуск, інакше новий флот у ПЕРШІЙ провінції списку C+0xE892 з портом і
         контролером C (без 0x49FC40 і без вимоги морської бази);  авіа: нова авіагрупа в першій провінції
         регіону столиці, що проходить 0x49FC40(C, D, P, —);  такої провінції немає → пропуск
    бригада → приєднати до дивізії S, що її приймає;  інакше → журнал і 0x6B (org × 0.5)
```
Авіатипи ≥ 17 (`cas`, `transport_plane`, `flying_bomb`, `flying_rocket`) щоразу отримують нову авіагрупу.

### 2.6 ШІ: суходіл (`0x695700`) ✅
**Коли**: метод військового агента ШІ `0x691120` наприкінці перепланує себе через d днів: d = 1, якщо C воює (або
прапорець `[0xD68566]+0x57C` 🔎), інакше `rand() % 7 + 1` (1–7) 🔎 (ланка повідомлення 0xAC до методу простежена
не до кінця). Якщо військами C не керує людина (§2.7), метод проходить фази агента; розгортання — `0x695700`:
```
для кожного регіону R зі списку C+0xE880 (🔎 театри ШІ):
   B := D пулу: не бригада, суходіл, не dormant, без призначення, дата прибуття ≤ сьогодні, і
        (без походження і R — регіон столиці) або регіон походження — R чи пов'язаний з ним (0x4C7E5D)
   R «належить» C (0x4C9E31):
      S* := серед стеків ШІ: у провінції в R, дружній (0x4E9FB0), не 0x5253A0 🔎, власник C — перший підхожий,
            далі лише строго ближчий до столиці (відстань від провінції або від наступного вузла маршруту)
      для D ∈ B:
          D — гарнізон (тип 9) або S* немає:
              P := R — регіон столиці і C контролює столицю ? столиця : перша провінція R
              P > 0, контролюється C, дружня → новий корпус у P;  S* := НОВИЙ КОРПУС
          журнал;  D → S* (0x6B, org × 0.5)
```
Нові сухопутні дивізії йдуть у **наявний стек, найближчий до столиці**, у регіоні столиці (або в новий корпус у
столиці); гарнізон завжди відкриває новий корпус, і решта кандидатів того ж проходу вливається вже туди. Якщо
новий корпус створити не вдалося, а S* є, — гарнізон іде в S*.

### 2.7 Військами країни ШІ керує людина → столиця ✅
`0x6A8420(C)`: перша країна i з ненульовим байтом `C+0x34AC+i` — під людиною (або i = 0 ❓). Тоді `0x691120`
замість фаз агента розгортає **кожну** D пулу без призначення, не dormant і не бригаду — без перевірки дати й без
`0x49FC40`: суходіл — новий корпус у столиці (або запасній провінції), авіа — нова авіагрупа там же, флот — новий
флот у провінції `0x44E190(C)+0x52` 🔎 (база регіону столиці), якщо там порт (інакше лишається в пулі); кожна —
через 0x6B (org × 0.5).

### 2.8 Добовий прохід юнітів з призначенням (`0x4846C0`) ✅
Щодня в обробнику країни, якщо гра приймає команди; лише D з `+0x14C > 0` (відкликання, §2.1).
```
P := призначення
D ще в дорозі (дата прибуття > сьогодні) і P дружня → чекати
інакше (прибула або P стала недружньою):
   C контролює P або P дружня → ціль := P
   інакше, якщо прибула: остання сусідня провінція не море/річка, не +0x180 🔎, дружня
   інакше: походження O, якщо дружнє;  інакше пошук дружньої провінції, найближчої до O, — але знайдена
           ГУБИТЬСЯ (0x484C8F) → ціль := 0 → столиця, якщо C її контролює, інакше D ЗНИЩУЄТЬСЯ
           (якщо дружніх провінцій немає зовсім — ціль := P;  без походження — одразу столиця або знищення)
   авіа, у цілі немає авіабази → найближча контрольована авіабаза C;  немає → призначення й походження := 0
           (D стає «новою» і чекає розгортання, §2.4)
   стек: збережений за ключем (власник C, та сама провінція, суходіл ↔ суходіл, авіа ↔ авіа; ФЛОТ приймає
         будь-кого) → стек C у цілі з ім'ям D.+0xC4 (без регістру; лише сухопутний чи авіа)
         → новий: авіа — авіагрупа, усе інше — СУХОПУТНИЙ стек (кораблі теж)
   0x6B (org × 0.5);  гарнізон у стеку без місії → місія 7 🔎;  поля пулу скинуто
```
Дивацтва гри (за кодом): знайдена найближча провінція губиться, і за неконтрольованої столиці юніт зникає;
корабель отримує сухопутний стек; флот за збереженим ключем приймає будь-яку дивізію.

## 3. Генерали ✅

### 3.1 Поля, сплячі й країна генерала
Поля L (land-combat.md §2.3.1): `+0x2C` спить (dormant), `+0x2D` у відставці / недоступний, `+0x5E` стек, `+0x62`
країна, `+0x52` / `+0x56` Start / End Year. Ключ у реєстрі — `(6, ID)`.
* Ключ сценарію `dormant_leaders` додає кожен ID у **глобальний** набір сплячих `[0xD61340]+0x1C574` (не в список
  країни); на старті гри всім генералам із набору ставиться `+0x2C := 1`.
* Розподіл по країнах на старті (`0x76DED0`): End Year > поточного року (і Start Year < `[this+0x12]` ❓, ймовірно
  далекий рік) → генерал у списку країни `+0x117F4`, `+0x62 := країна`; інакше `+0x2D := 1`. Отже, генерал з
  майбутнім Start Year має країну з першого дня. Генерали країни, якої на старті немає, отримують країну пізніше
  (`0x76DFA0`), коли її створюють 🔎.
* `C+0x11806` — окремий список країни, що завантажується з `db\leaders` 🔎; `wakeleader` прибирає L і звідти.

### 3.2 `sleepleader`
Валідність: L існує, має країну або стек, не спить, не у відставці. `which = −1` — випадковий генерал 🔎 (у ванілі
лише ID). Виконання: KILL_LEADER (0x91) країні L, синхронно → `0x47C0B0` (у класах людини — обгортка `0x651C40` з
повідомленнями гравцю, що закінчується тим самим): L немає або у відставці → нічого; якщо L командує S — S
лишається без генерала (вбудований командир ранг 25, land-combat.md §2.3.2), кожен бій S переобирає командувача
сторони, L повертається в список генералів власника S і звільняється; далі `L.спить := 1`, ключ L — у глобальний
набір сплячих. Країна L, відставка й місце в списку країни не змінюються; стек і дивізії лишаються на місці.

### 3.3 `wakeleader`
Валідність: L існує, має країну або стек, **спить**, не у відставці. Виконання: ACTIVATE_LEADER (0x8E) країні L з
порожнім ключем стека, синхронно → `0x482B60` (у класах людини — через `0x651B60`): без стека в повідомленні —
`L.спить := 0` і L у списку генералів адресата (з ключем стека, в інших викликах, L лише призначається в стек, сон
не знімається); в обох гілках L прибирається зі списку `C+0x11806` адресата, а ключ — з глобального набору.

### 3.4 Тригер `leader = ID`
`0x732750` (events.md §3.2): істина, якщо L існує, не спить, не у відставці й має стек або країну. Після
`sleepleader` — хиба, після `wakeleader` — знову істина. Країна й Start Year не перевіряються.

## 5. Реалізація в `dh-sim`
Модуль `dh-sim::deploy` (система `Deployment`) створює й знищує стеки (генерал повертається країні, нічого не
відшкодовується), додає дивізії з `add_division` у пул і переводить їх зі пулу в стек за половину організації, перевіряє
місце за §2.2 і виконує розгортання ШІ: кораблі, авіацію й бригади — у день завершення серії виробництва ШІ та кожні
`rand()%2+1` дні; сухопутні — за ритмом військового агента (щодня у війні, інакше кожні `rand()%7+1` дні); країна з
військовим контролем людини — у столицю. Пул людини автоматично не розгортається. `dh-sim::events` розв'язує випадкові
аргументи при спрацюванні й виконує команди §1 (`remove_division` — без урахування регістру), `steal_tech`, пули
транспортів і ескортів; `dh-sim::leaders` — сон і пробудження, глобальний набір «сплячих» зі сценарію, тригер `leader`.
Готова одиниця виробництва йде в пул з організацією 0 і запитом на розгортання. Тести на реальних даних: Graf Spee
приєднується до Kriegsmarine у провінції 80 у день завершення (1936-01-07) з організацією 0; подія 3001 —
«Tropas de África» у 347 під 3422 із шістьма дивізіями на половині організації, ополчення й транспорти в пулі, 3460
спить; 3002 → 3004 прибирає Легіон Кондор. Спрощення: «континент» регіону — суходільна зв'язність; порядок провінцій
регіону — пошук у глибину від найменшого ID; роль флоту (неперевірений тест агента) — «має транспорти»; перевірку
постачання вважаємо пройденою в регіоні столиці; найновіша модель — найбільший `new_model` технологій країни;
автоматичних назв, відкликання в пул із призначенням, сплячих дивізій, `where` у `build_division`, перевезених стеків
серед кандидатів `delete_unit`, бригад у пошуку `remove_division`, інших театрів ШІ, `convoy` і `resource` немає;
кожен генерал має країну з CSV від старту.

## 6. Відкриті питання
1. Інтерфейс розгортання людини (`0x61F030`) — відомий лише за викликами.
2. Ланка повідомлення 0xAC → `0x691120`, перший запуск військового агента після старту чи створення країни,

## 7. Незалежна перевірка: поправки ✅
1. **`remove_division` порівнює імена без урахування регістру** (`_stricmp`, `0x7A8430`), а не точним `strcmp`.
2. **Список `0xD77B36` — лише кораблі**: потоплений корабель лишається об'єктом без власника; сухопутні й повітряні
   дивізії `0x47AA40` видаляє одразу.
3. **`C+0x11806` — не список `dormant_leaders`**: ключ сценарію наповнює глобальний набір сплячих, а `C+0x11806` —
   список країни з `db\leaders`; `wakeleader` прибирає L з обох.
4. **`{3007 3050}` — список сплячих SPR** (`spain.inc`), не SPA; 3422 немає в жодному списку, висновок §4.1 чинний.
5. **Тригер 3004** вимагає ще й того, щоб подія 3108 не сталася (`NOT` над двома умовами — NOR).
6. Доповнення: міцність нової дивізії `add_division` — **min(стеля, 100)** при максимумі = стеля; валідність
   `delete_unit` вимагає хоч одного стека в C, а дивізії знищеного стека видаляються, коли обробляється повідомлення
   в черзі; `add_corps` **забирає чужого генерала** в C; лише для людини зміна генерала коштує дивізіям стека 20 %
   org; сухопутний стек не ставиться в море чи річку (рельєф 8/9); авіатипи ≥ 17 не приєднуються до наявної
   авіагрупи.
7. Лишилися невизначеними: флот для Graf Spee («Kriegsmarine» у 80 найімовірніше, але можливий Кіль) і країна
   генералів SPA на момент 3001.
8. Підтверджено: типи й обробники; розв'язання аргументів при спрацюванні; `add_corps`, `add_division`,
   `build_division`, `delete_unit` (§1); org × 0.5 при виході з пулу, `0x49FC40`, розгортання лише для ШІ та його
   каденції (§2); сон, пробудження й `leader` (§3); класи 0x2FC / `+0x160` — авіа, 0x300 vt 0x7E69A8 / `+0x161` —
   флот; дані прикладів.
