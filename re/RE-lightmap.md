## 1. Суть

`lightmap1..4.tbl` — це не «лише освітлення», а **готова піксельна сітка провінцій
на 4 зум-рівнях + шар «запеченого» освітлення** на тих самих рівнях. Гра
використовує ці файли для:
- визначення провінції за пікселем екрана (кліки, тултіпи, розстановка) — «GetProvinceAt»;
- відмальовування тайлів карти (затінення кольору провінції за світловим полем).

Перевірка: точка міста Рейк'явіка (13159, 749) → провінція 1 на L1; 2300/2769
точок міст збігаються точно на L1 (решту — портові/прикордонні пікселі);
ASCII-рендер Ісландії відтворює реальні обриси узбережжя (Рейк'явік 'R',
Акурейрі 'A', фіорди).

## 2. Файлова структура (усі 4 файли однакова, ПІДТВЕРДЖЕНО)

```
[таблиця зсувів: N×uint32 LE] [uint32 dataSize] [дані: dataSize байтів]
```

- **N = (936/s)·(360/s)**, де s = 2^(рівень−1): L1→336 960, L2→84 240, L3→21 060,
  L4→5 265 записів. (Попередній звіт помилково вважав 336 961 для всіх рівнів —
  це справедливо ЛИШЕ для L1.)
- **uint32 dataSize** стоїть одразу після таблиці (файловий офсет N·4): це і розмір
  області даних, і «сторожовий» зсув table[N] (монотонність зберігається, table[N] == dataSize).
- **Зсуви — відносно початку області даних**: секція i займає байти
  [table[i], table[i+1]): table[0] = 0, розділи йдуть без проміжків, суворо монотонно,
  table[N] = dataSize (перевірено для всіх 4 файлів).
- Контрольні числа (таблиця / dataSize / розмір файлу):
  | файл | N | таблиця Б | dataSize | файл |
  |---|---|---|---|---|
  | L1 | 336 960 | 1 347 840 | 22 502 879 | 23 850 723 |
  | L2 | 84 240 | 336 960 | 20 050 247 | 20 387 211 |
  | L3 | 21 060 | 84 240 | 12 133 718 | 12 217 962 |
  | L4 | 5 265 | 21 060 | 3 452 687 | 3 536 931 |
- Секцій із нульовою довжиною немає. Мінімальна секція = 6 Б, максимальна:
  1478 (L1), 1585 (L2), 1869 (L3), 1629 (L4).

## 3. Завантажувач 0x4D8F50 (з декомпіляції + асемблера)

Викликається з FUN_004D7400 (ініціалізація мапи, після boundbox). Цикл i = 1..4:

1. `FUN_007A630A(buf, "%s\lightmap%d.tbl" @0x847874, path @0x00DC1970, i)` — ім'я файлу;
2. `FUN_00426F50(stream, имя)` — конструктор файлового потоку (віртуальна таблиця
   0x007E3BA0, всередині f-відкриття);
3. обчислення розміру таблиці (асемблер 4D8FB5..4D8FF4):
   `eax = (int)(0x7E7F48[double=360.0] / scale)`; `eax = eax·29952`;
   `eax = (eax + (eax>>31 & 31)) >> 5` (= ceil(·/32)); `eax = eax / scale`; `×4`.
   Підсумок: **4·(936/scale)·(360/scale) байт** (0x7E7F48 = 360.0 = висота мапи в тайлах;
   scale = 1,2,4,8);
4. `bufA = new[uVar5]`; `FUN_004271A0(bufA, uVar5)` — **читає таблицю**;
5. `FUN_004271A0(&field[8], 4)` — читає dataSize (третє поле структури рівня);
6. `bufB = new[dataSize]`; `FUN_004271A0(bufB, dataSize)` — читає область даних;
7. `FUN_00426F80(stream)` — деструктор потоку (закриття).

`FUN_004271A0 = fread`-обгортка (перевірка: `FUN_007A67C4(ptr,1,size,FILE*)`,
помилка → рядок «Error reading file: %s» @0x83A3F0).

Структури рівнів: 4 записи по 12 Б, зсув 0x00AA10E0 + lvl·12:
`[0]=bufA (таблиця), [4]=bufB (дані), [8]=dataSize`. Рівень зум-індексу z (0..3)
відповідає файлу lightmap(z+1).tbl. Звільнення: FUN_004D9080 (free).

## 4. Формат секції (ПІДТВЕРДЖЕНО побайтово на всіх 447 525 секціях)

Секція i містить опис тайла: тайл = (32·2^z)×(32·2^z) пікселів мапи; внутрішня
сітка освітлення/провінцій у тайлі **завжди 32×32** «світлопікселів»
(розмір світлопікселя = 2^z пікселів мапи; на L1 = 1 px мапи).

### 4.1 Список ID (змінної довжини, k ≥ 1)

Пари байтів `(lo, hi)`: значення = `(hi & 0x7F) << 8 | lo`; **термінатор = пара, у
якої hi ≥ 0x80** (сама пара — останній елемент списку; біт 0x80 у значення не
входить). Довжина списку 2k байт. Спостережувані k: 1..34 (L1); розподіл на L1
(вибірка): k=1: ~91%, k=2: ~11%, далі 3..34.

Значення списку: провінційні ID (≤ 2769; 0 = PROV0/порожньо) та «border-коди» (> 2769) — див. §6.

### 4.2 Прапорець/квадродерево

Байт на зсуві 2k. **Біт 0 (LSB) = «розбити корінь 32×32»**:
- `0` → тайл однорідний: листів N = 1, лист покриває весь тайл;
- `1` → далі йде бітовий потік квадродерева з кореня рівня 5 (32×32).
  Кількість листів N (максимум 4⁵ = 1024).

**Читання бітів**: біт 0 байта споживається окремо (маска 0x01), далі біти цього ж
байта 1..7, потім біт 0 наступного байта, біти 1..7 … (маска 0x02→0x04→…→0x80→
0x01, перенос на наступний байт після біта 7). Потік починається з байта 2k.

**Декодер вузла (рівень l, координати (x,y), розмір 2^l)** (`FUN_004DC920` — лічильник
листів): читає 1 біт:
- `0` → лист 2^l × 2^l, вихід;
- `1` при l ≥ 2 → розбити на 4 дитини рівня l−1;
- `1` при l == 1 → 4 листи 1×1, вихід.

**Порядок відвідування дітей: SE → SW → NE → NW** (знизу-справа вгору-вліво).
Тобто стек LIFO: push NW, NE, SW, потім SE обробляється першим.
(ВАЖЛИВО: попередня ревізія записувала корені (0,0),(16,0),(0,16),(16,16) з
порядком NW→NE→SW→SE і коментарем «підтверджено оберненим рендером» — це
ХИБНО. Перевірка на реальних даних: звірка city-координат 2753 провінцій
Province.csv проти розкодованої карти дає 2751 збіг лише при порядку SE→SW→NE→NW;
при дзеркальному NW→… збігається лише 2276 (477 міст потрапляють на сусідні
провінції в межах блока 32×32). Обидва порядки споживають ОДНАКОВУ кількість
бітів і дають ОДНАКОВИЙ розмір секції — тому перевірка довжини порядок не
розрізняє; потрібна семантична звірка позицій. Незалежне підтвердження:
відкритий проєкт Zolo84/zolo (декодер HoI2-редактора) використовує той самий
порядок SE→SW→NE→NW.)

Початок наступного потоку (refs): `2k + bytes_consumed + (mask > 1 ? 1 : 0)`.

### 4.3 Потік refs (N значень, розрядність за k)

Індекси на список ID: значення 0..k−1. Розрядність:
- k == 1 → 0 біт (усі refs = 0, байтів 0);
- k == 2 → 1 біт; k ∈ 3..4 → 2 біти; k ∈ 5..16 → 4 біти; k > 16 → 8 біт.
Пакування LSB-first: 1-бітний — біти байта по порядку; 2-бітний — (b&3), (b>>2)&3,
(b>>4)&3, (b>>6); 4-бітний — молодша тетрада спочатку; 8-бітний — байт напряму.
Довжина = ceil(N·depth/8) байт.

### 4.4 Потік значень освітлення (N значень по 6 біт)

4 значення на 3 байти (LSB-first):
`v0 = b0 & 0x3F; v1 = (b1 & 0xF) << 2 | b0 >> 6; v2 = (b2 & 3) << 4 | b1 >> 4; v3 = b2 >> 2`.
Довжина = ceil(N/4)·3 байти (для N=1 це 3 байти — «хвіст» падінгу в 6-байтових секціях).

### 4.5 Еталонний 6-байтовий зразок (L1, тайл 0: океан)

`62 89 00 18 00 00` → ID = (0x89&0x7F)<<8 | 0x62 = **2402** (провінція океану);
flag 0x00 (однорідний, N=1); значення освітлення = 0x18 & 0x3F = **24**; байти 4–5 —
шматок 3-байтової групи 6-бітного потоку (не використані).

Той самий тайл у попередньому звіті описано як «(98,137,0),(24,0,0)» — це й був
цілий 6-байтовий розділ, а не «два триплети RGB».

### 4.6 Розгорнутий зразок (L1, тайл Рейк'явіка, 255 Б)

`01 00 | 00 44 | 01 44 | 03 00 | 00 47 | 01 C7 | 7F C0 0D 18 24 E7 …`
- список: [1, 17408=0x4400, 17409=0x4401, 3, 18176=0x4700, 18177=0x4701] — провінції
  1 (Рейк'явік) і 3 (Акурейрі) + border-коди;
- flag = 0x7F → квадродерево; N = 184 листи; refs (зразок) [2,2,1,1,1,1,1,0,0,…] —
  пікселі берега посилаються на різні провінції;
- значення освітлення 19..63 (середнє 31.8).

## 5. Зум-піраміда (ПІДТВЕРДЖЕНО)

| рівень | scale s | сітка тайлів | тайл, px мапи | світлопіксель, px мапи |
|---|---|---|---|---|
| 1 | 1 | 936×360 | 32×32 | 1×1 |
| 2 | 2 | 468×180 | 64×64 | 2×2 |
| 3 | 4 | 234×90 | 128×128 | 4×4 |
| 4 | 8 | 117×45 | 256×256 | 8×8 |

Один і той самий географічний піксель: секція тайла (x/s, y/s) на рівні s містить у
своєму списку ID ту саму провінцію (перевірено для Рейк'явіка на L1..L4:
L1 → ID 1 у списку; L2 (205,11), L3 (102,5), L4 (51,2) — також містять 1).
Внутрішня сітка завжди 32×32 субпікселів; зменшення деталізації = менша кількість
листів у квадродереві + об'єднання провінцій у списках (на L4 у секціях часто
лише 2–5 ID).

## 6. Семантика полів

### 6.1 Список ID = провінційна сітка (ПІДТВЕРДЖЕНО)

- Значення ≤ 2769 — **номер провінції** (перевірено: точка міста Рейк'явіка → 1;
  2300/2769 міст на L1 точно; «промахи» = порти/прикордонні пікселі, де сітка дає
  сусідню провінцію, напр. PROV2→2676, PROV4→2716, PROV10→12).
- Значення > 2769 — **border-коди** пікселів на межі провінцій (у рендері Ісландії
  вони утворюють тонкі ланцюжки рівно по межах R/A та берегових лініях):
  - біти 8..13 (`(v>>8) & 0x3F`) — індекс у runtime-таблиці сусідів 64×int32
    (адреса 0x00A98460 — збігається з базою об'єкта мап-рендера; точне наповнення
    **НЕ ПІДТВЕРДЖЕНО**; спостережувані індекси: 4, 7, 9, 14, 6, 12, 8, 10, 11, 13…),
  - біти 1..4 (`(v>>1) & 0xF`) — зсув у масиві прикордонних точок провінції
    (поле провінції +0x298, записи по 0x0C Б; перший uint32 запису = сусідня провінція;
    верх обмежений полем +0x290),
  - біт 0 — сторона/прапорець.
  Розв'язка border-коду виконується в FUN_004DAFB0 з урахуванням видимості
  провінцій (FOW, прапорці +0x180/+0x46E, прапорець режиму 0xA98444): у деяких
  режимах карти прикордонному пікселю присвоюється «спецпровінція»
  (numProvinces − (v&1) + 3 або +1). Точна формула таблиці/вибору — непідтверджена.

### 6.2 6-бітне поле = запечене освітлення (ПІДТВЕРДЖЕНО, точна формула — re/RE-colors.md)

- Діапазон 19..63 у вибірці; однорідні океанічні тайли: 24 (35 085 шт.) та 19
  (12 620 шт.) — два кластери (можливо глибина/регіон);
- **градієнт по широті**: середнє значення однорідного океану 20.6 (північ, рядки
  0–30) → 23.9 (південь, рядки 330–360) — художній затемнений північ, світлий південь;
- на суші варіює 19..63 (Рейк'явік: середнє 31.8, піки 63);
- використання в рендері (FUN_004DC010): значення разом із базовим кольором
  провінції (поля +0x13E/+0x142) через таблицю 0x00AA41CB (256 Б) та 16-бітну
  палітру 0x00A44C34 дає колір пікселя екрана → **це буквально шар освітлення
  («lightmap»)**, а не висота: океан не нульовий і має плавний градієнт.
- **Точна формула (підтверджено живою грою 2026-10-24)**:
  `колір = palette565[(LUT[light − off] << 6) | scale]`,
  де off=+0x13E (15), scale=+0x142 (0..63), LUT[i]=clamp(i+47,4,127),
  palette565 = 8192×u16 RGB565 (рядок = LUT-значення, стовпець = шкала).
  Океан = шкала 12: LUT 47-49 → (136,172,216) = 0x8D7B.
  Повний паспорт кольорів: **re/RE-colors.md**.

## 9. Відкриті питання (чесно)

1. Точний вміст/побудова 64-елементної таблиці border-кодів (runtime, 0xA98460).
2. ~~Точно крива освітлення (LUT 0xAA41CB)~~ **ВИРІШЕНО (2026-10-24)**: формула
   `palette565[(LUT[light-off] << 6) | scale]` підтверджена живою грою;
   див. re/RE-colors.md. Лишається: що саме означає кластер «19» vs «24» в океані.
3. Чи є 6-бітне поле чисто художнім освітленням, чи містить вкладений сигнал
   (глибина/висота) — рендер використовує його безпосередньо як колір, тож
   «чисте освітлення» найімовірніше, але математика кривої не відновлена.
4. Генератор цих файлів: у exe записувача немає (файли створюються зовнішнім
   інструментом мода — у ланцюжку рядків лише bordermap.bmp).
5. Поведінка «спецпровінцій» numProvinces±1/±3 при FOW — режимо-залежна і
   неповністю зрозуміла поза контекстом режимів стратегічної карти.

## 10. Як відтворити мапу

Для відмальовування карти на рівні L1: таблиця L1 + секції → для кожного тайла
список ID (розгорнути border-коди) + квадродерево (32×32 сітка) → для кожного
субпікселя провінція; 6-бітне поле — яскравість (0..63). Колір пікселя — через
точну формулу освітлення: політична палітра 0xA44C34 + LUT 0xAA41CB + поля
провінцій +0x13E/+0x142 → re/RE-colors.md (реалізація: dh-format/src/map_color.rs).
