## A. Склад набору 1380 морських зон

### A1. Розмірна структура (підтверджено, як і в RE-mapformats-full)
- 7 617 604 Б = `uint16 1380` + `uint16 0` + 1380×1380×`float32` = 7 617 600 ✓.
- Матриця симетрична (0 порушень на 200 випадкових пар), діагональ 0.
- Одиниця: **K = 72.3845 км/од** (калібрування по 143 парах row0 з унікальним exact-збігом;
  RE-док «72.4» — добре наближення). `навал[км] = значення × 72.3845`.

### A2. Набір провінцій: **568 морів + 812 портів = 1380** (ПІДТВЕРДЖЕНО)
- Терени Province.csv: Ocean 609 (з них 41 — **озера/замкнені басейни та «глобальні океани»**:
  1012, 1159, 2464 + 2746..2769 + 508/509/510, 1042, 1096, 1160, 1173, 1366, 1983/1984, 2263,
  2463, 2680, 2687 — це всі компоненти морського графа, КРІМ головного), тобто у відкритий
  океан виходить **568 морів**.
- Портів (Port Allowed=1 ≡ Port Seazone>0, набори ідентичні): **812**.
- 568 + 812 = **1380 точно**. Порівняння з альтернативою «609 морів + 771 порт» (з RE-доку):
  exact-кандидати перших зон (див. A4) трапляються ВИКЛЮЧНО серед {головний морський компонент ∪ порти},
  озера жодного разу не з'являються як кандидати → перемагає 568+812.

### A3. Порядок зон у матриці — НЕ за Id (спростування гіпотези RE-доку)
RE-док припускав «перші ~40 зон = провінції 1..41 за Id». Рядок 0 це спростовує:
зона 1 = 2654 (Coast of Greenland), зона 2 = 2716 (The Hebrides), зона 3 = 4 (Stornoway),
зона 5 = 6 (Inverness) — тобто **перші зони = північна Атлантика навколо Ісландії/Британії,
а не Id-порядок**. (Збіг «(0,3)=966.5 = GC(Рейк'явік→Сторновей)» з RE-доку — справжній,
звідси їхнє хибне узагальнення про Id-порядок.)

### A4. Ідентифікація зон через airdist (еталон)

### A5. ВАЖЛИВА ЗНАХІДКА: морські точки гри ≠ distances.csv (для частини зон)
При перехресній перевірці **попарних** відстаней між зонами виявлено розрив:
наприклад, M[1][3]×72.4 = **291.8 км**, тоді як adist(2654, 4) = **1804 км**
(пряма аеро-відстань Гренландія–Сторновей). Аналогічно M[1][2] = 512.6 км проти
adist(2654, 2716) = 1862 км. Тобто **однакова зона не може одночасно задовольнити рядок 0
і міжзонні пари при CSV-координатах** — морська матриця рахувалась на «морських точках»,
що для морських провінцій (26xx/27xx) **не збігаються з центрами з distances.csv**.
Симптоми того самого:
- зони 3 (966.5 км) і 6 (967.3 км від Рейк'явіка) обидві мають exact-кандидата «4 Stornoway»
  — за CSV такої пари не існує (другий запис на колі 967±4 немає), але M[3][6] = 129.6 км;
- пари з дуже малими значеннями: M[0][1300] = 33.3 км, M[3][1320] = 7.2 км, M[6][1319] = 1.4 км,
  M[1][1312] = 82.5 км — відстані «порт ↔ своя морська акваторія», яких немає в airdist
  (жодної провінції за 25–45 км від Рейк'явіка в airdist!).
Висновок: **набір = 1380 морських ТОЧОК (порт-точки і морські точки), а не 1380 CSV-центрів.
Порти, схоже, використовують CSV/порт-координати (збіги рядка 0 точні до 0.3 км),
моря — окремі «морські центри» (ймовірно, з мапи/пікселів або внутрішнього списку гри).**
Тому: точна бієкція зона→провінція відновлена для зон, чия морська точка ≈ CSV-центр
(перші ~15 зон + ~600 інших з |Δ|≤4 км), а РЕШТА потребує відновлення «морських координат»
трилатерацією з матриці (або розбору генератора в exe).

### A6. Статус питання (A)
- Набір 1380 (568 морів головного компонента + 812 портів): **ПІДТВЕРДЖЕНО**.
- Одиниця K=72.3845, семантика «морська відстань ≥ великого кола»: **ПІДТВЕРДЖЕНО**
  (адist-зіставлення; жодна пара точково-відомих зон не має naval < adist понад похибку).
- Порядок ≠ Id; перші зони ідентифіковані (табл. A4): **ВСТАНОВЛЕНО**.
- Повна бієкція 1380 зон: **НЕВІДНОВЛЕНА ПОВНІСТЮ** — морські точки гри для морів
  відрізняються від distances.csv (A5); потрібні «морські координати» (exe або трилатерація).

## B. Проекція мапи y↔lat (i x↔lon)

### B1. Дані
- Province.csv: City X/Y, Port X/Y (пікселі повної мапи 0..29952 × 0..11520); boundbox.tbl:
  bbox центрів (половинний масштаб 0..14976 × 0..5760 для per-провінційних, див. RE-док).
- distances.csv: lat/lon (8 знаків) для 2770 провінцій — **джерело airdist** (B3).

### B2. Співставлення (lat,lon)↔(x,y) — результат
Повна афінна підгонка (lat,lon) = A·(x,y)+b по **2756 bbox-центрах** і по **портах**:
- lat: rmse ≈ **3.0–3.3°**, p95 ≈ 6°; lon: rmse ≈ 3.9–11° (після unwrap ±180°).
Найкращі лінійні коефіцієнти (bbox-центри, повний масштаб):
  `lat ≈ 72.44 + 0.000212·x − 0.010582·y`
  `lon ≈ −173.85 + 0.011764·x + 0.000301·y`
Наближення RE-доку «y ↔ lat лінійно [75°N..−48°S]» (lat = 75 − 123·y/11520) відповідає цим
нахилам (≈0.01068 °/px) і є **розумною апроксимацією з кореляцією ~0.984, але з розкидом ±3°**.
Точнішої формули (рівнопроміжна, меркатор, поліноми 1–5 ступеня — перевірено) **не існує**:
залишок не скорочується нижче ~3° за жодної гладкої формули від (x,y).

Висновок: **distances.csv — це «географічні» координати, внесені розробниками як дані для
розрахунку відстаней, а не виведені з пікселів мапи проекцією.** Відхилення від bbox-центрів
сягають 0.5–3° (приклади: Reykjavik bbox-центр (13090,730) → csv (63.15,−21.05), а лінійна
формула дає (67.5,−19.7); The Hebrides: (14466,1535) → csv (57.0,−7.0)). Для «портових» пар
(boundbox↔csv) розкид такий самий. Тому для відмальовування пікселів мапи слід користуватися
координатами мапи (bbox/Province.csv) напряму, а не через distances.csv.

### B3. Контрольна перевірка через airdist (проекція ↔ відстані)
- airdist = великоколові відстані, розраховані **з distances.csv** (формула гаверсину,
  r ≈ 6378 км): підтверджено на ~4000 випадкових пар (похибка ≤ 2 км, 28/3998 > 2 км —
  виключно округлення uint16 та ±1 км).
- navaldist-значення для зон із відомими точками (напр. (0,3): 13.35 → 966.5 км =
  adist(1,4) = 967; (0,5): 15.43 → 1117.1 км = adist(1,6) = 1117) — збігаються, що підтверджує
  і шкалу 72.3845, і використання тих самих координат для портів.
- Тобто: «проекція» csv-координат гри = їхні lat/lon прямо; проекція мапи НЕ відновлюється
  з csv, бо csv не є функцією пікселів (B2).

### B4. Статус питання (B)
- Формула лат/лон із пікселів: **апроксимативна** (лінійна [75°N..−48°S]×[−180..180],
  ±3°/±6°), точна проекція гри **не існує в даних** — csv-координати є окремим набором.
- Перевірка через airdist: **виконана**, великоколова модель з r=6378 підтверджена.
- Морські точки navaldist2 для морів ≠ csv (A5) → якщо потрібна точна мапа морських зон,
  її слід відновлювати трилатерацією з navaldist2 (відкрите питання).
