## 1. Суть: border-код — це НЕ індекс у статичній таблиці

Border-код `v` (> 2769) у списку ID тайла кодує **провінцію-власника пікселя
через позицію в списку ID самого тайла** + точку межі + сторону:

```
v = 0x4000 | (idx << 8) | (off << 1) | side
  idx = (v >> 8) & 0x3F   — слот спільного буфера (див. §3); 4 ≤ idx < k+4
  A   = список_тайла[idx − 4]              — провінція-власник пікселя (≤ 2769)
  off = (v >> 1) & 0xF    — № запису в списку суміжностей провінції A (0..15)
  B   = adjacent[A][off]                   — провінція по той бік межі
  side = v & 1            — сторона (для FOW-підміни, §4)
```

- Біт 14 (0x4000) встановлено у ВСІХ border-кодах усіх рівнів (перевірено:
  `(v>>14)&3 == 1` для 227 002/227 002) — це константа-маркер, що гарантує
  v > 2769 (найменший реальний border-код 0x4400 = 17408).
- Біти 5..7 ЗАВЖДИ 0 (перевірено); біти 8..13 — idx; 1..4 — off; 0 — side.
- Розв'язка коду (0x4DAFB0) біт 14 ІГНОРУЄ — він служить лише для відрізнення
  border-коду від номера провінції (чому 0x4000, а не менший діапазон —
  припущення: будь-який `idx<<8` з idx≤8 дає значення < 2769, тож генератор
  зсуває коди на 0x4000 у вільний діапазон).

## 3. «64-елементна border-таблиця» 0xA98460 — що це насправді

Декодер 0x4DAFB0 читає border-значення як `*(int*)(0xA98470 + idx*4 − 0x10)`,
тобто база «таблиці» = **0xA98460** (64 слоти × 4 Б = 0xA98460..0xA9855F).
`0xA98470` = значення глобального `DAT_00aa4320`, встановлене в конструкторі
FUN_004D8EB0 (`mov ds:0xaa4320, 0xa98470`). ВИСНОВОК: це **спільний статичний
робочий буфер класу рендера мапи** (BSS: лежить у віртуальному .data,
VSize 0x59AC94, але ПОЗА файлом — RSize .data = 0x55000 закінчується на
0x481000; у файлі exe за адресою 0xA98460 **немає даних — нулі/0xCD... не
застосовне, це нулі BSS**; pefile-перевірка: VA 0xA98460 у жодній секції не
покривається файловим вмістом).

Наповнення слотів (розшифровано по замовчувачах/записах):
- **слоти 0..3 (0xA98460..0xA9846F) — службові поля об'єкта рендера**:
  - 0xA98460 — this-вказівник на heap-об'єкт класу (operator_new(0x25E),
    конструктор FUN_004010A0, vtable 0x7E32FC; запис: 0x4D6F20);
  - 0xA98464 — zoom-експонента (сеттер FUN_004D8EA0; використовується як
    лічильник зсуву `shl .., cl` у 0x4D8D90);
  - 0xA98468 / 0xA9846C — координати / центр відображуваної області
    (запис у 0x4D8DC6/0x4D8DCD; похідні в 0x847858/0x84785C);
- **слоти 4..63 (0xA98470..) — СПИСОК ID поточного тайла**: декодер пише
  k значень списку сюди (`список[i]` = слот 4+i). Реально використовуються
  слоти 4..4+k−1 (k ≤ 34 на L1, до ~49 на L3), решта — нулі.

Тому border-код завжди має idx ≥ 4 (перевірено: жодного idx < 4) — слоти 0..3
містять не-провінційні значення (вказівник/зум/координати; при читанні вони
санітайзяться: `if (A > 2769) A = 0`). «Зсув +4» в border-коді = фізичний зсув
списку відносно бази буфера.

**Відмінність від попереднього звіту**: попереднє припущення про «runtime-
таблицю сусідів 64×int32 з наповненням» — спростовано. Окремої 64-таблиці
НЕМАЄ: border-код адресує провінцію через позицію в списку ID тайла,
а «таблиця сусідів» — це масив суміжностей провінцій (adjacent.tbl, §5).
У файлі exe статичного наповнення цієї області немає (BSS).

## 4. Повна розв'язка border-коду в FUN_004DAFB0 (0x4DB08D..0x4DB19C)

```
v ≤ 2769                     → провінція як є
v > 2769:
  A = буфер[idx] (= список[idx-4]);  if (A > 2769) A = 0;   // санітайз
  off = clamp(off, 0, count(A)-1);   // count = провінція.+0x290
  if (A < 1)                       → результат = A          // 0
  B = borderPoints[A][off].prov    // перший dword запису 12 Б
  якщо (режим FOW увімкнено) І (B «невидима») І (прапорці +0x180 A і B = 0):
      результат = 2769 − side + 3   // якщо провінція A: +0x46E == 0
      результат = 2769 − side + 1   // інакше
  інакше → результат = A
```

Умова «B невидима»: (DAT_00a98444 & 0x4000) != 0  (біт FOW у наборі прапорців
режиму карти 0xA98444: 0x241ff, 0xa41ff, 0x4800, 0x243f5, 0x800, 0x441ff...)
І FUN_004ED310(A, B) == 0, де FUN_004ED310 = `prov[A]+0x3D8 == prov[B]+0x3D8`
(поле +0x3D8 — «власник/контроль»: сусід видимий, якщо під тим самим контролем).
Прапорець +0x180 провінції — примусова видимість; +0x46E — типовий прапорець
(сеттер FUN_004E8A10; точна семантика НЕ підтверджена, гіпотеза: море/суша —
визначає, який FOW-маркер використати).

Спецзначення 2770..2772 (= 2769−side+1/3) — «FOW-маркери прихованого сусіда»
(гіпотеза: рендер фарбує їх у колір «невідомої території»; пряма перевірка
рендера не проводилась).

## 5. Масив прикордонних точок (borderPoints) та adjacent.tbl

- Поля провінції (запис 0x4B2 Б, база DAT_00ab27b4): **+0x290** = count,
  **+0x294** = capacity, **+0x298** = вказівник на масив записів **по 12 Б**.
  Запис: `{int prov (сусід), int type, int extra}`.
  - type (runtime, з CSV adj-defs.csv через FUN_004E3DC0): 0 = normal,
    1 = river, 2 = sea?, 3 = canal, 4 = impassable (рядки "river"/"canal"/
    "impassable"/"normal"/"remove"); у готовому adjacent.tbl типу немає (0).
  - extra — значення з CSV; у adjacent.tbl = 0xCDCDCDCD (debug-сміття, не
    заповнене).
- **adjacent.tbl** (map/Map_1/adjacent.tbl, 200 096 Б — ПІДТВЕРДЖЕНО):
  `[таблиця (numProvinces+1)×uint32 префіксних сум]` (останній = 15751) +
  `[15751 запис × 12 Б]`. numProvinces = 0x877690 = 2769 (empirically). Порядок
  записів = порядок off у border-кодах (підтверджено прикладами §2.2).
- Завантажувач **FUN_004E0B60**: читає adjacent.tbl → копіює записи в
  borderPoints кожної провінції (+0x290/+0x294/+0x298), відфільтровуючи
  сусідів, чия провінція має тип 9 (поле +0x254; count = після фільтра).
- Якщо adjacent.bin немає — **FUN_004EBBA0** («Rebuilding...», рядок
  "..\\..\\build files\\bordermap.bmp" тієї ж послідовності) будує суміжності
  скануванням сітки провінцій і зберігає.

## 6. Відкриті питання (чесно)

1. Семантика прапорця +0x46E (впливає на вибір FOW-маркера +1 vs +3) і
   прапорця +0x180 — точно не встановлена.
2. Чому маркер саме 0x4000 (біт 14) — спостережено факт; мотивація генератора
   (зовнішній інструмент) — припущення (гарантія v > 2769).
3. Чи використовує рендер значення спецпровінцій 2770..2772 (колір «туману»)
   — не перевірялось.
4. Запис borderPoints[+4] (type) та [+8] (extra) у розв'язці border-коду НЕ
   використовуються — лише [+0]; вони потрібні іншим підсистемам (річки,
   канали, непрохідність).

## 7. Як розкодувати border-код самостійно

1. Розпарсити список ID тайла (§4.1 RE-lightmap.md): значення v.
2. Якщо v ≤ 2769 — провінція. Інакше:
   `idx = (v>>8)&0x3F; off = (v>>1)&0xF; side = v&1; A = список[idx-4];`
3. `B = adjacent_tbl[A][off]` (таблиця префіксних сум + записи 12 Б).
4. Піксель належить провінції A; B — сусід по той бік; side — сторона
   (впливає лише на FOW-підміну в грі).
