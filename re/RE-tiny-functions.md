## 1. FUN_004136a0 @ 4136a0 (13 Б) — диспетчер `this->vtable[1](arg)`; фактично `FontManager::GetFont(ім'я_bmp)`

Декомпіляція (файл є): `(**(code **)(*param_1 + 4))(param_2)` — виклик 5-го слота віртуальної таблиці з передачею **одного аргументу** (this зберігається в ecx). Асемблер:

```
4136a0: mov edx,[esp+4]      ; arg
4136a4: mov eax,[ecx]        ; vtable
4136a6: push edx
4136a7: call [eax+4]         ; vt[1](arg)
4136aa: ret 4
```

**Семантика доведена викликами (728 call-site'ів у всьому .text!):** я зібрав усі 728 місць виклику та витягнув останній `push imm32` перед кожним:

| push (ім'я файлу) | к-сть викликів |
|---|---|
| 0x82f010 `"eurostilecond14.bmp"` | 322 |
| 0x83bcc0 `"eurostilecond14bold.bmp"` | 254 |
| 0x848100 `"eurostilecond24bold.bmp"` | 93 |
| 0x82f024 `"eurostilecond20bold.bmp"` | 38 |
| 0x85b444 `"eurostilecond18bold.bmp"` | 14 |
| 0x83b87c `"eurostilecond14FixNum.bmp"` | 1 |
| 0x87b688/0x87c00c/0x87c038 (копії рядків у .data) | 3+1+1 |
| 0xfa, 0xf2, 0xff (артефакти зворотного скану, не імена) | 3 |

- Тобто **726/728** викликів передають ім'я .bmp-шрифта; значення, що повертається, зберігається як вказівник шрифта (напр. `mov [esi+0x56], eax`, `mov [esi+0x18], eax`) або повертається далі.
- `this` у всіх викликах — `DWORD PTR ds:0x88ebb4` = **глобальний менеджер шрифтів**.
- Слот vt[1] менеджера = **FUN_00414410** (vtable 0x7e35c4: `[0]=0x413ab0` deleting-dtor, `[1]=0x414410`): це **пошук рядка в тернарному дереві** (TST): порівняння перших символів, рекурсія `FUN_004148b0` у гілки `+6/+0xa/+0xe`, при збігу повертає `**(param_1+4)` = **об'єкт шрифта**. Тобто GetFont = «знайти шрифт за іменем у кеші-дереві».
- **Відповідь на питання RE-fonts.md §8 «висота клітинки [?]»**: 0x4136a0 **НЕ** пов'язаний із висотою клітинки. Висота = param_3 завантажувача `FUN_00411598` (квадратні клітинки W×W, підтверджено піксельним аналізом). 0x4136a0 — отримувач шрифта за ім'ям (формулювання «реєстрація шрифту за ім'ям» уточнено: це *отримання/кеш-пошук*, а не реєстрація).
- **[?] Відкрите питання:** `DAT_0088ebb4` (сам покажчик менеджера) лежить у BSS-хвості .data (RVA 0x48EBB4 > raw-розмір .data 0x55000 → нуль у статичному образі) і в усьому .text **жодного разу не записується** — лише 734 читання `mov ecx, ds:0x88ebb4`, 1 перевірка `cmp ...,0` і обнуління при shutdown (0x78febe). Хто ініціалізує в рантаймі — статично не знайдено (те саме для `DAT_0088ebb0`=HDC, див. §3). Менеджер-об'єкт на 0x88ebb8 конструюється статично: `0x4136b0: mov ecx,0x88ebb8; call 0x4136f0` (vtable 0x7e35c4 + sub-vtable 0x7e35f0 на +0x12) + atexit-деструктор 0x4136d0→0x413950.

## 2. FUN_00411b53 @ 411b53 (96 Б) — конструктор «другого класу шрифтів» (не GDI!)

Декомпіляція (файл є) + асемблер:

```
push ebp / mov ebp,esp / sub esp,8
mov [ebp-8], ecx                    ; this
mov ecx, [ebp-8]
call 0x583720                       ; конструктор базового класу (спільний для багатьох класів гри)
mov [this+0],  0x7e35c0             ; vtable = PTR_FUN_007e35c0
mov [this+0xc], 0                   ; param_1[3] — покажчик (у dtor звільняється operator delete)
mov [this+0x8], 0                   ; param_1[2] — покажчик на таблицю гліфів (у dtor ітерується!)
цикл i=0..0x100: mov [this+0x14+i*4], 0   ; inline-таблиця 256 гліфів (0x14..0x413)
return this
```

- Клас = **другий (споріднений) клас шрифтів** з RE-fonts.md §4: vtable `0x7e35c0`, таблиця гліфів на +0x14 (256×4), поруч +0x8 (теж таблиця гліфів, що звільняється в dtor через `FUN_00411230`+free) та +0xc.
- Супутні функції класу (vtable 0x7e35c0: `[0]=0x413670` scalar-deleting-dtor → `0x411bb3` dtor (331 Б: звільняє +0xc, таблицю +8 (гліфи 8-байтові через FUN_00411230), слоти +0x14, потім базу), `[2]=0x414410` (TST-пошук — метод GetFont доступний і тут), далі 0x4144a0...0x414720).
- `FUN_00411cfe` (105 Б) = «звільнити всі гліфи таблиці +0x14» — викликається при shutdown.
- **Це НЕ GDI-клас**: у конструкторі немає жодного GDI-виклику; гліфи — ті ж 8-байтові RLE-об'єкти, що й у першого класу (FUN_00411230/00411210).
- Клас реально інстанціюється: **5 статичних глобалів** у CRT-ініціалізації: `0xdc3d08` (0x78f63d), `0xdc2cc8` (0x78f67f), `0xdc30e0` (0x78f6bb), `0xdc4228` (0x78f6fd), `0xdc2170` (0x78f739; + ще 0xdc2688/0xdc4640 — через 411cfe при shutdown 0x78fec8-0x78feeb). Активне використання в грі — як у RE-fonts.md: «використання в DH не простежене» **[?]** (інстанси є, але хто вантажить у них гліфи — потребує окремого розбору 0x4144xx-групи).

## 3. GDI-текст у бінарнику: CreateFontA/SelectObject/TextOut — ВІДСУТНІ

- Повний список імпортів GDI32.dll (з таблиці імпортів exe):
  - `GetStockObject` (IAT 0x3e3010) — лише **2 виклики** (0x78f7f8, 0x78f869), обидва `push 4, call` — це **BLACK_BRUSH для hbrBackground двох WNDCLASS** (поряд: LoadIconA(0x65), CreateWindowEx...; USER32-імпорти 0x7e31e0 = LoadIconA тощо). До шрифтів стосунку не має.
  - `GetCharWidth32A` (IAT 0x3e3014) — лише **1 виклик**, у `FUN_0041363e` (0x41363e, 44 Б): `GetCharWidth32A(DAT_0088ebb0, ch, ch, &w)` — міряє ширину символа на глобальному HDC.
- **Немає** (grep по всьому дизасемблеру + по всіх декомпіляціях + повний список імпортів GDI32/USER32): CreateFontA/W, SelectObject, DeleteObject, TextOutA/W, ExtTextOut, GetTextExtent*, GetTextMetrics, SetTextColor — **жодного**. USER32-імпорти — лише віконні (CreateWindowExA, LoadIconA, RegisterClassExA, DefWindowProcA...).
- `FUN_0041363e` — **мертвий код**: жодного `call 0x41363e` у .text. До того ж `DAT_0088ebb0`, який передається як HDC, — BSS-глобал (нуль у статичному образі), що **ніде не записується** (єдине посилання в .text — саме це читання). Тобто навіть у живу виклик дав би GetCharWidth32A(0,...) → FALSE.
- **Висновок:** DH не має GDI-тексту взагалі. Весь текст — бітмап-шрифти через власний рендерер FUN_00411e4d (RE-fonts.md §5). «Другий клас шрифтів» також внутрішній; GDI-міряльник ширини — спадок HoI2, у DH не підключений.
