## 2. Механіка FUN_00533df2 (0x533df2)

```c
// void __thiscall FUN_00533df2(запис* this, uint id, char* рядок)
*this = id;              // перші 4 байти комірки = ID токена
strcpy(this+4, рядок);   // далі — текст ключового слова (до 512 байт)
```

Це **не** хеш-таблиця і не сам реєстр: це **ініціалізатор комірки запису** формату `struct { uint32 id; char name[512]; }` (516 Б = 0x204 — такий крок записів, які перебирає `FUN_00533f75` у циклі `0xafa16c + i*0x204`). ID іде стеком, адреса комірки — у ECX (`this`).

`FUN_0052bb4a` — ланцюжок із 1669 таких викликів (33 КБ), що заповнює весь масив записів (BSS-хвіст .data, обнулений при старті). Прямих викликів `FUN_0052bb4a` у корпусі не знайдено (жодного E8/E9-переходу чи вказівника) — імовірно викликається через CRT-таблицю ініціалізаторів/непрямий виклик; без нього реєстр був би порожнім, тож він виконується до `FUN_00533f75`.


## 3. Реєстр і пошук (рядок → ID → обробник)

- **Масив записів**: `0xafa16c` (BSS), 1669 записів по 0x204 Б: `{ int id; char name[512] }` (id на 0xafa168+i*0x204, ім'я на +4).

- **Таблиця вказівників**: `DAT_00bcc57c[1690]` — `id → вказівник на ім'я`; будує `FUN_00533f75`.

- **Спеціальні ID** (без імені в таблиці): 1..10 — розділювачі `= " { } ( ) # ¤(0xA4) , \n` (0x850b30..); 0x528='\t', 0x529=' ', 0x52a (0x850b58..); службові типи токенів: 0x524 — слово/число, 0x527 — рядок, 0x531 — EOF, 4 — `{`, 8 — `}`.

- **Динамічна реєстрація**: `FUN_00535cf0`/`FUN_005362c0`/`FUN_0053f2a0` викликають `FUN_00533df2(1|0x528, динамічний_рядок)` у рантаймі.

- **Пошук рядка**: BST — вставка `FUN_0042a0fe` (дублікат → друк помилки), пошук `FUN_00429fa0` (strcmp-обхід). Користувачі: `FUN_005342d1` (лексер), `FUN_00534368` (API слово→ID, немає → 0x527).

- **Споживання ID**: `FUN_00534a40` (стейтменти), `FUN_004a8c90` (288-case switch), завантажувачі (0x4bb6b0 — події, 0x4d0250 — building_costs, ...).
