**Джерела:** `/tmp/dh-disasm.txt` (objdump, 1 381 251 рядків), `/tmp/dh-decomp/` (Ghidra), `/tmp/dh-functions-index.txt`.
**Метод:** суцільне дизасемблювання регіонів 0x741400–0x7423ff, 0x743f00, 0x7443f0–0x74454a, 0x7466f0–0x7468ac; grep по всьому .text на call-site'и; звірка з декомпіляціями.

## (1) Серверна частина Bsocket (0x7416a0–0x7418a0) — accept-loop НЕ ІСНУЄ у покритому коді

### 0x741740 — `Bsocket::bind+listen` (відновлено повністю; у функцій-індексі ВІДСУТНЯ)
Сигнатура: `(this, backlog:int)` — `ret 0x4`, 1 стековий аргумент.
```
1. createSocket() 0x7420f0 (стан → 2); <0 → return -1
2. temp AnsiString ← константа 0x88ebf8 == "" (порожній хост; strlen/copy/free-машинерія 0x674e40/0x674e20)
3. 0x741ff0(this, &temp)  — заповнення sockaddr_in на this+0x26: sin_family=2, порт=htons(this+4),
   хост порожній → htonl(INADDR_ANY); помилка → return -1 (без змін стану)
4. bind(sock([this+0x22]), &this+0x26, 16)  (IAT 0x796ac2, stdcall ret 0xc)
   помилка → WSAGetLastError→this+0x36, return -1
5. listen(sock, backlog=аргумент)  (IAT 0x796abc, stdcall ret 0x8)
   помилка → WSAGetLastError→this+0x36, return -1
6. стан → 8 (НОВЕ значення: 8 = "слухає"), return 1
```

### 0x741870 — `Bsocket::accept` (обгортка accept; індексована)
`accept(sock, NULL, NULL)` (IAT 0x796ac8). Успіх → **повертає сирий SOCKET** (не обгортає у Bsocket); помилка → `WSAGetLastError→+0x36`, лог "accept: " (0x874400), return -1. Жодного циклу/обробки нового сокета тут немає.

### 0x7416a0 — `read-until-pattern` (не індексована; раніше описана неточно)
Сигнатура: `(this, buf, maxlen, pattern)` — `ret 0xc`.
```
- memset(buf, 0, maxlen) (аргумент 2 як довжина)
- цикл з pos=2: recv(sock, buf+pos-2, 1, 0)  ← прапор = 0, НЕ MSG_PEEK (виправлення попереднього звіту)
  - домішує по 1 байту в буфер (накопичення з позиції 0)
  - після кожного байта: 0x7a9780(buf, pattern) — це КАСТОМНИЙ substring-search (2 аргументи,
    оптимізований word-пошук перших 2 байт зразка; НЕ memcmp, як було написано раніше)
  - зразок знайдено → return (лічильник+1) = кількість прочитаних байт, включно зі зразком
  - recv==-1 → WSAGetLastError→+0x36, return -1; recv==0 (EOF) → return -1
  - pos==maxlen (ліміт) → return -1
```

### Висновок по (1): активного accept-loop немає
У ВСЬОМУ дизасемблі (1.38M рядків) функції серверного шляху зустрічаються **рівно один раз — у власних визначниках; жодного call-site**:
`0x7416a0`, `0x741740`, `0x741870` (accept), `0x741fc0` (setSocket — «природне» продовження accept: стан→4, this+0x22=сокет), `0x741d00` (readAll), `0x741fe0` (setBufferSize), а також обидві одноразові send-копії `0x741bc0` і `0x7421d0` (див. нижче).
Серверна функціональність Bsocket присутня в бінарі, але НЕ прив'язана до жодного покритого шляху — гра-хост не крутить server-loop через цей клас у покритому коді. Принципово не виключені непрямі виклики через вказівники з .data/.rdata (дамп даних-секцій недоступний — exe відсутній, лише Ghidra-проєкт) — **не підтверджено**.

## (2) «timeout=10000» — це НЕ таймаут, а РОЗМІР БУФЕРА ЧИТАННЯ (read-chunk)

### Поле +0xa і його повний життєвий цикл (grep по всьому .text: ВСЬОГО 5 звернень)
| Адреса | Операція |
|---|---|
| 0x741472 (ctor 0x741450) | `+0xa = арг3` (10000 = 0x2710; у всіх 4 call-site'ах: 7447de, 745601, 74610c, 757313 — `push 0x2710; push 1; push 0; lea ecx,...; call 741450`) |
| 0x741fe0 | сеттер `Bsocket::setBufferSize(int)` — `+0xa = арг` (аксесор, 4 байти) |
| 0x741d0b / 0x741d1b / 0x741d42 | читання в **0x741d00 (readAll)** — див. нижче |

**Ніде більше** — ні в connect (0x7418a0), ні в recvN (0x741f50), ні в recv-until (0x741630), ні в writeAll (0x741dd0), ні в bind/listen/accept — поле +0xa не читається. Таймаутних примітивів (select/WSAEventSelect/SO_RCVTIMEO) у Bsocket немає взагалі.

### 0x741d00 — `Bsocket::readAll` (НЕ індексована, у попередньому звіті пропущена)
Сигнатура: `(this, char** out_buf)` — `ret 0x4`; повертає загальну довжину або -1.
```
buf = new char[this+0xa]                      // 0x7a635c — первинний буфер 10000
off = 0
loop:
  n = recv(sock, buf+off, this+0xa, 0)        // порція = ціле +0xa
  n==-1 → WSAGetLastError→+0x36; free(buf); *out=0; return -1
  n==this+0xa → буфер повний → grow: new char[off+n+this+0xa]; memcpy; free(old); off+=n; continue
  інакше → *out=buf; return off+n            // неповна порція = кінець даних
```
Тобто **readAll читає «весь потік до тиші»**: поки кожна порція заповнюється на 10000 байт — буфер росте; вихід — як тільки прийшла неповна порція (або помилка). Розмір порції = поле +0xa = 3-й аргумент конструктора.
Примітка: `0x741dd0` (якому попередній звіт приписував «write-all-цикл send») — підтверджено декомпіляцією `FUN_00741dd0.c`: це саме **writeAll** (`Ordinal_19`=send, цикл до повної відправки, лог "Bsocket._write: "+hexdump+'\n', помилка → "Tried to BSocket._write: "+WSAGetLastError→+0x36). А ось readAll — окрема функція 0x741d00, яку раніше плутали з нею.

### Висновок по (2)
Третій параметр конструктора (10000) — розмір буфера/порції читання (chunk size) для readAll, що встановлюється в +0xa і змінюється через 0x741fe0. Позначення «timeout» у попередньому звіті — помилкове. Нижня межа перевірки: `readAll` сама не має call-site'ів (мертва в покритті), тож «таймаут» і не міг проявитися в роботі клієнта.

## (3) 0x7466f0 — call-site ВІДСУТНІЙ (підтверджено), семантика відновлена

**Пошук:** `grep '7466f0'` по всьому дизасемблі → **1 збіг — сам визначник** (рядок 1151647). Жодного `call`, жодного завантаження адреси. У декомпіляціях `grep FUN_007466f0` → лише власний файл. Сусідні `7466b0` (007466b0, індексована) також не посилається на неї.

**Семантика (дизасемблювання 0x7466f0–0x7468ac + декомпіляція):** `int reconnect(host:char*, port, thread_name:char*, password:char*)` — метод класу ClientLobby (SEH-кадр 0x7df4f8):
1. Копіює host (param_1) і password (param_4) у локальні AnsiString;
2. Створює PThread-об'єкт з ім'ям param_3 (0x673c70);
3. Викликає логін `0x7460d0` (який сам робить connect і весь обмін);
4. Якщо логін успішний (повернув 0) → `reconnect` вбудованого Bsocket: `lea ecx,[this+0x1a]; call 0x741b50` (закриття старого сокета + connect);
5. При -1 → фатал `"socket.reconnects(cil.getPort() , cil.getIP())"` (0x87470c, ClientLobby.cpp рядок 0x6a=106, 0x87473c).

Висновок: у межах покриття 0x7466f0 — **мертвий код** (можливий виклик поза покриттям через таблицю функцій/колбек, оскільки це виглядає як колбек повторного підключення лобі; перевірити без даних-секцій неможливо — не підтверджено).

## (4) 0x7443f0 — «Network reader thread» (повний розбір)

### Об'єкт потоку (створюється 0x748370, індексована; дубль ініціалізації — 0x744150)
`FUN_00748370` — конструктор ThreadSafeList-об'єкта, що водночас є контейнером потоку:
- +0x00 vtable `0x7fa1a0` (список також має внутрішню vtable 0x7fa1ec на +0xe)
- +0x04 вказівник на структуру повідомлення `{char* buf; int len}` (ініціалізується аргументом виклику 748370 — див. «непідтверджене»)
- +0x08 `Bsocket*` (саме на ньому читаються пакети)
- +0x0c стоп-прапорець (byte)
- +0x22 PMutex (CreateMutexA), +0x2a голова списку (вузол з +0x4a060), +0x2e лічильник вузлів
- Ім'я м'ютекса/списку: "ThreadSafeList Mutex" (0x87463c); ім'я потоку: `s_Network_reader_thread` (0x8744d4)

Обгортка PThread: `operator_new(0x20)` → `[0]=vtable 0x7fa1e8/0x7fa1f0`, `[1]=ThreadSafeList*`, `[5]=0x7443f0` — **функція встановлюється як ДАНІ (поле об'єкта), тому у .text немає її xref'ів**. Запуск через PThread::start (0x743630) → CreateThread прока → **trampoline 0x743f00**: `ecx=[arg+4]`; якщо 0 → віртуальний `run()` (vtable+4); інакше `call [arg+0x14]` **без стекових аргументів, з ecx = PThread[4] = ThreadSafeList** — так 7443f0 отримує this.

### Цикл 0x7443f0 (this = ThreadSafeList-об'єкт)
```
while ([+0xc] != 1):                       // стоп-прапорець
  1. 0x741630(this->bsocket(+0x8), stackbuf[32], 0x20, delim=0)
     — читання по 1 байту ДО байта '\0'; <=0 → потік завершується (повна зупинка циклу)
  2. len = atoi(stackbuf)                  // 0x7a7b3c
     len<=0 → вихід; len > [esp+0x10] → вихід
     [esp+0x10] = неініціалізований локаль стеку (у кадрі вище немає запису;
     trampoline 743f00 локальних не має) → фактичний ліміт НЕДЕТЕРМІНОВАНИЙ
     (на практиці майже завжди проходить; жодного cmp,100 тут НЕМАЄ)
  3. payload = operator_new(len); recvN(bsocket, payload, len)  // 0x741f50
     != len → free(payload); вихід потоку
  4. msgbuf: [+0x4-структура].buf = payload; .len = len
  5. WaitForSingleObject(mutex +0x22, INFINITE)   // помилка → фатал Mutex.h:128 (0x87460c)
  6. node = operator_new(0xc); push у список (голова +0x2a); node[2] = &+0x4-структура;
     [+0x2e]++
  7. ReleaseMutex(+0x22)                     // помилка → фатал Mutex.h:149 (0x8745ec)
```
Особливості:
- Потік **мовчки завершується** при будь-якій аномалії читання (жодних повторних спроб).
- Перевірки «останній байт payload == '\0'» у reader ТУТ немає (на відміну від читачів рядків 0x745980/0x7459f?); recvN просто тягне рівно len байт.
- Кожна ітерація виконує додатковий `operator_new(8)` — результат зберігається в локаль і **ніколи не використовується** (dead store; імовірно, заміщений у процесі компіляції код {buf,len}-структури).
- Накопичення: самі вузли (по 12 байт) і payload-буфери — heap; нічого не звільняється самим reader'ом (власник черги).
- Раніше звіт коректно вказував 0x744433 (read-until-0) і 0x744470 (recvN) — підтверджено; додано: буфер довжини — 32 байти на стеку (ліміт фактично ~30 байт через `maxlen-2` у 0x741630).

## (6) Створення Bsocket-об'єктів: завжди ВБУДОВАНІ/СТЕКОВІ, operator new немає

Усі 4 call-site'и конструктора (grep `call 0x741450`):
| Call-site | Контекст | Зберігання |
|---|---|---|
| 0x7447de | ctor net-клієнта (vtable 0x7fa210) | **вбудовано у клас, зсув +0x1a** (`lea ebp,[esi+0x1a]; mov ecx,ebp`) |
| 0x74610c | логін 0x7460d0 (ClientLobby login) | **стековий локаль** (`lea ecx,[esp+0x4c]`) |
| 0x745601 | логін-варіант 0x7455d0 | **стековий локаль** (`lea ecx,[esp+0x44]`) |
| 0x757313 | ctor 0x7572e0 (клас PThreadClient-стилю, vtable 0x7fa2cc) | **вбудовано у клас, зсув +0x10** (`lea ecx,[ebx+0x10]`) |

У жодному з цих call-ів немає попереднього `operator_new` для самого Bsocket (єдиний new поблизу — 0x20 байт для PThread у 0x744798/0x7572e0 — НЕ для Bsocket).
Підтвердження вбудовування +0x1a: dtor клієнта 0x7468b0 → `lea ecx,[esi+0x1a]; call 0x7415c0`; клієнтський reconnect 0x7466f0 → `lea ecx,[edx+0x1a]; call 0x741b50`.
Стек-варіанти Y 0x7460d0/0x7455d0 знищуються ЯВНИМ викликом 0x741520 перед кожним return (11 site-ів: 745632, 7457d1, 74584c, 745895, 7461a9, 746387, 74645f, 746a87, 7574a2 + делегування 741500→741503).

**Розмір об'єкта Bsocket:** поля займають +0x00..+0x36(+4) = ~0x3a байт; vtable `0x7fa188`; віртуальних викликів через [this] у покритому коді немає (всі методи викликаються прямо).

## Виправлення та уточнення попереднього звіту (RE-network.md)

1. **«timeout=10000» → розмір буфера читання readAll** (поле +0xa; п. (2)). Позначення «таймаут» знято.
2. **0x7416a0**: recv-прапор = **0** (не MSG_PEEK); порівняння — **substring-search 0x7a9780 (2 аргументи, кастомний strstr-style)**, не memcmp; буфер накопичується з позиції 0.
3. **0x741d00 readAll** — взагалі не була в попередньому звіті (геп). Це окрема функція, що читає порціями по this+0xa.
4. **0x741bc0 і 0x7421d0** (одноразові send-копії) — теж **без жодного call-site** в усьому .text (раніше вважалися робочими копіями write; фактично мертві — працює лише варіант writeAll 0x741dd0).
5. **0x741870 accept** повертає сирий SOCKET (state не чіпає); «природний» наступник (0x741fc0 setSocket) також без калерів.
6. Стан **8** = «слухає» (bind+listen успішні) — нове значення стану, відсутнє в попередньому звіті.
7. Reader-потік: уточнено структуру об'єкта (ThreadSafeList + PThread wrapper), встановлення thread-fn як поля даних (+0x14), недетермінований ліміт довжини, dead alloc(8) на ітерацію.

## Непідтверджене (обмеження)
- Будь-які непрямі виклики мертвих функцій (0x7416a0/0x741740/0x741870/0x741d00/0x741bc0/0x7421d0/0x741fc0/0x741fe0/0x7466f0) через вказівники у .data/.rdata — **перевірити неможливо**: виконуваний файл відсутній (є лише Ghidra-проєкт `/tmp/Darkest Hour.exe/dhproj.rep_ghidra`), objdump-даних секцій немає. Висновок «мертвий код» стосується покритої області .text.
- Третій (регістровий) аргумент 0x748370, що ініціалізує +0x04 (структуру повідомлення), у декомпіляції не видно; не впливає на описаний цикл.
- Фактичний ліміт довжини повідомлення в reader-потоку — неініціалізоване значення стеку (не 100, як у читачів рядків 0x7455d0/0x7460d0).
